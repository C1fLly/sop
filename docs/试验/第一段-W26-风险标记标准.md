# 第一段 W26：哪些工单要标风险（第二稿）

状态：第二稿（2026-11-18）。写设计的人出初稿，Codex（接的是另一家的模型）独立复核一次，按复核意见改成本稿。用户知情即可，不需要他判断（设计书 W26：哪些算技术风险他判断不了）。第 2a 期按实际标出来的比例和复查发现的问题再校正一次。

花费：Codex 复核一次，记账 0.30 美元（按词元数用偏高的单价估的）。

初稿和 Codex 的复核原文在 `docs/试验/脚本/第一段/W26/`。

## 风险标记管什么

规划阶段（F6 拆工单时）给每张工单写一行「风险」。带风险标记的工单：

1. 单独做一次独立复查（T9，约 1.2 到 1.5 美元一次）。没标的跳过 T9，靠写代码的 AI 自查、结果校验、门禁，问题要到整个功能的复查（F16）才被独立地看到。
2. 脚本建议小白逐张验收（F13），而不是整份做完统一验收。

## 怎么写

`风险：无`，或者：

```
风险：R1、R3。调整「只看本公司订单」的筛选，写错可能让甲公司看到乙公司的订单。
验收动作：用甲公司的账号打开乙公司的一张订单，应提示没有权限。
```

- 说明里必须写清「改了什么，出错会影响谁、造成什么」。只写「涉及数据，风险较高」这种话，规划复查（F9）按不合格打回。
- 能让小白动手看到的，写一条验收动作和预期结果，写进验收卡。小白看不到的（密钥泄露、同时操作时数据错乱），写明靠哪项技术检查把关，不能把「建议逐张验收」当成有人把住了关。

## 怎么判断

- **以这张工单实际改变的行为为准**，不以文件名、不以它自称的类型为准。
- **先看下面的类别，命中任一条就标。**「一般不用标」那一节只在一条都没命中时才适用。例如只改登录页的提示文字：改的是文字，但它在登录页上，用户看到的登录行为没变，不标；要是同时改了「输错几次锁定」，属于 R1，标。
- 拿不准时就标。标多了的代价是多花复查的钱、多一次逐张验收；漏标的代价是问题晚发现。这句话只兜少数边界，每一类都写了明确的触发条件。

## 类别

| 编号 | 类别 | 必须标 | 一般不标 |
|---|---|---|---|
| R1 | 登录和权限 | 登录、退出、找回密码、会话过期、锁定；谁能看、谁能改哪条数据（含「只能看本公司的数据」）；角色和授权；审计日志 | 只改登录页的文字和样式，行为不变 |
| R2 | 钱和数量 | 影响结算、权益、资源分配或正式业务记录的计算：金额、价格、折扣、税费、余额、积分、库存、工时、请假天数；四舍五入；对账；按日期跨月跨年拆分的统计 | 只在页面上显示、不影响任何业务结果的数（「共 12 项」、展示用的百分比） |
| R3 | 数据的结构和去留 | 数据库结构变更（迁移文件）；删除数据、批量修改数据；导入；导出别人的数据或全量数据；数据的保留和清理；备份和恢复 | 下载当前用户自己在页面上已经看得到的那几条 |
| R4 | 对外的约定和外部服务 | 接口对外的行为变了：字段、错误码、默认排序、字段含义（不管改没改契约文件）；对外发送的接收人、范围、时机、重试方式变了；第三方服务的凭据、付费调用；拿第三方的返回结果做关键业务决定 | 只改通知的文案；只改地图的展示选项 |
| R5 | 关键业务状态和不能撤回的动作 | 改变业务状态怎么流转、进入下一步要满足什么条件（例如审批人能不能批自己的申请、已取消的订单还能不能处理）；已经产生外部影响、事后补偿也消除不了的动作（发出的邮件、扣的款、发的货）；会改数据、发消息或花钱的定时任务 | 只读的定时任务（刷新一个允许短暂过期的展示缓存） |
| R6 | 个人信息和保密数据 | 展示、搜索、记日志、缓存、导出、上报个人信息（身份证号、手机号、住址、银行卡）或公司的保密数据（报价、合同、经营报表）。看实际接触了什么，不靠产品流程里的分级当开关 | 不碰这类数据的页面 |
| R7 | 同时操作和资源 | 多个操作争用同一份资源、状态或额度（多人改同一条、同一人开两个页面、后台任务和人工操作同时进行）；排队、抢占、重复提交、去重；跨时区、跨天的时间计算；大批量查询、上传大小、任务执行方式的变化，可能把服务器拖垮 | 一般的性能优化，不改结果也不改限制 |
| R8 | 把关本身 | 删除测试、削弱断言、缩小测试范围、改测试的预期去迁就新的行为、改测试是否执行；改构建配置、检查工具的配置；新增「跳过这个测试」「这一行不检查」的标记 | 新增测试；给旧测试多加断言；只改测试的名字和整理测试数据 |
| R9 | 修复 | 由验收不通过、功能复查、功能门禁、GitHub 检查失败生成的修复工单，一律标（设计书 7.4） | （第一版不设例外，见下面「没有照办的」） |
| R10 | 密钥和安全设置 | 密钥和服务凭据怎么加载、放在哪（例如把服务端密钥打进浏览器的包里）；关闭证书校验；放宽跨域访问；改安全相关的响应头 | 无 |
| R11 | 不可信的输入 | 用户上传、解压文件；拿用户输入拼数据库查询、执行命令、读文件；显示用户写的富文本；按用户给的网址去抓内容。指这些处理和限制本身的改动，不是所有带输入框的页面 | 普通表单字段，经档案自带的校验和转义 |
| R12 | 运行环境和依赖 | 部署和运行的配置（容器、编排、环境配置的模板）；依赖的版本和锁文件；检查流程文件 | 只升级开发时用的辅助工具，不进正式构建 |

v0.7 的初稿里有一条「纯粹的重构且已有测试全部覆盖，可以不标」，第二稿删了。Codex 指出：覆盖率只说明代码被测试运行过，证明不了权限边界、失败路径、同时操作都被测对了，所以不能拿它豁免敏感逻辑的重构。现在重构照上表判断：碰到哪一类就按哪一类标。

## 谁标、谁审、脚本怎么兜底

- 规划阶段写工单的 AI 按本标准写风险行。规则写在项目规则 `AGENTS.md` 里，本标准随工具包版本走。
- 规划复查（F9）逐张审风险行：漏标的、说明是空话的，算阻断问题。
- **脚本兜底（T4）**：在 AI 做完、提交之后，看这张工单相对功能分支的**全部**改动（新增、修改、删除、改名、从敏感位置挪出去都算），碰到了档案声明的敏感位置，即使没标也做 T9。同时脚本在这张工单的风险行后面追加一句「脚本补标：碰到了某某位置」，并且如果还没验收，F13 的建议改为逐张验收。
- 敏感位置由各技术栈档案写具体的路径，不让脚本临时猜。至少要有这几类：
  - 登录和权限模块；
  - 核心业务规则（金额、库存、额度、状态流转、结算、对账）所在的模块；
  - 数据模型、数据访问和数据库查询、迁移文件、初始数据、批量修数据和备份恢复的脚本；
  - 外部服务和异步任务：支付、邮件、短信、回调、定时任务、队列、重试和去重；
  - 数据往外走的地方：日志、错误上报、统计、缓存、文件存储、导入导出；
  - 输入安全和安全配置：上传、解压、富文本、命令执行、跨域、证书、密钥加载；
  - 接口的定义：契约文件，以及路由、请求和响应的类型；
  - 部署文件、依赖清单和锁文件；
  - 已有的测试文件（被修改、删除、改名）；构建配置、检查工具的配置；新增的跳过或不检查标记。
- 本标准自己、`AGENTS.md`、档案里的敏感位置清单、决定做不做 T9 的配置，都是受保护路径（设计书 5.6），改它们走规范变更或工具包升级，守门检查拦着，不在这里重复。
- 敏感逻辑第一次写进一个新文件时，这个文件还不在敏感位置清单里，脚本兜不住。所以档案的敏感位置要按目录和模块写，不按单个文件写；写进新目录的，在规划复查和功能复查里看。这一处脚本保证不了，如实写明。
- 紧急修复流程里的工单总是做 T9（设计书 7.5）。

## 预计的比例和花费

类别比初稿多了，估计一个一般的业务功能有四到六成的工单会被标。按一个功能 10 张工单、标 5 张算，逐张复查约 6 到 7.5 美元，另外小白逐张验收的次数也多了。这是推算，第 2a 期按实际比例校正；比例明显偏高时，先收紧「一般不标」那一列，不先删类别。

## Codex 复核意见的处理

| 复核意见 | 处理 |
|---|---|
| 漏了密钥和安全设置、不可信输入、关键业务状态、运行环境和依赖、非个人的保密数据、备份恢复和资源耗尽 | 接受。加了 R10、R11、R12；R5 扩成「关键业务状态和不能撤回的动作」；R6 扩到保密数据；备份恢复并进 R3；资源耗尽并进 R7 |
| R8「改已有测试」太宽 | 接受。只有削弱测试的改动必须标；新增测试、多加断言不标。脚本兜底仍然看「已有测试被修改或删除」，因为脚本分辨不了削弱和加强，交给 T9 看 |
| R9 修复工单一律标，不分原因 | **没有照办。** 设计书 7.4 定了修复工单一律算带风险标记。理由：修复工单本身说明前面的把关漏过一次；而且「这次只是错别字」是写修复的 AI 自己说的，脚本核对不了。第一版宁可多花这一份复查的钱；第 2a 期看修复工单的实际比例，比例高再考虑只对文案和样式的修复设例外 |
| R3、R4、R5、R2 缺少后果门槛 | 接受。每一类都加了「必须标」和「一般不标」两列 |
| 「类别」和「举例」哪个决定命中；例外和类别冲突时谁优先 | 接受。写明以实际行为为准；先看类别，命中就标；「一般不标」只在一条都没命中时适用 |
| 「重构且覆盖率够就免标」不成立 | 接受。删了 |
| R6 不应靠产品分级当开关 | 接受 |
| 「不能撤回」应按外部影响判断 | 接受，写进 R5 |
| 「改接口契约」应看实际行为 | 接受，写进 R4 |
| R7 理解得太窄 | 接受，改成「争用同一份资源、状态或额度」 |
| 说明可能是空话 | 接受。规定说明要写清影响谁、造成什么，F9 把空话打回 |
| 脚本兜底的敏感位置清单漏了几类 | 接受，补齐 |
| 兜底要看最终的全部改动，并把补标写回工单、影响验收建议 | 接受。设计书 7.5 原来只写了「T4 核对改动范围时」，本稿写明看的是提交后相对功能分支的全部改动，补标写回风险行，并改 F13 的建议 |
| 敏感逻辑写进新文件时兜不住 | 接受，如实写明；档案按目录和模块写敏感位置 |
| 风险标记要带小白能做的验收动作 | 接受，写进「怎么写」 |
