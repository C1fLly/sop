# 检查库

设计书第 14 节。约定（14.1）：

- 每个检查一个目录 `checks/<名字>/`，脚本是 `check.py`，只判断一件事，只读，不改项目。
- 用法：`check.py <参数文件.json> [--report <报告.json>]`。退出码 0 通过、1 不通过、2 无法判断；标准输出一行结论；详细报告写成 JSON。
- 每个检查附至少一个「应通过」和一个「应报错」的样例：`samples/pass-*/`、`samples/fail-*/`。样例目录里有 `args.json`（里面的 `{CASE}` 换成样例的临时副本所在的位置），需要先造现场的再放一个 `setup.sh`（在临时副本里执行）。
- 总检查 `total_check.py` 逐个跑所有样例（16.1）：没有「应报错」样例的检查不合格；「应报错」的样例上没报错的检查不合格。
- 结论要由检查自己写出来：`lib.cli` 收尾时在 JSON 报告里写上「退出码」「结论」两项。总检查只认这一份：报告读不出、没记退出码、记的和进程的退出码对不上，都算检查自己崩了，不符合（Python 没兜住的错退出码也是 1，例如一导入就崩，不能冒充报出了问题）。所以检查一律经 `lib.cli` 收尾。
- 每个检查在 `check.py` 开头写明在哪里运行（本机 / 两处）。

## 规划文件的格式（工具包的约定，写进项目规则；技能实际产出的样子第 2a 期核对，W25）

规格 `.scratch/<功能>/spec.md`：

```
# 标题
## 用户故事
- S1：作为……我要……以便……
## 技术            ← 以「## 技术」开头的节（含它下面的小节）是技术部分，T8 之后只许改这几节
```

工单 `.scratch/<功能>/issues/<两位编号>-<短名>.md`：

```
# 01 标题
状态：未开始
依赖：无            （或：02、03）
覆盖：S1、S2
风险：无            （或：类别：理由）
## 要做什么
## 验收标准
- [ ] AC1：……
## 评论
```

验收卡 `.scratch/<功能>/cards/<编号>.md`：每一步写明对应哪条验收标准，形如 `1. [AC1] 前置……；操作……；预期……`。

实现阶段工单文件里只许变：勾选框、「状态：」那一行、「## 评论」那一节（14.2 的「已确认内容」）。
