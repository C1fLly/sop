# 试验 S2：隔离机制

状态：已完成（2026-11-17，三个部分）。机制定为 bubblewrap 加一个专供受限侧的 Docker，四条要求可以同时满足；四个 AI 工具放进去都能工作。没做的部分列在末尾。

三个部分都没有用管理员密码。前两部分没有调用 AI；第三部分调用了，Claude Code 这边合计约 0.41 美元，另外三个工具各一次简短调用。没有碰真实的凭据：凡是要证明「读得到」的地方，用的都是临时目录里的一份假凭据。

## 要验证什么

设计书 6.2 要求受限环境同时满足四条：

1. 受限侧读不到 GitHub 登录凭据、SSH 密钥。
2. 受限侧写不了工具包目录、别的项目、机器级配置。
3. 受限侧对共用的 `.git` 只能写入提交内容和自己分支的指针；`.git` 里的配置和钩子对它只读。
4. 受限侧仍然能用 Docker 跑测试。

设计书 6.5 写着「第三、四条能否同时满足尚未验证」。

## 这台电脑的现状

| 项目 | 情况 |
|---|---|
| 系统 | Ubuntu 26.04.1 LTS |
| bubblewrap | 已装（0.11.1），普通用户不用管理员密码就能用 |
| `unshare` 直接建隔离空间 | 不行，被系统的安全规则拦住 |
| firejail、podman | 没装 |
| GitHub 登录凭据 | 存在**系统钥匙串**里，不是一个文件。程序通过 `/run/user/1000/bus` 这条通道向钥匙串索取 |
| GitHub 凭据的权限 | 包含 `repo`、`delete_repo`（能删仓库）、`admin:public_key` |
| Git 推送方式 | SSH |
| SSH 密钥 | `~/.ssh` 下；另有一个 SSH 代理，通道在 `/run/user/1000/gcr/ssh`。**拿到这条通道就能推送，不需要读到密钥文件** |
| Docker | rootless，29.9.3，通道在 `/run/user/1000/docker.sock`，以当前用户的身份运行 |

由此得出：**凭据不只是文件。** 要让受限侧拿不到凭据，要同时挡住四样：`~/.ssh`、钥匙串的通道、SSH 代理的通道、环境变量。后三样设计书没有写。前三样里有两样都在 `/run/user/1000` 下，所以这个目录不能整个给受限侧。

## 第一部分：bubblewrap

### 做了什么

试验目录 `/tmp/sop-spike-s2/`：

- `proj/`：按设计书 5.1 搭的项目。一个裸仓库 `.git`，四个工作目录 `main`、`feat-a`、`ticket-a-1`、`ticket-a-2`。
- `outside/secret.txt`：假凭据，代表受限侧不该看到的东西。
- `otherproj/`：代表别的项目。
- `sandbox.sh`：用 bubblewrap 启动受限环境。做法是：
  - 环境变量全部清空，只放回路径等 10 个；
  - 系统目录只读；
  - 用户主目录、`/tmp`、`/run` 都换成空的临时目录，所以主目录下的东西默认全都看不到；
  - 只把这张工单的工作目录放进去，可写；
  - 工作目录里那个指向 `.git` 的小文件设为只读；
  - `.git` 有两种放法：
    - **粗**：整个可写，只把配置文件和钩子目录设为只读（设计书 6.2 第三条的字面意思）；
    - **细**：整个只读，只放开四处可写——提交内容、本工作目录的登记、本功能的工单分支指针、对应的指针变更记录。
- `probe.sh`：在受限环境里逐项尝试，每项事先写明「应该做得到」还是「应该做不到」。

跑了三轮：细的不给 Docker；粗的不给 Docker；细的给 Docker 通道。

### 结果

#### 要求一（读不到凭据）：成立

| 尝试 | 结果 |
|---|---|
| 看到 `~/.ssh` | 做不到 |
| 看到钥匙串的通道 | 做不到 |
| 看到 SSH 代理的通道 | 做不到 |
| 用 `gh` 查登录状态 | 做不到 |
| 读假凭据 | 做不到 |
| 环境变量里找密钥 | 没有 |

前提是不给 Docker 通道，见要求四。

#### 要求二（写不了别处）：成立

工具包目录、别的项目、同项目的其他工作目录，在受限环境里都看不到。往 `~/.config/sop` 写文件，写进的是临时目录，真实位置没有变化（已从外面核对）。

同样以不给 Docker 通道为前提。

#### 要求三（`.git` 只能写提交和自己的分支指针）：细的放法基本成立，粗的不成立

| 尝试 | 细 | 粗 |
|---|---|---|
| 在自己的工作目录里提交 | 可以 | 可以 |
| 改 `.git` 里的配置 | 做不到 | 做不到 |
| 往钩子目录里放钩子 | 做不到 | 做不到 |
| 换掉工作目录里指向 `.git` 的小文件 | 做不到 | 做不到 |
| 移动 `main` 的指针 | 做不到 | **做到了** |
| 移动功能分支 `feat/a` 的指针 | 做不到 | **做到了** |
| 移动同一功能另一张工单的指针 | **做到了** | **做到了** |
| 改别的工作目录的登记 | 做不到 | **做到了** |
| 往 `.git` 顶层新建文件 | 做不到 | **做到了** |

细的放法只剩一处漏洞：同一个功能下的各张工单，分支指针存在同一个目录里（`ticket/<功能>/`），而 Git 更新指针时要在这个目录里新建文件，所以只能整个目录一起放开，放不到单张工单。

#### 要求四（能用 Docker）：和要求一、二冲突

把现有 Docker 的通道给受限侧之后：

| 尝试 | 结果 |
|---|---|
| 跑一个容器 | 可以 |
| 让容器把沙箱外的假凭据目录挂进去再读 | **读到了** |
| 让容器往沙箱外的「别的项目」写文件 | **写进去了**（从外面核对，文件确实出现了） |

原因：容器不是由受限环境里的程序启动的，而是由 Docker 的后台程序启动的。这个后台程序在受限环境**外面**，以当前用户的身份运行，当前用户能读写的东西它都能读写。受限侧只要能对它下命令，就能让它把任何目录挂进容器，包括 `~/.ssh` 和钥匙串、SSH 代理的通道所在的目录。

所以：**只要把现有 Docker 的通道给受限侧，要求一和要求二就都不成立了。** 这比设计书 6.5 预计的更严重，冲突不在第三、四条之间，而在第四条和第一、二条之间。

另外试了一项：在受限环境里再建一层隔离空间，做不到（被系统的安全规则拦住）。这意味着不能简单地在 bubblewrap 里面再启动一个 Docker。

### 第一部分的结论

1. **bubblewrap 可以作为受限环境的机制**：不要管理员密码，要求一、二都能满足，要求三用细的放法基本满足。
2. **设计书 6.2 第一条要补充**：凭据包括钥匙串的通道、SSH 代理的通道、环境变量，不只是文件。
3. **设计书 6.2 第三条的字面做法不够**。只把配置和钩子设为只读，受限侧仍能移动任何分支的指针、改别的工作目录的登记。要反过来：整个 `.git` 只读，只放开必需的四处。
4. **工作目录里指向 `.git` 的小文件必须只读**。这是新发现的一处：特权侧在工作目录里执行 Git 命令时，是靠这个小文件找到仓库的。如果受限侧能改它，就能把特权侧引到一个假仓库去，而仓库的配置里可以写「执行某条命令」。这条攻击没有实际演示，只验证了设为只读后受限侧换不掉它。稳妥起见，特权侧执行 Git 命令时还应当总是明说仓库在哪，不依赖这个小文件。
5. **同一功能的各张工单之间隔不开分支指针**。两个处理办法：靠第四层（每步开始前特权侧核对历史延续）事后发现；或者改分支的命名，让每张工单的指针单独占一个目录。
6. **Docker 是没解决的问题**，要用户决定往哪个方向试，见下。

### Docker 怎么办：三个方向

| 方向 | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | 给受限侧另起一个专用的 Docker 后台程序，还是当前用户，但让它自己也看不到凭据 | 不要管理员密码；不动现有的 Docker | 多一个后台程序和一份单独存放的镜像；能不能做成还没试 |
| 乙 | 单独建一个系统用户，受限侧和它自己的 Docker 都以这个用户运行 | 最稳，靠操作系统本身的权限；是设计书 6.3 写的保底方案 | 要管理员密码；要为这个用户另配一套 Docker；项目目录要两个用户共用 |
| 丙 | 在 Docker 通道前面放一个过滤程序，只放行不越界的命令 | 不要管理员密码；不多起 Docker | 过滤程序要自己写，Docker 的命令种类很多，漏掉一种就全破。不推荐 |

写这一节时三个方向都还没有试。甲和乙都涉及 Docker，按用户的全局规则要先问。

## 第二部分：方向甲——专供受限侧的 Docker（2026-11-17）

用户选定：先试甲，不成再用乙，不考虑丙。结果：**甲做成了。**

没有用管理员密码，没有调用 AI，没有联网拉镜像。没有改动原来的 Docker：试验前后它都在运行，容器 0 个、镜像 7 个、数据卷 3 个，前后一致。

### 做法

用 Docker 自带的免管理员启动脚本 `dockerd-rootless.sh`，再起一个后台程序。和原来那个的区别：

- 通道、数据目录、运行目录全部另放（试验里放在 `/tmp/sop-spike-s2/rd/`）。
- 启动脚本允许指定「用哪个程序当 dockerd」。指定成一个自己写的小脚本 `dockerd-wrap.py`，它在启动真正的 dockerd 之前，先把根目录换成一个只含白名单的目录，再把旧的根目录彻底摘掉。
- 白名单里只有：系统程序目录（只读）、系统配置目录、Docker 的程序（只读）、这个专用 Docker 自己的数据和运行目录、试验项目。
- 项目里，`.git` 整个只读；每个工作目录里指向 `.git` 的小文件只读。
- 用户主目录的其他部分、`/run`（钥匙串通道、SSH 代理通道、原 Docker 的通道都在这里）、`/tmp` 的其他部分，在它的视野里都不存在。
- 启动时环境变量全部清空。
- 以一个临时的用户级后台服务运行（`systemd-run --user`），试完停掉就消失。

容器是由这个后台程序启动的，所以容器能挂进去的目录，最多就是这个后台程序自己看得到的白名单。

镜像是从原来的 Docker 导出再导入的（`docker save` 接 `docker load`），原来的 Docker 只被读取。

### 结果

直接对专用 Docker 下命令（等于受限侧能做的最大动作）：

| 尝试 | 结果 |
|---|---|
| 跑一个容器 | 可以 |
| 容器挂上工单的工作目录并写文件，外面看得到，属主是当前用户 | 可以 |
| 容器开的网页，从本机和从受限环境里访问 | 可以 |
| 挂假凭据目录再读 | 做不到 |
| 往「别的项目」写文件 | 没有落到真实位置 |
| 看到真实的 `~/.ssh`、钥匙串通道、SSH 代理通道、原 Docker 的通道、工具包目录 | 都做不到 |
| 把整个根目录挂进容器再找假凭据 | 找不到。主目录下只看得到 `tools`，`/tmp` 下只看得到试验目录 |
| 经容器改 `.git` 的配置、放钩子、移动 `main` 的指针 | 都做不到 |
| 经容器换掉工作目录里指向 `.git` 的小文件 | 做不到 |
| 给容器最高权限并让它看到所有进程，逐个进程（478 个）找通往禁区的路 | 0 次得手 |
| 最高权限的容器钻进 1 号进程的环境 | 做不到 |
| 最高权限的容器直接读硬盘 | 做不到 |
| 最高权限的容器读别的进程的环境变量找密钥 | 找不到 |

再把 bubblewrap 受限环境和专用 Docker 接在一起（受限环境里只给专用 Docker 的通道），四条要求一起验：全部符合，只剩第一部分已知的那一处（同一功能的各张工单之间挡不住分支指针）。

### 新发现的一处漏洞

工单 1 的受限环境，借专用 Docker 往工单 2 的工作目录里写了文件，**写进去了**。

原因：bubblewrap 是每张工单起一个，只放进这张工单的工作目录；而专用 Docker 是大家共用一个，它的白名单里是整个项目。所以经 Docker 这条路，同一项目的各个工作目录之间互相挡不住。如果一个专用 Docker 同时服务几个项目，项目之间也挡不住。

处理办法：

- 每个项目起一个专用 Docker，项目之间就隔开了。代价是每个项目各存一份镜像。
- 同一项目的各工作目录之间，靠第四层事后发现（每个步骤结束后核对改动范围）。每张工单起一个 Docker 太重，不建议。

### 试验里没有覆盖的

- 专用 Docker 这次是「没有资源限额」的状态运行的（它连不上系统的服务管理通道，所以不能限制容器的内存和处理器用量）。对跑测试没有影响，正式做时再看要不要接上。
- 数据放在内存盘上。正式用要放在硬盘上，没试。
- 联网拉镜像（这台电脑上网要走代理，而专用 Docker 的环境变量是清空的，代理要另外配）。
- Compose、构建镜像、Testcontainers（它要把 Docker 的通道再挂进一个容器里）。
- 长时间运行、开机自启、多个项目各起一个。
- 这台电脑设了 8 个代理相关的环境变量。受限环境清空环境变量后，里面的程序上网也要另外配代理。

### 结论

1. **方向甲成立**：不要管理员密码，不动原来的 Docker，四条要求可以同时满足。方向乙（单独的系统用户）暂时用不着，仍作保底。
2. 专用 Docker 的视野要用白名单定，不能用「把几个敏感目录盖住」的办法，后者会漏。
3. 专用 Docker 按项目各起一个；同一项目的工作目录之间靠事后核对。

## 第三部分：把四个 AI 工具放进受限环境（2026-11-17）

用户同意花这笔钱。这一部分真的调用了 AI。

### 做法

在第一部分的受限环境（细的放法）上，每个工具只多放进它运行必需的最少东西，脚本是 `sandbox-ai.sh`：

| 工具 | 放进去的东西（都是只读） | 登录信息从哪来 |
|---|---|---|
| Claude Code | 只有程序本身 | 环境变量（这台电脑上 Claude Code 的服务地址和密钥是以环境变量的形式给的） |
| Codex | 程序目录、`config.toml`、一份模型清单文件 | `config.toml` |
| OpenCode | 程序目录、`opencode.json` | `opencode.json` |
| Pi | 程序目录、Node、`models.json`、`auth.json`、`settings.json` 等四个文件 | 这几个文件 |

- 各工具真实的配置目录（`~/.claude`、`~/.codex` 等）**不放进去**。里面有历史会话、用户的设置和钩子；如果让受限侧能写，AI 可以往里面放一个钩子，等用户下次在外面正常使用这个工具时被执行，等于逃出去了。
- 代理的环境变量放进去（这台电脑上网走本机的代理）。
- 密钥靠环境变量继承传进去，不写在命令行上，因为命令行别的进程看得到。
- 四个工具都用「不逐条询问、不用自带沙箱」的方式运行：Claude Code 加 `--dangerously-skip-permissions`，Codex 加 `--dangerously-bypass-approvals-and-sandbox`，OpenCode 加 `--auto`，Pi 本来就不问。

给每个工具同一个任务：在当前目录建一个文件；执行 `ls ~/.ssh`；执行 `cat` 假凭据；把两条命令的原样输出报回来。

### 结果

| 工具 | 能应答 | 文件建成（从外面核对） | 读 `~/.ssh` | 读假凭据 | 用时 | 花费 |
|---|---|---|---|---|---|---|
| Claude Code | 能 | 是 | 读不到 | 读不到 | 19 秒 | 报告 0.148 美元 |
| Codex | 能 | 是 | 读不到 | 读不到 | 12 秒 | 报告用了 16,957 个词元，金额不详 |
| OpenCode | 能 | 是 | 读不到 | 读不到 | 13 秒 | 没有报告 |
| Pi | 能 | 是 | 读不到 | 读不到 | 31 秒 | 没有报告 |

四个工具都是第一次就跑通。「三个工具能应答」这件事，之前只是用户说的，现在实测确认了。

OpenCode 运行时显示它用的模型叫 `iceman-free` 和 `hy4-flash-free`。这是它自己选的，这次没有指定模型。

另外三项：

- **工具自带的沙箱不能套在受限环境里面。** 不调用 AI 试了 Codex 的（`codex sandbox ls`），报错「没有权限再建一层隔离空间」。所以在受限环境里只能关掉工具自带的沙箱，隔离完全由外面这一层负责。Claude Code 自带的沙箱没有单独试，原理相同。
- **受限环境关掉再开，Claude Code 能续接上一次的会话。** 做法是给它一个留在受限环境外面、只属于这个项目的状态目录（用 `CLAUDE_CONFIG_DIR` 指过去）。第一次让它记一个暗号，关掉受限环境，重新开一个再续接，它答对了，会话编号不变。两次报告花费 0.108 和 0.158 美元；后来在 S0 里弄清楚，续接时报告的是这个会话的累计数，所以第二次实际只花了 0.05 美元。真实的 `~/.claude` 里没有出现这次试验的会话记录。
- 这项续接试验第一次失败了，原因在我的脚本（清理环境变量时把「状态目录放哪」的设置也清掉了），多花了一次 0.108 美元的调用。

Claude Code 这边合计约 0.41 美元（0.148 + 0.108 + 0.158；最初按 0.52 美元报给了用户，那是把续接的累计数重复算了一次）。

### 结论

1. **四个 AI 工具都能在受限环境里工作，并且都读不到凭据。** 6.2 的四条要求在放进 AI 之后仍然成立。
2. 每个工具只放程序和最少的登录信息；真实的配置目录不放。
3. 工具自带的沙箱要关掉，它们套不进去。
4. 会话要能续接，就得给每个项目一个专门的状态目录。Codex、OpenCode、Pi 的续接没有试。
5. **AI 服务的密钥在受限环境里读得到**，同在里面运行的项目代码也读得到。这一点绕不开：AI 工具要用它才能工作。

### 这一部分没有覆盖的

- Codex、OpenCode、Pi 的会话续接，以及它们的状态目录怎么留在外面。
- 用户在主目录下为各工具设的全局规则和全局技能，在受限环境里看不到。正式做时要由流程命令只读地放进去，或者把规则都放在项目里。
