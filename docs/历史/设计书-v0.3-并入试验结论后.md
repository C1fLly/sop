## 1 目标与边界

### 1.1 目标

让一个没有编程基础的人（下称**小白**）指挥 AI 完成企业生产级项目的开发、上线和运维。小白只看行为、不看代码。工具包要让 AI **精准**、**高效**、**高质量**地开发：每一步知道唯一目标和边界；不需要人参与的步骤自动连续执行；把关靠脚本和独立复查，不靠 AI 自述。

### 1.2 范围

| 方面 | 范围 | 谁定的 |
|---|---|---|
| 操作系统 | Ubuntu 26.04 LTS；24.04 LTS 待 wt 在其上测试通过后加入 | 用户定了只支持 Ubuntu；版本是设计 |
| 代码托管 | GitHub | 由使用 wt 推出 |
| 仓库形式 | 裸仓库加 worktree，由 wt 管理 | 用户 |
| AI 工具 | Claude Code、Codex、OpenCode、Pi，都在第一版 | 用户 |
| 技能 | mattpocock/skills | 用户 |
| 技能文件 | 原样使用，技能目录里的任何文件都不改。原因：技能会更新，更新会把改动盖掉。工具包自己的约定只能写在技能之外（附录 B） | 用户（2026-11-17） |
| 技术栈 | 两套后端，可按统一接口增补 | 用户 |
| 端 | 第一版 Web 管理后台，其他端在第一版之后 | 用户 |
| 生命周期 | 需求到上线运维。其中部署、发布、线上运维这几块的开发**暂缓**，什么时候恢复由用户定（第 19 节）；其余照常 | 用户（暂缓是 2026-11-17 定的） |
| 带路窗口 | 常驻 | 用户 |
| 实现路径 | 流程命令编排、原样运行 `implement-spec`，都在第一版，每次由小白选 | 用户 |
| 工具包仓库 | 公开 | 用户 |
| wt 仓库 | 私有 | 用户 |
| 参考部署平台 | 一个海外托管平台。S8 的纸面首选是 Render，没有注册和实测；随部署相关的开发一起暂缓 | 用户定了方向 |
| GitHub 付费计划 | 不开通。项目仓库公开时用分支保护，私有时由小白在网页上手动点合并 | 用户 |
| 第 0 期的主链试走 | 由 AI 扮演小白 | 用户 |
| 兜底 | 没有专业技术人员 | 用户 |
| 已有的旧项目 | 不在第一版范围内 | 设计 |

### 1.3 红线

出现下列情况，流程命令停止并说明原因和可以购买哪类专业服务：

- 需求属于受监管业务：持牌金融、医疗数据、未成年人数据等。
- 预期规模需要多机房容灾或分布式架构。P1 用业务语言询问（多少人用、最忙时同时多少人、停一小时损失多大），由脚本换算。
- 需要手写密码处理、令牌签发、加密算法、支付清算逻辑。使用成熟框架自带的登录模块或第三方身份服务不属于此列。开发过程中由红线扫描（14.2）检查。

用户要的是「大型企业生产级」。本工具包能支撑的是单一数据中心内可水平扩展的系统，超过这个规模属于上面第二条。

### 1.4 设计解决不了、只能降低的风险

- 工具包自身由 AI 编写和测试，没有专业人员最终把关（第 16 节）。
- 隔离防的是 AI 走捷径，不是蓄意绕过（第 6 节）。
- 规格本身理解错了而小白确认了它。
- 复查的 AI 与写代码的 AI 有相同的盲区。
- 架构失误和扫描器覆盖不到的安全漏洞。
- 第 0 期的主链试走由 AI 扮演小白，测不出用户本人会卡在哪里；这要到第 2a 期用户第一次真正上手时才知道。

## 2 设计原则

| 编号 | 原则 | 含义 |
|---|---|---|
| Y1 | 脚本优先 | 一件事能由脚本做，就不交给 AI；能由 AI 做，就不交给人 |
| Y2 | 一步一责 | 每个步骤只有一个执行者、一个产出、一个出口检查。一个技能一次产出的一组文件算一个产出 |
| Y3 | 进度靠事件日志 | 每个步骤的开始、完成、失败、跳过、重新打开都由流程命令记成事件并推送；当前位置由事件按流程定义回放得出 |
| Y4 | 能继续的一切都在远程 | 继续开发所需的内容都在 Git 远程仓库、GitHub 和部署平台上；本机只有可重建的开发环境文件、缓存和日志 |
| Y5 | 无全局状态 | 当前项目、当前工单从当前目录得出 |
| Y6 | 不采信自述 | AI 说「完成」「我照做了」都不算数，由脚本验证或事后核对 |
| Y7 | 输入精确 | AI 每一步收到的是脚本拼好的任务包，只含这一步需要的内容 |
| Y8 | 一处定义 | 每条规则、每份配置只存在一份，其他地方引用或由它生成 |
| Y9 | 变化点在接口后 | AI 工具、技术栈、端、部署方式各自是可替换的模块，接口固定 |
| Y10 | 可审计 | 流程命令执行的每条命令都打印并记入日志，供维修窗口和独立审查使用 |
| Y11 | 新改动不降低质量 | 质量指标按本次改动的代码衡量，不按全项目总量衡量 |
| Y12 | 特权侧不运行项目代码 | 拿着登录凭据的那一侧只做推送、合并、记账；凡是 AI 写的或项目里的代码，都在读不到凭据的受限侧运行 |

Y2 的已知例外如实列出：7.3 的 P2、P3 和 7.7 的 R5 是「脚本给出建议，人确认」；7.4 的 F8 一次产出验收卡和摘要两类文件。

## 3 总体结构

### 3.1 模块

| 模块 | 单一职责 |
|---|---|
| 引导 | 在一台什么都没有的电脑上把工具包装到能运行 |
| 内核 | 读流程定义、读写事件日志、拼任务包、调用执行者、校验结果 |
| 受限运行器 | 在读不到凭据的环境里启动 AI 和一切项目代码 |
| 流程定义 | 声明有哪些流程、步骤、顺序 |
| 检查库 | 每个检查一个脚本，判断一件事是否成立 |
| 提示词库 | 每个 AI 步骤一个任务包模板 |
| 技能副本 | 固定版本的 mattpocock/skills，原样，不改动 |
| AI 工具适配器 | 把「交互启动」「自动调用」翻译成具体工具的命令 |
| 技术栈档案 | 一套后端技术栈的全部预置决定和命令 |
| 端档案 | 一种端的原型、测试、验收、发布方式 |
| 部署档案 | 一个部署平台的开通、部署、回退、备份、日志、告警、线上体检脚本 |
| 机器层 | 工具清单、安装、体检、网络设置 |
| 带路与维修 | 带路窗口和维修窗口的启动词和规则、小白手册 |
| 自测 | 验证以上所有模块 |

### 3.2 仓库和安装目录

工具包仓库（GitHub 公开仓库，开启分支保护）的内容：

```
bootstrap.sh            第零步引导脚本（只用 bash）
kernel/                 内核（Python，只用标准库）
runner/                 受限运行器
flows/                  流程定义（TOML）
checks/                 检查库，每个检查附「应通过」和「应报错」的样例
prompts/                任务包模板
skills/                 技能副本（原样）、许可证、版本记录
adapters/ai/<工具名>/    AI 工具适配器
profiles/stack/<名称>/   技术栈档案
profiles/end/<名称>/     端档案
profiles/deploy/<名称>/  部署档案
machine/                工具清单、安装脚本、体检、网络设置
templates/project/      新项目仓库的初始文件
guide/                  带路和维修的启动词、小白手册、破坏演练脚本
tests/                  自测
docs/                   设计书、审查记录、依据
```

装到电脑上的样子：

```
~/tools/sop/
  sop                    启动器：按项目声明的版本找到对应目录并执行
  versions/<提交编号>/    每个已安装版本一个目录，内容就是上面仓库在那个提交时的样子
```

- 版本用提交编号标识，不用可以被改动的标签名。
- 多个版本并存，每个项目在 `sop.json` 里声明自己用哪个，升级一个项目不影响其他项目。
- 机器级命令（体检、安装）使用已安装的最新版本。

### 3.3 语言和格式

- 引导脚本只用 bash。
- 内核用 Python，只用标准库，经 `uv run` 执行。
- 检查脚本用 shell 或 Python。
- 工具包自带的声明文件（流程定义、档案、工具清单）用 TOML，只读。
- 脚本写出的文件一律用 JSON，包括项目声明 `sop.json`、风险分级、网络设置、工具位置登记、结果文件、事件。
- Node 相关一律用 nvm 加 pnpm 和 `pnpm dlx`。

### 3.4 AI 的五种角色

| 角色 | 做什么 | 能改什么 | 怎么启动 |
|---|---|---|---|
| 执行 | 按任务包写代码、写文档 | 只能改任务包允许的路径 | 流程命令启动，自动或交互 |
| 复查 | 审查规划或代码，只报告 | 只能写自己的结果文件 | 流程命令自动调用，全新会话 |
| 技术决策 | 回答技术问题，依据是档案和决策记录 | 只能新增决策记录；规格和工单的修改由执行角色按它的决定去做 | 流程命令自动调用 |
| 带路 | 向小白解释现状、对照书面标准帮助判断 | 不能改任何东西 | `sop guide`，常驻 |
| 维修 | 处理机器、工具、环境的故障 | 机器环境；不能改项目代码和事件日志 | `sop repair` |

所有 AI 窗口都由 `sop` 启动，包括需要小白粘贴内容的情况。小白不自己打开 AI 窗口，这样每个窗口都在受限环境里。

## 4 机器层

### 4.1 支持的系统

Ubuntu 26.04 LTS。wt 的说明书列出它在 22.04 和 26.04 上测试通过，没有 24.04；24.04 要等 wt 自己的测试在上面跑通后才列为支持。装机流程用全新安装的虚拟机验证。

### 4.2 第零步：引导

1. 小白在终端执行印在小白手册首页的一条命令，用系统自带的下载工具取得 `bootstrap.sh` 并运行。用哪个下载工具在虚拟机上核实后写定。
2. `bootstrap.sh` 先问网络情况（是否需要代理、是否用国内软件源），再用 apt 安装 git 和 curl，把工具包取到 `~/tools/sop`，安装 uv。需要管理员密码时由系统直接向小白询问。
3. 完全连不上外网时，支持从另一台电脑下载离线包后用 U 盘拷入。
4. 结束时提示执行 `sop machine setup`。

### 4.3 固定位置

| 内容 | 位置 |
|---|---|
| 工具包 | `~/tools/sop/versions/<提交编号>` |
| wt | `~/tools/wt` |
| Docker（rootless） | `~/tools/docker` |
| 工具包新装的运行时 | `~/tools/<名称>-<版本>`，多个版本并存 |
| Node | nvm 管理，版本由项目的 `.nvmrc` 指定 |
| Python | uv 管理，版本由项目的 `.python-version` 指定 |
| 项目 | `~/Project/<项目名>`，项目名只用小写字母、数字和 `-` |
| 项目的开发环境文件 | `~/Project/<项目名>/.shared/.env`，只含本机开发用的值 |
| 运行日志 | `~/Project/<项目名>/.shared/runs/` |
| 机器级配置和登记 | `~/.config/sop/`（网络设置、工具实际位置、端口登记） |

电脑上已经装好、位置不符合上述规则的工具不算不合格，体检把它的实际位置登记下来，之后按登记的位置使用。

### 4.4 工具清单和网络设置

- `machine/tools.toml` 是基础工具的唯一清单：名称、版本要求、安装位置、检查命令、安装脚本、是否需要管理员权限。
- 技术栈档案需要的运行时写在档案自己的 `toolchain.toml` 里，项目选定档案后一并体检。
- 网络设置在 `~/.config/sop/network.json`，由第零步写入、之后可改。安装脚本按它配置各工具；体检检查 GitHub、AI 服务、各软件源是否连得上。

### 4.5 机器流程

| 步骤 | 名称 | 执行者 | 产出 | 出口检查 |
|---|---|---|---|---|
| M0 | 引导 | 脚本（小白执行） | 网络设置、git、curl、工具包、uv | `sop` 能运行 |
| M1 | 体检 | 脚本 | 体检报告 | 报告已生成 |
| M2 | 安装工具 | 脚本（小白在终端执行） | 清单上不需要登录就能取到的工具 | 这些工具符合清单 |
| M3 | 登录 GitHub | 人（工具包自带的引导脚本） | GitHub 登录状态和 SSH 密钥 | `gh auth status` 通过，SSH 连通 |
| M4 | 登录 AI 工具 | 人（工具包自带的引导脚本） | 各 AI 工具的登录状态 | 启用的每个适配器自检通过 |
| M5 | 安装 wt | 脚本 | `~/tools/wt` | `wt doctor` 的环境部分通过 |
| M6 | 准备受限环境 | 脚本 | 第 6 节所需的隔离设置 | 隔离自检通过（6.2 的四条要求） |
| M7 | 安装全局规则 | 脚本 | 各 AI 工具全局规则文件里的受管段落 | 段落内容与工具包里的一致 |

- 引导脚本都是工具包里写好的，不由 AI 生成。
- wt 的仓库是私有的，所以它的安装排在登录 GitHub 之后。
- 全局规则只含与工具包版本无关的机器级规则（包管理、Docker）。与流程有关的规则都在项目里，随项目声明的版本走。

### 4.6 三种场景

| 场景 | 步骤 |
|---|---|
| 新电脑、新项目 | 第零步，`sop machine setup`，`sop project new` |
| 新电脑、继续旧项目 | 第零步，`sop machine setup`，`sop project clone <所有者/项目名>`，按提示补装项目需要的运行时，执行 `sop` 接着做 |
| 已有电脑、多一个项目 | `sop project new` |

### 4.7 换电脑时每样东西在哪里

| 内容 | 在哪里 | 换电脑怎么恢复 |
|---|---|---|
| 代码、规格、工单、验收卡 | Git 远程仓库的代码分支 | 克隆 |
| 进度（事件日志） | Git 远程仓库的日志分支 | 克隆 |
| 进行中的功能和工单 | 远程分支；每个步骤完成后流程命令都会推送 | `sop project clone` 按远程分支和事件日志重建工作目录 |
| 每条分支以谁为基准 | wt 记在本机；事件日志里另记一份 | wt 在新电脑上会按 PR 的目标分支把基准补记回来（S3 实测）；事件日志里的那一份是双保险（S6 实测可据此重建）；开 PR 时流程命令总是显式指定目标分支 |
| 追问到规格、工单之间的对话 | 只在本机的 AI 会话里；追问结束时写出的交接文件在远程 | 见下 |
| 项目的 wt 钩子 | 工具包自带，不属于项目 | 克隆时安装 |
| AI 的长期笔记 | 仓库内 `docs/notes/` | 克隆 |
| 技能文件 | 仓库内 | 克隆 |
| 工具包版本 | `sop.json` 声明 | 克隆时自动安装 |
| 开发环境文件 `.shared/.env` | 本机 | 按仓库里的清单重新生成；第三方测试密钥按引导重新填写 |
| 线上密钥 | 部署平台和 GitHub 的密钥存储 | 开发电脑上本来就没有 |
| 开发数据库里的数据 | 本机 | 不恢复，由迁移和种子数据重建 |

如实说明三种会丢东西的情况：

- 自动步骤进行到一半时旧电脑损坏：丢一个步骤，重做。
- 对话步骤（F2、F5、F6）进行到一半时换电脑：对话不在远程，这一步要重做；已写出的交接文件能减少重复。
- 原样运行 `implement-spec` 的路径：每合入一张工单推送一次，最多丢一张工单的实现。

GitHub 是唯一的远程。`sop backup` 把整个仓库打成一个备份文件存到小白指定的另一个位置，体检流程会提醒执行。

## 5 项目层

### 5.1 项目根目录（本机）

```
~/Project/<项目名>/
  .git/                        裸仓库
  .shared/                     本机专用：.env、wt 钩子、运行日志
  main/                        默认分支的工作目录
  feat-<功能>/                  功能的工作目录（集成分支）
  ticket-<功能>-<编号>/          工单的工作目录
```

### 5.2 仓库内容

### 5.3 项目上下文

流程命令从当前目录向上找同时含有 `.git`（裸仓库）和 `.shared` 的目录作为项目根；当前目录在项目根下的第一层目录名就是工作目录。

### 5.4 分支和 PR 的结构

| 层级 | 分支 | 工作目录 | PR |
|---|---|---|---|
| 功能 | `feat/<功能>`，从 `main` 建 | `feat-<功能>/` | 指向 `main`，功能期间是草稿 |
| 工单 | `ticket/<功能>/<编号>`，从功能分支建 | `ticket-<功能>-<编号>/` | 指向功能分支 |

- 建目录用 `wt new`，推送和开 PR 用 `wt pr --base <目标分支>`（总是显式指定），合并后用 `wt done` 清理。
- 工单分支落后于功能分支时，用 `wt sync --merge` 把功能分支合进来，不变基、不强制推送、不改写历史。
- 工单 PR 上只跑快档检查，功能 PR 上跑全档检查。最终依据是功能 PR 上的检查。
- 推送、开 PR、合并、清理全部由流程命令执行。
- 以上结构用 wt 现有的命令能走通（S3 实测）。wt 不管的两件事由流程命令直接做：工单 PR 合并后把本机的功能目录快进到远程（`wt done` 只更新 `main` 目录）；功能 PR 转正式（用 `gh pr ready`）。
- wt 把基准和 PR 号记在 `.git/config` 里，所以 wt 只在特权侧运行。

### 5.5 资源隔离

| 资源 | 隔离方式 |
|---|---|
| 端口 | 每个工作目录建立时由流程命令从机器级登记里分配一组，删除时归还 |
| 容器 | Compose 项目名为 `<项目名>-<目录名小写>`，不写死容器名 |
| 数据卷 | 随 Compose 项目名区分。工作目录删除后，脚本算出哪些卷属于已删除的目录，列给小白并用一句话说明「这些是已删除目录的开发数据」，小白同意后删除 |
| 运行时版本 | 多版本并存，项目声明自己用哪个 |

### 5.6 受保护路径

下列内容决定把关的松紧，或会被自动执行，任何普通 AI 步骤的可改范围都不包含它们：

- `sop.json`、`.github/workflows/`。
- `AGENTS.md`、`CLAUDE.md`、`.claude/` 和 `.agents/` 下的全部内容（技能文件、AI 工具的项目设置）。
- `docs/agents/`、`docs/standards/`、`docs/baseline/`。
- 档案声明的规范配置文件，例如代码检查规则、架构依赖规则。
- 仓库之外的 `.shared/hooks/`：由工具包安装，受限侧只读。`wt new` 每次都会带着凭据执行其中的准备脚本，没有跳过的选项，所以工具包安装的准备脚本只做不运行项目代码的事（例如链接 `.env`）；安装依赖由流程命令在受限侧另做。

只有三种专门的步骤可以改它们：工具包升级、规范变更（7.11）、验收（只更新视觉基准）。

项目不使用提交钩子工具。提交前该做的检查都由门禁在受限侧完成，流程命令自己提交时关闭钩子。

## 6 信任与隔离

### 6.1 防的是什么

防的是 AI 为了「让任务通过」而走捷径：改检查、改测试、伪造记录、跳过步骤、自己推送。不防蓄意攻击。

### 6.2 两侧和一个窄接口

把这台电脑上的活动分成两侧：

| | 特权侧 | 受限侧 |
|---|---|---|
| 是什么 | 流程命令本身 | AI 进程，以及一切项目代码的运行 |
| 能做什么 | 推送、开 PR、合并、调用 wt、写事件日志、分配端口、启动受限侧 | 读写指定的工作目录、运行命令、使用专供受限侧的 Docker |
| 不能做什么 | 不运行任何 AI 写的或项目里的代码 | 读不到 GitHub 登录凭据和 SSH 密钥；写不了工具包和别的项目；碰不到用户原来的 Docker |

属于受限侧的不只是 AI，还包括：安装依赖、构建、跑测试、跑门禁、重新运行 AI 声称通过的命令、启动开发服务、启动验收环境、执行项目的准备脚本。第二轮审查指出 v0.2 只限制了 AI 进程，而这些地方照样在带着凭据运行 AI 写的代码；本版把它们全部划入受限侧。

受限环境必须满足四条要求，M6 的隔离自检逐条验证：

1. 受限侧读不到 GitHub 登录凭据、SSH 密钥。凭据不只是文件，下面四样都要挡住：`~/.ssh`；系统钥匙串的通道（GitHub 凭据可能存在钥匙串里）；SSH 代理的通道（拿到它不用读密钥文件就能推送）；环境变量里的密钥。
2. 受限侧写不了工具包目录、别的项目、机器级配置。
3. 受限侧对共用的 `.git` 只能写入提交内容和自己分支的指针；`.git` 里的其余内容对它只读，包括配置、钩子、别的分支的指针、别的工作目录的登记。工作目录里指向 `.git` 的那个小文件也只读。
4. 受限侧仍然能用 Docker 跑测试。它用的是专供受限侧的 Docker；用户原来的 Docker 不能给它（6.3）。

受限侧需要特权操作时，只能通过一个窄接口向特权侧提出请求。请求的种类是固定的少数几种（例如「为某张工单建工作目录」「我已把某张工单合入功能分支」），特权侧逐个校验、执行、记入日志。这个接口只在 7.6 的路径和个别技能需要推送临时分支时使用。

### 6.3 实现机制

由试验 S2 定下（2026-11-17，记录在 `docs/试验/S2-隔离机制.md`）。两样东西合起来用，都不需要管理员密码：

**一、每个 AI 步骤起一个 bubblewrap 受限环境。** bubblewrap 是 Ubuntu 上现成的工具，把一个程序关进一个只看得到指定目录的环境里。

- 环境变量全部清空，只放回必需的几个。
- 系统目录只读。用户主目录、`/tmp`、`/run` 都换成空的，所以主目录下的东西默认全都看不到；需要的再一样一样放进去。
- 只放进这一步要用的那个工作目录，可写。工作目录里指向 `.git` 的小文件只读。
- `.git` 整个只读，只放开四处可写：提交内容、本工作目录的登记、本功能的工单分支指针、对应的指针变更记录。
- 特权侧执行 Git 命令时总是明说仓库在哪，不依赖工作目录里那个小文件。

**二、每个项目起一个专供受限侧的 Docker。** 它是用 Docker 自带的免管理员方式另起的一个后台程序，和用户原来的 Docker 互不相干：通道、数据、镜像都另放。

- 它启动前先把自己的根目录换成一个只含白名单的目录：系统程序、它自己的数据、这个项目。所以它启动的任何容器，能挂进去的最多就是这个白名单。
- 项目里的 `.git` 和各工作目录里指向 `.git` 的小文件，在它的视野里只读。
- 受限环境里只给这个专用 Docker 的通道。

**三、AI 工具怎么放进受限环境。** S2 把四个工具都放进去跑通了。

- 每个工具只放进程序本身和最少的登录信息，都是只读。
- 各工具真实的配置目录（`~/.claude`、`~/.codex` 等）不放进去。里面有用户的设置和钩子，受限侧如果能写，就能留下一段等用户在外面使用时才执行的代码。
- 每个项目给每个工具一个专门的状态目录，留在受限环境外面，用来存会话，这样受限环境关掉再开还能续接（Claude Code 实测可以）。
- 工具自带的沙箱关掉，它们套不进去（10.2）。
- 密钥靠环境变量继承传进去，不写在命令行上。
- 用户在主目录下为各工具设的全局规则，在受限环境里看不到。M7 安装的全局规则要由流程命令只读地放进去。

为什么不能把用户原来的 Docker 给受限侧：容器是由 Docker 的后台程序启动的，而原来那个后台程序以用户的身份在受限环境外面运行。受限侧只要能对它下命令，就能让它把 `~/.ssh` 或钥匙串通道所在的目录挂进容器。S2 用一份假凭据演示了这一点。

保底方案仍是单独的系统用户：靠操作系统本身的文件权限保证第一条要求。它的代价是安装时需要管理员权限，Docker 要为这个用户另行配置，项目目录要两个用户共用。只有上面的做法在后续试验里被推翻时才启用。

还没有验证的：Codex、OpenCode、Pi 的会话续接（W24，第 0 期不做）；专用 Docker 上的 Compose、构建镜像、Testcontainers、联网拉镜像，以及受限环境里安装依赖和运行 Java、Node（这几样明确留到第 2a 期，见第 19 节）。

### 6.4 四层做法

**第一层：线上密钥不在开发电脑上。**

- `.shared/.env` 只放本机开发用的值。
- 线上密钥只存在部署平台和 GitHub 的密钥存储里，由小白通过部署档案自带的引导脚本直接填到那里。这些脚本是工具包里写好并实测过的，不由 AI 现写。
- 存在 GitHub 上的线上密钥一律放在一个「部署环境」里，并给这个环境加一条规则：只有 `main` 分支能用。仓库级不放任何密钥。S4 实测：仓库级的密钥，PR 里的代码读得到；放在限定了 `main` 的部署环境里，PR 上的任务和分支上的任务都在启动前被拒绝，只有主线上的部署流程读得到。这条规则在私有仓库的免费计划上也能设。
- 开发电脑上仍然有一样值钱的东西：GitHub 登录凭据。它由第二层保护。

**第二层：只有特权侧能推送和合并。** 即 6.2 的第一条要求。这是整个设计的承重点。

**第三层：主线只能通过检查过的 PR 改变。**

- GitHub 上的检查分两个，配合使用（S4 实测）：
  - **项目检查**：运行 PR 里的代码（门禁的各项命令）。它的定义取自 PR 自己，PR 可以把它改成永远通过，所以单靠它不算数。
  - **守门检查**：定义永远取自主线，PR 改不了它。它不取出、不运行 PR 里的代码，只查这个 PR 有没有改动受保护路径（5.6），其中就包括项目检查的定义。
  - 两个都通过才算通过。每个检查的名字在所有检查流程里唯一。
- 项目检查用到的检查脚本，按主线上 `sop.json` 声明的版本从公开的工具包仓库拉取。
- 工单 PR 的目标是功能分支，它上面的检查只是提前发现问题，不作为依据。
- 改动受保护路径的专门流程（7.11）怎么过守门检查，还没有定（W21）。
- 项目仓库公开时：开启分支保护，要求上面两个检查都通过，对管理员同样生效。没通过检查的 PR 合不进主线，也不能直接往主线推送（S4 实测，含 PR 自己改检查定义、另加同名假检查两种作弊）。
- 项目仓库私有时：免费计划没有分支保护。合并到主线这一下由小白在 GitHub 网页上亲手点。网页上会显示检查是绿是红，小白只在全绿时点。AI 没有网页登录，替代不了这一下。

**第四层：事后一定能发现。**

- 每个 AI 步骤结束后，脚本核对它的全部改动是否都在可改范围内。
- 事件日志在单独的分支上，只有特权侧能推送。
- 每个步骤开始前，特权侧现场向 GitHub 查询远程分支，核对本地历史是它的延续。
- 流程命令每次运行前核对本机工具包目录与声明的提交编号一致。

第四层依赖第二层：如果 AI 能推送，它就能改远程分支和日志。所以第二层没有退路。

### 6.5 已知的弱点

- 同一个功能的各张工单之间，挡不住互相移动分支指针。原因是它们的指针存在同一个目录里，而 Git 更新指针时要在这个目录里新建文件，只能整个目录一起放开。靠第四层事后发现。
- 同一个项目的各工作目录之间，经专用 Docker 这条路互相挡不住：专用 Docker 是整个项目共用一个，它看得到整个项目。靠第四层事后发现。
- AI 服务的密钥在受限环境里读得到，同在里面运行的项目代码也读得到。AI 工具要用它才能工作，这一点绕不开。它被拿走的后果是别人花用户的额度，不涉及代码仓库。
- 6.3 的做法试过 Git、Docker 和四个 AI 工具各一次最短的任务，还没有试安装依赖、构建和跑测试。
- 这台试验电脑上网要走代理。受限环境和专用 Docker 的环境变量都是清空的，代理要另外配进去，还没有做。
- 特权侧手里的 GitHub 凭据权限偏大（试验电脑上的那一份包含删除仓库）。M3 的登录引导应当只申请用得到的权限。
- 四个 AI 工具自带的限制手段各不相同（10.2），后三个工具还没有实测。
- 7.6 的路径要求 AI 在整个项目根下活动，受限范围比其他路径大。
- 私有仓库靠小白手动点合并：小白如果在检查是红色时也点了，没有东西拦他。小白手册会把「只在全绿时点」写成硬规矩。
- 私有仓库上，脚本同样能合并检查是红色的 PR（S4 实测）。所以流程命令合并工单 PR 之前自己查检查结果（T12），是私有仓库上唯一的防线。
- 特权侧手里的凭据能关掉分支保护、改部署环境的规则。受限侧拿不到这份凭据。
- 项目仓库公开时，代码、检查日志、日志分支上的事件（花费、步骤、确认记录）所有人都看得到；陌生人也能从自己的副本开 PR。守门检查不运行 PR 的代码，所以后者本身是安全的，但守门检查里永远不能加运行 PR 代码的步骤。

| P5 | 画产品地图 | AI 交互 | `wayfinder` | 地图和决策工单 | 地图有目的地；决策工单格式正确；只改了允许的路径 |
| P6 | 解决调研类决策工单（每张一次） | AI 自动 | `research` | 该工单的答案 | 该工单已解决 |
| P7 | 解决其余决策工单（每张一次） | AI 交互 | `wayfinder` | 该工单的答案 | 没有未解决的决策工单 |
| P8 | 产品规格 | AI 交互 | `to-spec` | `.scratch/_product/spec.md` | 规格格式检查通过 |
| P9 | 功能清单 | AI 交互，续接 P8 的会话 | 无（工具包自己的任务包） | `.scratch/_product/features/`，每个文件一个功能 | 依赖无环；每个文件有交付什么、依赖谁 |
| P10 | 确认功能清单 | 人（带路窗口协助） | 无 | 确认事件 | 事件存在 |
| P11 | 骨架 | 作为第一个功能走功能流程 | 见 7.4 | 能运行的最小系统，并已部署到预发 | 功能流程的全部检查，加门禁自检 |
| P12 | 导航外壳 | 作为第二个功能走功能流程 | 见 7.4 | 全部页面在导航里占位、可以点进去 | 功能流程的全部检查；小白确认整体结构 |
| P13 | 通用契约 | 作为第三个功能走功能流程 | 见 7.4 | 登录接法、错误格式、分页、权限模型、审计日志，以及一个把这些行为演示出来的示例页面 | 功能流程的全部检查，加契约一致性测试 |

说明：

- **功能清单不用 `to-tickets` 产出。** 技能原文要求每张工单小到一个全新会话能做完，而「功能」还要再走一遍追问、规格、拆工单，比这大。P9 是工具包自己的步骤。功能顺序由脚本从 P9 的文件得出。
- **导航外壳排在通用契约前面**，让小白尽早看到整个产品的页面结构。它只做占位，各页面的细节原型在各自的功能里做。
- **P13 的示例页面**是为了让小白验收得了：登录、没权限时的提示、出错时的提示、列表翻页，这几样在页面上看得见。其余看不见的部分由契约一致性测试把关。
- P2 中 AI 提议档案以外的技术栈时，先过偏离检查表（11.4），再走新增档案的流程。
- 部署档案需要长周期事项时（例如国内平台的备案），P3 当场提示并让它独立进行，不卡住后续步骤。第一版的参考平台在海外，不涉及备案。

### 7.4 功能流程（每个功能一轮）

| 步骤 | 名称 | 执行者 | 技能 | 产出 | 出口检查 |
|---|---|---|---|---|---|
| F1 | 开轮 | 脚本 | 无 | 功能分支和工作目录 | 目录就绪，分支已推送 |
| F2 | 追问 | AI 交互 | `grill-with-docs`，结尾用 `handoff` | 术语表和决策记录的更新、交接文件 | 小白确认已达成共识；交接文件存在；只改了允许的路径 |
| F3 | 页面原型（有新页面或改页面时） | AI 自动，全新会话 | 无 | 正式应用里的页面，数据是假的 | 页面能打开；只改了允许的路径 |
| F4 | 原型确认 | 人 | 无 | 确认事件，或一份修改意见 | 已确认。不满意时写意见，回到 F3 |
| F5 | 规格 | AI 交互，续接 F2 的会话 | `to-spec` | `spec.md` | 规格格式检查通过；只改了允许的路径 |
| F6 | 工单 | AI 交互，续接同一会话 | `to-tickets` | 工单文件 | 工单格式和关系检查通过；只改了允许的路径 |
| F7 | 规划校验 | 脚本 | 无 | 校验报告 | 每条用户故事至少被一张工单的覆盖行引用；每张工单有验收标准、覆盖行、风险行 |
| F8 | 验收包 | AI 自动 | 无 | 每张工单一份验收卡，加一份大白话摘要 | 每条验收标准至少对应验收卡一个步骤 |
| F9 | 规划复查 | AI 自动，全新会话 | 无 | 结果文件 | 没有阻断问题 |
| F10 | 确认规划 | 人（带路窗口协助） | 无 | 确认事件 | 事件存在 |
| F11 | 提交规划 | 脚本 | 无 | 推送到功能分支 | 远程与本地一致 |
| F12 | 开功能 PR | 脚本 | 无 | 指向 `main` 的草稿 PR | PR 存在 |
| F13 | 选实现方式 | 人（直接回车采纳脚本的建议） | 无 | 选择事件 | 事件存在 |
| F14 | 实现 | 见 7.5 和 7.6 | `implement` 或 `implement-spec` | 功能分支上全部工单的实现 | 每张工单都有合入事件 |
| F15 | 功能门禁 | 受限脚本 | 无 | 门禁报告 | 见第 14 节 |
| F16 | 功能复查 | AI 自动，规范和规格各一个全新会话 | 无 | 两份结果文件 | 没有阻断问题 |
| F17 | 行为验收 | 人 | 无 | 验收事件；通过时更新视觉基准并提交 | 每张验收卡都通过 |
| F18 | 功能 PR 转正式 | 脚本 | 无 | 正式 PR | PR 已转正式，说明已填入 |
| F19 | 等 GitHub 检查 | 脚本 | 无 | 检查结果 | 全档检查通过 |
| F20 | 合并到主线 | 公开仓库是脚本；私有仓库是人在网页上点合并 | 无 | 合并到 `main` | PR 已合并 |
| F21 | 清理 | 脚本（`wt done`） | 无 | 目录和分支已删 | wt 核对通过 |
| F22 | 复盘 | AI 自动 | `retro` | 复盘记录和改进建议 | 记录存在 |
| F23 | 记录指标 | 脚本 | 无 | 指标事件 | 预警已展示 |

说明：

- **F2、F5、F6 在同一个会话里**，这是技能作者的要求，靠续接会话保持上下文。
- **原型这条岔路的衔接**照技能作者的做法：F2 结束时用 `handoff` 写一份交接文件；F3 在全新会话里以它为输入做原型；F4 确认后，流程命令把「原型做成了什么样、小白说了什么」写成第二份交接文件；F5 续接 F2 的会话时带上它。
- **F3 的原型就是正式页面**：用正式组件写在正式应用里，数据由假数据层提供；实现阶段把假数据换成真实接口。脚本检查正式构建里不含假数据层。
- **追问、规格、工单三步里技能都会向小白提问**，其中有技术题（追问里的技术决策、`to-spec` 要核对的测试切入点、`to-tickets` 要问的粗细和依赖）。处理办法：
  - 技能的配置文件里要求 AI 给每个问题标上【业务】或【技术】。小白不需要自己分辨。
  - 【业务】题小白自己答。【技术】题小白统一回一句「技术题按你的推荐，并记入决策记录」。
  - F9 的复查会逐条审这些按推荐定下的技术决定是否与档案一致；也会找出被标成【技术】、实际会改变用户看得见的行为的决定，转成大白话在 F10 交给小白确认。
- **F9 审的内容**：规格是否与产品规格或原型矛盾；工单是否是大小合适的纵向切片；用词是否与术语表一致；验收卡上的预期结果是否符合规格；大白话摘要是否如实；上一条说的技术决定。验收包排在复查之前，所以复查审得到它。
- **F10 小白确认三样看得懂的东西**：大白话摘要、验收卡、已确认的原型。
- **F13 的建议由脚本算出**：含风险标记的工单建议逐张验收，其余建议整份做完统一验收。
- **F15 里的界面变化**：功能有意修改了已有页面时，截图与旧基准不同。门禁把这类差异列为「待验收的界面变化」，不算失败；F17 小白看过并通过后，基准才更新。没有对应验收卡的界面差异才算失败。
- **F17 不通过时**，小白按偏差模板写「我做了什么、期望什么、实际什么」，流程命令据此生成修复工单，回到 F14。
- **验收卡什么时候重新打开**，只有两种情况：这张工单的 PR 在验收之后又有了新提交；或者之后的门禁里，这张卡对应的自动测试或视觉基准不通过。
- **F22 的复盘**：流程命令把本功能各次 AI 会话的日志位置传给它。改进建议里属于项目规范的走规范变更流程（7.11）；属于工具包的在工具包仓库里登记。

### 7.5 工单流程（流程命令编排的路径）

| 步骤 | 名称 | 执行者 | 技能 | 产出 | 出口检查 |
|---|---|---|---|---|---|
| T1 | 开工单目录 | 脚本（`wt new`） | 无 | 工单分支和工作目录 | 目录就绪 |
| T2 | 拼任务包 | 脚本 | 无 | 任务包 | 任务包校验通过 |
| T3 | 实现 | AI 自动，全新会话 | `implement` | 提交和结果文件（含 PR 说明） | 见 T4 |
| T4 | 结果校验 | 脚本 | 无 | 校验报告 | 结果文件格式正确；声称的提交存在；工作区干净；只改了允许的路径 |
| T5 | 工单门禁 | 受限脚本 | 无 | 门禁报告 | 快档门禁通过；已有测试的改动已列出 |
| T6 | 修复（最多 3 轮） | AI 自动，全新会话 | `implement` | 修复提交、结果文件 | 回到 T4 |
| T7 | 深入诊断（T6 用完后） | AI 自动，全新会话 | `diagnosing-bugs` | 根因和修复提交 | 回到 T4；仍不通过则到 T8 |
| T8 | 技术决策（T7 不成时） | AI 自动 | 无 | 一条决策记录 | 决定是三者之一：拆工单、改规格的技术部分、建议放弃这条行为 |
| T9 | 工单复查 | AI 自动，规范和规格各一个全新会话 | 无 | 两份结果文件 | 没有阻断问题 |
| T10 | 推送并开工单 PR | 脚本（`wt pr --base`） | 无 | 指向功能分支的 PR | PR 存在 |
| T11 | 行为验收（逐张方式） | 人 | 无 | 验收事件；通过时更新视觉基准并提交 | 验收卡每项通过 |
| T12 | 等 GitHub 检查 | 脚本 | 无 | 检查结果 | 快档检查通过 |
| T13 | 合并工单 PR | 脚本 | 无 | 合入功能分支 | PR 已合并 |
| T14 | 解决冲突（T13 有冲突时） | AI 自动 | 无 | 把功能分支合入工单分支并解决冲突的提交 | 回到 T5 |
| T15 | 清理 | 脚本（`wt done`） | 无 | 目录和分支已删 | wt 核对通过 |

说明：

- 脚本算出所有不被阻塞的工单，同时为它们各走一遍本流程，并行数有上限。
- **工单复查对所有 AI 工具都由流程命令独立执行（T9）。** `implement` 结尾自己会调用 `code-review`，那一次是写代码的 AI 自己安排、自己看结果，不算独立把关。用户定了保留（技能保持原样，W15）。所以每张工单有两次审查：`implement` 自己的那一次，和流程命令的独立复查。
- **T8 之后**：决定是「拆工单」或「改规格的技术部分」时，由执行角色按决策记录修改规格和工单，然后重走 F7、F8、F9；只有大白话摘要或验收卡因此变了，才需要小白重新确认变化的部分（8.3）。决定是「建议放弃这条行为」时，用业务语言问小白：去掉，还是换个做法。
- **T11 排在 T12 前面**：验收通过会产生一次更新视觉基准的提交，排在等检查之前，检查查的就是最终内容。
- **T12 先看 PR 有没有冲突**：有冲突的 PR 上，GitHub 根本不跑项目检查（S4 实测），等不来结果。有冲突就直接去 T14。
- **T14 用合并，不用变基**：不改写历史、不需要强制推送。

### 7.6 原样运行 `implement-spec` 的路径

小白在 F13 选了这条路径，且适配器声明支持子代理时可用。

| | 流程命令编排 | 原样运行 `implement-spec` |
|---|---|---|
| 谁决定先做哪张、同时做几张 | 脚本 | AI |
| 谁建工作目录、分配端口 | 特权侧 | AI 通过窄接口请求特权侧去建 |
| 工单 PR | 每张一个 | 没有，子代理在本地合入功能分支 |
| 谁推送 | 特权侧，每个步骤后 | 特权侧，AI 每报告合入一张就推送一次 |
| 复查 | 每张一次，加 F16 | 全部完成后一次，加 F16 |
| 逐张行为验收 | 可以 | 不可以 |

技能原文与本设计不同的地方共五处，处理如下。技能文件保持原样（1.2），所以前四处不靠改技能原文，而是靠三样：窄接口；项目规则和任务包里写明的说明；受限环境本身（没有凭据，推送和开 PR 本来就做不成）。**这个做法还没有验证**：S7 是在改过原文的技能副本上走通的，那是用户定下「技能保持原样」之前做的（W25）。

| 技能原文要求 | 本设计的处理 |
|---|---|
| 子代理各自建工作目录 | 通过窄接口请求特权侧建。特权侧在项目根下调用 wt、分配端口；安装依赖等准备工作在受限侧做（5.6） |
| 探索用的子代理把笔记存到仓库之外 | 改存到项目根下的 `.shared/notes/` |
| AI 自己开草稿 PR、最后转正式 | 功能 PR 已由 F12 开好，转正式由 F18 做 |
| AI 自己清理所有工作目录 | 由特权侧在结束后清理 |
| 合并子代理在本地把工单分支合入集成分支 | 保留。这是与 wt 原规则唯一不同的地方，规则来源里写明 |

实现结束后脚本核对：用 Git 列出这个仓库的全部工作目录（不只看项目根下的），每个都必须是经窄接口建的；每张工单的分支都已合入功能分支。不符合则整轮作废重做。

试验 S7 验证了这条路径走得通（2026-11-17，记录在 `docs/试验/S7-原样运行implement-spec.md`）：三张小工单，AI 在受限环境里一次做完，经窄接口建目录、本地合并、每合入一张推送一次，没有越界，事后核对全部符合。五处差异够用，没有发现第六处。它仍是第一版里最复杂的一块，排在第 2c 期。S7 定下的做法和要注意的地方：

- 窄接口只有三种请求：建目录、报告已合入、报告全部完成。特权侧对「建目录」核对工单编号在已推送的规划里；对「报告已合入」核对目录是经它建的、工单分支已合入功能分支、功能分支是远程的延续、没有改受保护路径，都通过才推送。
- 受限环境放进整个项目根，再把 `.git`（只放开提交内容、各工作目录的登记、本功能的工单分支指针、功能分支指针）、`main` 目录、`.shared`（只放开笔记和请求两个目录）盖成只读。
- 这条路径的隔离比别的路径弱在三处，都靠核对发现：AI 能自己建工作目录和分支（事后核对能发现，S7 演练过）；运行中才建的工单目录里指向 `.git` 的小文件设不成只读，所以特权侧只在项目根下执行 wt，执行 Git 命令时总是明说仓库在哪；所有功能的功能分支指针 AI 都能移动，靠推送前核对「是远程的延续」。
- 结束后的清理由特权侧自己核对「已合入功能分支」再强制删除分支。`wt done` 要看 PR，Git 的安全删除拿主线判断，这里都用不了。
- 任务包里要告诉 AI：在 `.git` 大部分只读的环境里，提交和合并时 Git 会打印一行 `packed-refs.lock` 的只读报错，其实成功了。
- 特权侧每次启动受限环境前，先把本功能的分支指针目录建好（最后一条工单分支删掉后 Git 会把空目录一并删掉）。
- `implement-spec` 结尾也会调用 `code-review` 并派帮手修。保留，因为技能保持原样（W15）。
- 技能原文要 AI 自己清理工作目录。不改原文的话 AI 可能真的去清理，这本身无害：特权侧结束后的清理只处理还在的那些。真正要靠规则说服、靠事后核对兜底的只有一处：AI 照原文自己去建工作目录。

### 7.7 发布流程

**本节到 7.9 的开发暂缓**（用户 2026-11-17 定，见第 19 节的第 3 期）。下面的设计留作恢复时用。

第一版只支持有现成且实测过的部署档案的平台。没有档案的平台要先按新增档案的流程做出档案并实测，不由 AI 在对话里现写部署脚本。

用 `sop release` 发起。

| 步骤 | 名称 | 执行者 | 产出 | 出口检查 |
|---|---|---|---|---|
| R1 | 开通生产环境 | 人（部署档案自带的引导脚本） | 生产环境、平台上的线上密钥、告警接收方式 | 档案的连通检查通过；密钥清单在平台上齐全 |
| R2 | 部署到预发 | 脚本 | 预发环境上的待发布版本 | 健康检查通过 |
| R3 | 上线关卡 | 脚本 | 关卡报告 | 见下 |
| R4 | 预发验收 | 人 | 验收事件 | 冒烟验收卡每项通过 |
| R5 | 发布 | 人确认，脚本执行（触发主线上的部署流程） | 生产版本 | 发布完成 |
| R6 | 发布后验证 | 脚本 | 验证报告 | 冒烟通过；不通过则退回上一个程序版本 |

R3 的关卡在预发环境上实际演练：HTTPS、健康检查、备份并恢复到一个新实例、程序版本回退、告警能送达、仓库里没有密钥、依赖没有高危漏洞、压测基线、定时备份已配置。哪些项由平台自带、哪些由脚本完成，写在部署档案里。

数据库变更的规则：

- 每次发布的数据库结构变更必须向后兼容，旧版本程序在新结构上仍能运行。删除或改名分两次发布完成。
- 结构变更前先自动备份。
- 回退只回退程序版本，不回退数据。
- 脚本检查迁移文件是否含有破坏性操作。

### 7.8 紧急修复流程

线上正在出问题时用 `sop incident` 发起，不走完整的功能流程。

| 步骤 | 名称 | 执行者 | 技能 | 产出 | 出口检查 |
|---|---|---|---|---|---|
| E1 | 登记 | 人（粘贴告警或现象） | 无 | 故障事件 | 事件存在 |
| E2 | 止血 | 人确认，脚本退回上一个程序版本 | 无 | 服务恢复 | 健康检查通过 |
| E3 | 取证 | 脚本（导出线上日志并去掉敏感信息） | 无 | 日志包 | 日志包存在 |
| E4 | 诊断 | AI 自动 | `diagnosing-bugs` | 根因、一个能复现问题的测试 | 该测试在现有代码上不通过 |
| E5 | 修复 | 工单流程的 T2 到 T9，在一条从主线建的修复分支上 | `implement` | 修复提交 | 复现测试通过，全档门禁通过 |
| E6 | 验收 | 人 | 无 | 验收事件 | 只验这一个行为 |
| E7 | 合并并发布 | 功能流程的 F18 到 F20，再走发布流程 | 无 | 修复上线 | 发布后验证通过 |
| E8 | 复盘 | AI 自动 | `retro` | 能防止同类问题的新检查或新规范 | 记录存在 |

### 7.9 线上环境故障和日常运行

**不是程序错误的线上故障**（磁盘满、数据库不可用、证书过期、欠费停机、流量异常）：

1. `sop prod doctor` 运行部署档案自带的线上体检脚本，收集状态并给出结论。
2. 常见故障由部署档案自带的处置脚本处理（扩容、重启、续证书），执行前用一句话向小白说明并取得同意。
3. 处置脚本处理不了的，启动维修窗口的线上模式。它只能调用部署档案提供的脚本，不能直接在线上执行任意命令。
4. 仍处理不了的，流程命令给出平台客服渠道和应提供的信息。这是「没有专业人员」前提下的最后一步，如实写明。

选用托管平台的一个理由就是缩小这一类故障：服务器、证书、备份由平台负责。

**日常运行**，由平台的定时功能和 GitHub 的定时流程执行，失败时通知小白：

- 定时备份，每月自动做一次恢复演练。
- 依赖漏洞扫描。
- 平台费用和额度预警。
- 线上密钥的轮换提醒。

**告警怎么到小白手里**：由部署档案规定，第一版候选是平台自带的告警加邮件；能否推到手机在选定平台时核实。小白的电脑关着时，告警仍然送达；`sop incident` 在下次开机时把未处理的告警列出来。

涉及个人信息的项目，P1 命中后流程里增加一份隐私合规清单，内容待定（W11）。

### 7.10 体检流程

用 `sop health` 发起。触发提醒的条件：每完成 5 个功能，或距上次体检满 30 天，先到为准；项目长期没人操作时由 GitHub 的定时流程发提醒。

| 步骤 | 名称 | 执行者 | 技能 | 出口检查 |
|---|---|---|---|---|
| H1 | 全量检查 | 受限脚本 | 无 | 全档门禁、全量端到端测试、安全扫描、门禁自检的结果已生成 |
| H2 | 指标趋势 | 脚本 | 无 | 趋势报告已生成 |
| H3 | 架构调查 | AI 自动 | `improve-codebase-architecture` | 报告已生成 |
| H4 | 选出要处理的问题 | AI 自动（技术决策角色，按报告里影响最大的选） | 无 | 决策记录存在 |
| H5 | 处理 | 每个选中的问题作为一个功能走功能流程 | 见 7.4 | 功能流程的全部检查 |
| H6 | 依赖更新 | 作为一个功能走功能流程 | 见 7.4 | 功能流程的全部检查 |
| H7 | 备份和升级提醒 | 脚本 | 无 | 已提醒执行 `sop backup`；已检查工具包和技能副本有无新版本 |

### 7.11 规范变更和工具包升级

这两个流程是受保护路径的入口。

**规范变更**，由复盘的改进建议触发，或用 `sop standards` 发起：

| 步骤 | 名称 | 执行者 | 出口检查 |
|---|---|---|---|
| G1 | 起草变更 | AI 自动 | 只改了受保护路径里与本次变更有关的文件 |
| G2 | 判断收紧还是放宽 | 脚本按规则判断；规则判断不了的一律算放宽 | 结论已记录 |
| G3 | 复核（放宽时） | AI 自动，另一个模型 | 没有阻断问题 |
| G4 | 小白知情（放宽时） | 人 | 一句大白话说明放宽了什么、为什么；小白确认 |
| G5 | 走 PR 和检查 | 脚本 | 检查通过并合并 |

**工具包升级**，用 `sop self upgrade` 发起：安装新版本，更新 `sop.json` 的版本声明，同步技能文件和检查流程，重跑门禁自检，走 PR 和检查。升级后门禁自检不通过则退回。

### 7.12 功能的变更、放弃和中断恢复

- **做到一半想改需求**：`sop feature change`。小白用大白话写出要改什么，流程命令回到 F2 续接追问，之后重走规划各步；已合入的工单不动，变化部分生成新工单。
- **放弃一个功能**：`sop feature drop`。流程命令列出会丢掉的内容，小白确认后关闭 PR、删除工作目录和分支，记一条放弃事件。
- **自动步骤中途崩溃、断电、超时、额度用完**：日志里有「步骤开始」而没有结束事件。下次执行 `sop` 时，流程命令列出该工作目录里未提交的改动，丢弃它们，从上一次提交的状态重做这一步。额度用完或被限流时先暂停，提示稍后再执行。
- **流程停下来等小白时**：除了终端里的提示，发一条桌面通知。推到手机的方式是候选项（W13）。

## 8 流程引擎

### 8.1 步骤的声明

每个步骤声明：编号和名称、执行者、输入文件、产出文件、要运行的脚本或任务包模板、出口检查、失败后去哪、重试次数和费用上限、可改范围、是否有执行条件、会不会改动已确认过的内容。

### 8.2 事件日志

- 放在单独的分支 `sop/journal` 上，不含代码。往这条分支推送不触发 GitHub 上的检查（S4 实测；原因是这条分支上没有检查流程文件，所以它上面永远只能有事件文件），也不改变任何代码分支，所以不影响已通过的检查和已做的验收。
- 项目仓库公开时，给这条分支加保护：禁止改写历史、禁止删除，不要求走 PR。S4 实测加了之后正常写入不受影响。私有仓库的免费计划加不了保护，靠本机隔离和 6.4 第四层。
- 一个事件一个文件，文件名唯一。多张工单并行时各写各的文件，互不覆盖。
- 只有特权侧写入和推送。
- 事件种类：步骤开始、步骤完成、步骤失败、步骤跳过、人的确认、重新打开、放弃。
- 「步骤完成」带证据：出口检查的结果、相关提交的编号、花费。
- 「步骤失败」同样记录，带第几次尝试、原因、花费。修复轮数和失败花费由此得出。
- 「步骤跳过」用于有执行条件的步骤，带跳过的原因。
- 「人的确认」带被确认内容当时的提交编号。
- 当前位置由流程命令按流程定义回放事件得出。回头路（T6 回 T4、T14 回 T5、F17 回 F14）在回放里是同一步骤的又一次尝试。
- 出口检查只在步骤完成那一刻运行一次，之后不重新运行。

试验 S6 验证了以上做法，并定下几处细节（记录在 `docs/试验/S6-事件日志.md`）：

- 写入时不把日志分支检出成目录：直接造一个只多一个文件的提交，接在远程最新的提交后面再推送；不用强制推送，被别人抢先了就取回重来。4 个进程同时各写 25 个事件、两台电脑同时写，都一个不少。
- 事件的先后以提交顺序为准，不以各台电脑的时钟为准。
- 断网时写不了事件，流程停下，不在本地攒着（与 Y4 一致）。
- 回放遇到流程定义里没有的步骤编号时不猜，只记下个数。回放必须用项目声明的那个工具包版本的流程定义（W18）。
- 往真的 GitHub 写一个事件要 3 到 7 秒（S3 实测，试验电脑走代理）。一张工单约 30 个事件，就是 1.5 到 3.5 分钟只花在记账上。怎么减少见 W17。

### 8.3 什么时候需要重新确认

记录不因为文件内容变了而失效。失效只由「重新打开」事件触发，而这种事件只能由声明了「会改动已确认内容」的步骤发出。

小白确认过的东西只有三样：原型、大白话摘要、验收卡。规则是：

- 后续步骤改动了这三样之一的可见内容时，发出重新打开事件，小白只需确认变化的部分。
- 实现阶段把原型的假数据换成真接口、往工单里追加评论、修改工单状态、修改规格里的技术段落，都不需要小白重新确认；规格技术段落的修改由 F9 的复查重审。
- 没有被任何步骤声明的改动，由每步结束后的可改范围检查拦住。

### 8.4 执行规则

执行 `sop` 时，流程命令从当前位置连续执行，遇到下面任一情况停下：下一步的执行者是人或 AI 交互；某一步失败且自动处理的办法用完；达到时长或费用上限。

每次停下打印四件事：现在在哪一步、刚才自动做了什么以及各自通过与否、现在需要你做什么、做完后执行什么命令。

对话步骤没有可靠的费用上限手段（AI 工具的费用限定参数只在自动调用时有效），只记录花费并在超过预算时提醒。

### 8.5 命令

| 命令 | 做什么 |
|---|---|
| `sop` | 显示当前位置并继续执行 |
| `sop status` | 只显示当前位置和事件，不执行 |
| `sop check [步骤]` | 只运行出口检查 |
| `sop accept` | 启动验收环境并逐项记录验收结果 |
| `sop guide`、`sop repair` | 启动带路窗口、维修窗口 |
| `sop machine doctor`、`sop machine setup` | 体检、安装 |
| `sop project new`、`sop project clone` | 新建项目、克隆已有项目 |
| `sop feature new`、`sop feature change`、`sop feature drop` | 开始、变更、放弃一个功能 |
| `sop release` | 发起发布 |
| `sop incident`、`sop prod doctor` | 紧急修复、线上体检 |
| `sop health`、`sop standards` | 体检、规范变更 |
| `sop cost` | 显示各步骤的 AI 花费和一张总费用清单 |
| `sop backup` | 把整个仓库备份到另一个位置 |
| `sop self install`、`sop self upgrade`、`sop self rollback` | 安装、升级、退回工具包版本 |
| `sop profile test <档案>` | 运行档案合规测试 |

通用开关：`--dry-run` 只打印要执行的命令，`--yes` 自动确认非破坏性的提问。

## 9 任务包和结果文件

### 9.1 任务包

由脚本按模板拼出，固定八节：

| 节 | 内容 |
|---|---|
| 目标 | 这一步唯一要完成的事 |
| 技能 | 要调用的技能及其参数 |
| 必读 | 需要读的文件路径，只给路径不复制内容 |
| 可改范围 | 允许修改的路径 |
| 禁止 | 不修改已有测试来让测试通过、不碰受保护路径、不做范围以外的事 |
| 完成标准 | 必须通过的命令 |
| 交回 | 结果文件的路径和格式 |
| 不确定时 | 不猜；把问题写进结果文件，标明是业务问题还是技术问题 |

### 9.2 结果文件

AI 每个步骤结束时写一份 JSON：状态、本步的提交、运行过的验证命令及退出码、与规格或工单不一致的地方及理由、提出的问题及其类别、复查类步骤的发现及是否阻断、PR 说明（实现类步骤）。

脚本校验格式并交叉核对：声称的提交是否存在；声称通过的命令由受限脚本重新运行。

### 9.3 自动步骤里问题的去向

自动调用的 AI 有问题要问时，不会卡住等人，而是**正常结束、什么都不做、把问题当作回答交回来**（S1 后续实测：`tdd` 没有事先约定测试切入点时就是这样，工具报告的是成功）。所以流程命令不能只看退出状态：没有提交、交回的是问题，就按下面的规则处理，答案出来后续接原会话或重做这一步（续接后它接着把活干完了，Claude Code 实测）。

- **技术问题**交给技术决策角色，答案写成决策记录，流程命令重新执行原步骤。
- **业务问题**展示给小白，带路窗口解释题意和各选项的后果。答案追加到工单的评论区，重新执行原步骤。
- 类别由提问的 AI 标注。技术决策角色发现被标成技术的其实是业务问题时，转给小白。

## 10 AI 工具适配器

### 10.1 接口

能力声明：能否交互启动、能否自动调用、能否续接会话、技能调用的写法及自动调用时能否触发、是否支持子代理、自带哪些限制手段、能否限定费用、规则文件名和技能目录、会话日志位置、各技能在这个工具上能否完整运行。

四个操作：

| 操作 | 做什么 |
|---|---|
| `probe` | 自检：已安装、已登录、能力声明与实际一致 |
| `start_interactive` | 在受限环境里启动交互会话，把任务包作为开场内容 |
| `run_headless` | 在受限环境里自动执行任务包，返回退出状态、花费、会话日志位置 |
| `resume` | 续接会话并送入补充说明 |

退路：

- 工具不支持自动调用时，流程命令在受限环境里启动一个交互窗口并显示任务包，小白把它粘贴进去；AI 写出结果文件后小白执行 `sop` 继续。
- 技能命令在自动调用下无法触发时，任务包改为「读取该技能的文件并照做」。
- 工具不支持子代理时：需要子代理的复查由流程命令分成多个全新会话完成；其他需要子代理的技能（追问里查事实、调研、产品地图）在适配器的能力声明里标明能否运行，不能运行的由流程命令改用单会话的任务包替代。

| 费用限定 | `--max-budget-usd`（只在自动调用时有效） | 帮助里没有 | 帮助里没有 | 帮助里没有 |

核对和后续试验中发现、会影响设计的九件事：

1. **工具自带的「是否已登录」查询不能当依据。** 本机的 Codex 接的是配置文件里写的一个自定义服务，不是它官方的账号，所以它自己的查询命令报告「未登录」；OpenCode 的查询列不出任何已登录的账号；Pi 的查询会把环境变量里的密钥也算作「已就绪」。所以适配器的 `probe` 要判断「已登录」，只能真的发一次最短的调用。
2. **AI 工具的密钥会通过环境变量传下去。** 从一个 Claude Code 会话里启动别的程序时，这个会话的 Anthropic 密钥在环境变量里，子进程读得到，Pi 会直接拿它当自己的密钥用。6.2 的第一条要求目前只写了 GitHub 登录凭据和 SSH 密钥这两样文件；受限侧启动时还要清理环境变量，这一点并入试验 S2。
3. **两个技能目录够四个工具用。** `.claude/skills` 加 `.agents/skills`，与 5.2 一致。S5 实测：整个目录复制过去后四个工具都认得；OpenCode 两处都认，但同一个技能只列一次。升级技能时两处要一起换。
4. **Codex 不认技能文件里「只允许人触发」的标记，它认的是技能目录里另一个文件 `agents/openai.yaml`。** mattpocock/skills 的每个技能目录里已经自带这个文件，标着只允许人触发的技能在里面也写了禁止自动触发（S0 准备时核对过原文）。所以复制技能时要把整个技能目录一起复制，不能只复制 `SKILL.md`；不需要另打补丁。S5 实测：整目录复制后，只允许人触发的技能在 Codex 的清单里都不出现。
5. **后三个工具都没有费用限定参数。** 8.4 里靠这个参数卡费用上限的做法只在 Claude Code 上成立，其余三个只能记录花费、事后提醒。Codex 运行结束时报告用了多少词元，不报告金额；OpenCode 和 Pi 在默认输出里不报告。
6. **工具自带的沙箱套不进受限环境。** 在 6.3 的受限环境里，工具自带的沙箱启动不了（Codex 实测）。所以四个工具在受限环境里都以「不逐条询问、不用自带沙箱」的方式运行，隔离完全由 6.3 负责。表里「自带的限制手段」一行只在受限环境之外才用得上。
7. **这台试验电脑接的服务不接受带自定义系统提示词的调用，小一档的模型也用不了**（S0 里遇到，原因没有追查）。普通调用正常。所以 10.3 说的「不同角色配不同模型」在具体的电脑上受它接的服务限制；任务包要作为普通的提问内容传进去，不能依赖自定义系统提示词。

8. **任务包里要用到哪个技能，必须写明名字。** 在 Claude Code 上，项目里的技能不出现在它给 AI 的清单里，AI 不会看描述自己去选用（S5 实测）；点名调用和按名字加载都可以。技能和 Claude Code 自带的技能重名时（`code-review`），用的是项目里的那一份。
9. **启动 Pi 时要把键盘输入关掉**，否则它会一直等输入（S5 里卡了 5 分钟）。

主链上的技能在原文里都标着只能由人输入命令触发。它们在自动调用下能否触发：Claude Code 已由试验 S1 确认可以；其余三个工具由 S5 用试验用的暗号技能、S1 后续部分用真实的 `grill-me` 确认可以。所以 10.1 里「读取该技能的文件并照做」的退路，四个工具目前都用不着，留作保底。

### 10.3 角色配置

项目可以为每种角色指定不同的工具和模型。复查建议用与执行不同厂商的模型，默认是同一工具的全新会话（W9）。

## 11 技术栈档案

### 11.1 档案是什么

一份档案是一套技术栈的全部预置技术决定，让 AI 在追问环节少问技术题，也让门禁和命令在不同技术栈之间保持同一个接口。后端档案和端档案相互独立，只通过 `contracts/openapi.yaml` 连接。

### 11.2 档案接口

| 文件 | 内容 |
|---|---|
| `profile.toml` | 名称、类型、适用场景、支持的数据库、每项依赖的支持期限和核对出处 |
| `toolchain.toml` | 需要的运行时和工具 |
| `scaffold/` | 脚手架 |
| `commands.toml` | 统一命令表 |
| `gates.toml` | 快档和全档门禁的组成、阈值、受保护的规范配置文件 |
| `decisions/` | 预置的决策记录：分层、数据访问、数据库迁移、登录接法、日志、错误格式、测试切入点 |
| `standards.md` | 编码规范 |
| `brief-skeleton.md` | 骨架阶段的说明 |
| `seed/` | 验收数据的装载方式 |
| `seeds-defect/` | 门禁自检用的缺陷样本 |
| `redline/` | 红线扫描规则：哪个模块可以使用密码、令牌、加密相关的库 |
| `pitfalls.md` | 已知的坑和处理办法 |

### 11.3 统一命令表

`setup`、`dev`、`build`、`typecheck`、`lint`、`format`、`test-unit`、`test-integration`、`test-e2e`、`test-mutation`、`migrate`、`seed`、`codegen`、`gate-fast`、`gate-full`。所有任务包和流程定义只用这些命令名，具体命令由档案填写，全部在受限侧运行。

### 11.4 新增档案

步骤：复制档案模板，填写各文件，每项选型附官方支持期限的出处，由另一个模型独立复查选型，执行 `sop profile test <档案>`。合规测试用这份档案新建一个样例项目，走通骨架的最小链路并运行门禁自检。

如实说明：新增一份档案是一件按天计的工作。接口保证的是新档案接入后流程、命令、门禁与已有档案一致，且不需要修改内核；它不保证省事。选型的好坏由 AI 判断加另一个模型复查，没有专业人员把关。

AI 提议档案以外的技术栈时，逐项过偏离检查表：是否主流；是否在长期支持期内；是否有成熟的类型检查、代码检查、测试、变异测试工具；是否有成熟的数据库迁移工具和登录模块；能否按 OpenAPI 契约做一致性校验；各依赖版本是否兼容及核对出处。

### 11.5 第一版的档案（候选选型）

下面都是候选，还没有核对当前版本和支持期限。

| 档案 | 候选选型 |
|---|---|
| `backend-java-spring` | Java 长期支持版、Spring Boot、Maven；PostgreSQL（用户 2026-11-17 定；原来的候选是 MySQL，因为找不到全托管 MySQL 的平台而改）；Flyway；数据访问在 MyBatis-Plus 和 Spring Data JPA 之间二选一；Spring Security；JUnit 和 Testcontainers；ArchUnit；PIT |
| `backend-ts` | Node 长期支持版、TypeScript、NestJS；PostgreSQL；Prisma；Vitest；dependency-cruiser；Stryker；ESLint |
| `web-admin-vue` | Vue 3、TypeScript、Vite、pnpm；Pinia、Vue Router；Element Plus；按契约生成接口类型；MSW 提供假数据；Playwright；Stylelint |
| 参考部署档案 | 一个海外托管平台。候选：Railway、Render、Fly.io。试验 S8 做了纸面比较（只读官方文档，没有注册和实测，记录在 `docs/试验/S8-部署平台选型.md`），还没有选定，见下 |

- 数据库不与后端绑死：每份后端档案声明自己支持哪些数据库，第一版每份只实测一个。
- S8 的纸面结论：
  - 没有一家同时提供全托管的 MySQL 和 PostgreSQL。Render 和 Fly.io 只有全托管的 PostgreSQL，MySQL 要自己跑；Railway 两样都有，但备份和高可用要用户自己打开，告警自己配。
  - 如果 Java 那套后端第一版改用 PostgreSQL，纸面首选 Render：备份由平台默认做并能恢复成新实例，服务不健康会自己重启，自带邮件告警，费用固定（两套环境每月约 27 到 63 美元，估算），官方写明收借记卡。
  - 如果 MySQL 一定要托管，只能选 Railway，并接受上面说的半托管，以及只收信用卡。
  - 用户手里的卡能不能用，三家的官方文档都没写，要注册后实测。
  - 用户 2026-11-17 定了 Java 那套改用 PostgreSQL，所以纸面首选是 Render。还没有注册和实测；部署相关的开发暂缓，实测随它一起往后放（W23）。
- Web 管理后台的前端只做 Vue 这一份，同时配合两套后端。之前讨论里提过「TypeScript 全栈」，如果用户希望 TypeScript 后端配另一种前端，需要再加一份端档案（W14）。
- 接口契约采用契约优先。

## 12 端档案

端档案在 11.2 的基础上增加：

| 内容 | 含义 |
|---|---|
| 假数据层 | 原型阶段页面的数据来源，以及检查正式构建不含它的方法 |
| 设计令牌 | 颜色、字号、间距的唯一定义处，以及禁止写死这些值的检查规则 |

| 发布步骤 | 这个端特有的发布和审核流程 |
| 自动化覆盖说明 | 每一项能自动测试还是只能人工验收 |

档案可以把某一项声明为「人工」，流程命令遇到这种声明时，把对应的检查换成验收卡上的人工项。

### 12.1 接口的通用性

接口目前只有 Web 管理后台一个真实样本，另在纸面上推演过微信小程序：

| 接口项 | Web 管理后台 | 微信小程序 |
|---|---|---|
| 假数据层 | MSW | 请求层的假数据开关 |
| 端到端测试 | Playwright | 自动化依赖开发者工具，Ubuntu 上没有官方版本，只能少量覆盖 |
| 视觉基准 | 容器里截图 | 做不到，声明为人工 |
| 验收预览 | 本机网址 | 命令行上传体验版，手机扫码 |
| 发布步骤 | 随后端部署 | 提交审核、发布 |

App 没有推演过。接口是否通用，要等第一版之后做出第二种端才能确认。

### 12.2 第一版之后的端

| 端 | Ubuntu 上的限制和做法 |
|---|---|

## 13 验收环境

`sop accept` 负责把环境准备到小白可以直接点。整套环境在受限侧启动。

1. **启动**。从要验收的那个工作目录启动整套系统，用它自己的端口和容器名。数据库是这次验收专用的全新实例，不使用命名卷。
2. **装数据**。执行数据库迁移，再装入验收数据。验收数据由实现它的那张工单一并交付。
3. **建账号**。按验收卡里写的角色建好测试账号。
4. **引导**。打印网址和各角色的账号，逐项显示验收卡：前置条件、操作、预期结果，以及异常操作（输错、无权限、重复提交、刷新、断网）。小白每项回答通过或不通过，不通过时写一句现象。
5. **记录**。验收结果记成事件。全部通过时，在固定的容器镜像里为涉及的页面截图，更新视觉基准并提交。
6. **复原**。停止并删除这次验收的容器，不留数据。

## 14 检查库

### 14.1 统一约定

- 每个检查一个文件，只判断一件事；只读，不修改项目。
- 退出码：0 通过，1 不通过，2 无法判断。
- 标准输出一行结论，详细报告写成 JSON。
- 每个检查必须附至少一个「应通过」和一个「应报错」的样例。
- 每个检查标明在哪里运行。

### 14.2 检查清单

「在哪运行」一列：**本机**表示只在本机，因为它依赖本机的步骤信息；**两处**表示本机受限侧和 GitHub 都运行。

| 类别 | 检查 | 在哪运行 | 能保证什么 | 保证不了什么 |
|---|---|---|---|---|
| 环境 | 工具清单、适配器自检、连通性、隔离自检 | 本机 | 工具齐全、能用、6.2 的四条要求成立 | 6.5 列出的两处挡不住的地方 |
| 项目 | 目录结构、技能文件与工具包一致 | 两处 | 结构和版本正确 | 无 |
| 项目 | 仓库里没有密钥 | 两处 | 没有常见格式的密钥 | 扫描认不出的格式 |
| 项目 | 可改范围 | 本机 | 一个步骤的改动都在允许的路径内 | 路径内改得对不对 |
| 项目 | 受保护路径 | 两处 | PR 没有改受保护路径，除非是专门的流程 | 无 |
| 项目 | 历史延续 | 本机 | 本地历史是现场查到的远程分支的延续 | 无 |
| 规划 | 规格格式、工单格式和关系 | 本机 | 各节齐全、阻塞无环 | 内容好不好 |
| 规划 | 故事覆盖 | 本机 | 每条用户故事被某张工单的覆盖行引用 | 工单是否真的实现了它 |
| 规划 | 验收卡格式 | 本机 | 每条验收标准有对应步骤 | 步骤是否充分、预期是否正确（由 F9 审） |
| 实现 | 结果文件 | 本机 | 格式正确、声称的提交存在 | 无 |
| 实现 | 已有测试的改动 | 两处 | 列出所有被修改、删除、跳过的已有测试 | 改动是否正当（由复查审） |
| 实现 | 验收标准有测试 | 两处 | 每条验收标准有带标记的测试 | 测试是否真在测这件事 |
| 实现 | 变异测试 | 本机，功能 PR 上再跑一次 | 对本次改动的代码故意改错，要求测试能发现 | 只覆盖变异工具能生成的错误 |
| 实现 | 快档、全档门禁 | 两处 | 档案定义的命令全部通过 | 无 |
| 实现 | 重复运行 | 本机 | 全档门禁连续多次通过 | 极低概率的偶发失败 |
| 实现 | 契约 | 两处 | 契约文件合法、后端与契约一致、前端生成代码是最新的 | 契约设计得好不好 |
| 实现 | 界面 | 两处 | 没有写死设计令牌的值；截图与基准的差异在允许范围内或已列为待验收；正式构建不含假数据层 | 好不好看 |
| 实现 | 架构规则 | 两处 | 模块依赖方向符合规定，没有循环依赖 | 模块划分是否合理 |
| 实现 | 红线扫描 | 两处 | 只有档案指定的模块使用了密码、令牌、加密相关的库 | 不经这些库的手写实现 |
| 实现 | 迁移安全 | 两处 | 迁移文件不含破坏性操作 | 数据含义上的问题 |
| 实现 | 依赖安全 | 两处 | 没有已知高危漏洞 | 未公开的漏洞 |
| 实现 | 改动质量 | 两处 | 本次改动的代码覆盖率达标、单个函数复杂度不超限、没有新增重复 | 整体设计 |
| 合并 | GitHub 检查和 PR 状态 | 本机 | 检查通过、状态正确 | 无 |
| 发布 | 上线关卡 | 预发环境 | 7.7 的 R3 各项实际演练通过 | 线上独有的问题 |
| 趋势 | 指标记录和预警 | 本机 | 记录每次的数字，连续恶化时预警 | 无 |

GitHub 的免费时长有限。为此：工单 PR 只跑快档；全档只在「目标是 `main` 且已转正式」的 PR 上跑（这个条件写在检查定义里，S4 实测有效，被跳过的任务不计时长）；耗时的变异测试和重复运行主要在本机受限侧跑；事件日志的推送不触发检查。项目仓库公开时不计时长。

S4 量出的是次数：一个功能有 N 张工单、每张平均推送 p 次时，工单 PR 上跑 N × p × 2 个任务，功能 PR 草稿期间跑 (N + 1) × 2 个（每合入一张工单就重跑一遍），转正式时 2 个（其中 1 个是全档），合入主线后部署 1 个。10 张工单约 55 个任务。每个任务跑几分钟要等有了技术栈档案才知道（第 2a 期）。私有仓库的免费额度按官方文档折算约每月 2000 分钟（没有逐字核对原文）。草稿期间的功能 PR 要不要连快档也跳过，见 W22。

### 14.3 留给 AI 和人的部分

由 AI 审查：规格与产品规格、原型是否矛盾；工单是否是大小合适的纵向切片；用词是否与术语表一致；验收卡的预期是否符合规格；实现是否符合规格的含义；已有测试的改动是否正当；设计味道；合并冲突的解决；故障根因。

只能由人做：业务决策、原型确认、行为验收、账号和密钥、发布确认、私有仓库的合并点击。

### 14.4 门禁自检

每份档案带一组缺陷样本，例如破坏一个类型、违反一条架构规则、写死一个颜色、删掉一个断言、在别的模块里使用加密库。门禁自检在临时副本里逐个应用，要求门禁每次都不通过。在骨架阶段、每次体检、每次工具包升级时运行。

## 15 防偏差机制

| 偏差 | 防线 |
|---|---|
| 会话过长导致质量下降 | 每张工单一个全新会话；状态在仓库 |
| 各会话做法不一致 | 档案的规范和架构规则、设计令牌、术语表 |
| 偏离需求或多做 | 故事覆盖、复查的规格轴、行为验收、已确认的原型 |
| 新功能弄坏旧功能 | 全量回归；验收过的行为都有自动测试；视觉基准 |
| AI 削弱把关 | 第 6 节；已有测试的改动一律列出并复查；变异测试；受保护路径 |
| 文档与代码脱节 | 契约一致性；术语表和决策记录的更新是步骤的产出 |
| 代码越来越乱 | 改动质量检查；体检流程里的架构调查 |
| 版本变动 | 锁文件、技能副本、工具清单、项目声明的工具包提交编号 |
| 门禁自身失效 | 门禁自检；检查的样例 |
| 悄悄累积的问题 | 趋势预警、体检流程 |

趋势预警记录：每张工单的自动修复轮数、验收返工次数、门禁耗时、改动覆盖率、变异测试得分、AI 花费。

## 16 工具包自身如何被验证

工具包由 AI 写、AI 测，没有专业人员最终把关。做法如下，残余风险见 1.4。

### 16.1 每个检查必须证明自己会报错

- 每个检查附「应通过」和「应报错」的样例。
- 一个总检查逐个运行所有样例：没有「应报错」样例的检查不合格；在「应报错」样例上没有报错的检查不合格。
- 样例和检查出自同一个 AI，所以每一期的独立审查要逐行看总检查，并抽查样例是否真的代表该报错的情况。

### 16.2 其他自测

| 层次 | 验证什么 |
|---|---|
| 内核单元测试 | 事件的回放（含回头路、条件步骤、重新打开）、任务包拼装、结果校验 |
| 流程沙箱 | 用「假 AI」适配器按剧本产出文件，离线跑通各流程 |
| 隔离自检 | 在受限侧尝试读凭据、写工具包、改 `.git` 配置，以及借 Docker 做同样的事，要求全部失败 |
| 档案合规测试 | 每份档案能建出样例项目并通过门禁自检 |
| 真实 AI 演练 | 每个适配器在真实工具上跑通交互、自动调用、技能触发、结果文件 |
| 文档检查 | 文档引用的命令、步骤编号、文件路径都存在 |

### 16.3 每一期结束时的两道外部把关

- **独立审查**。用一个全新的窗口、尽量换一个模型，按工具包里固定的审查说明审查本期的产出。由用户自己开窗口做最独立。
- **破坏演练**。由脚本逐项执行破坏动作（例如把一个测试的预期结果改掉并提交），小白只看结果：屏幕上应当显示检查失败。这是小白对工具包本身的行为验收。

### 16.4 版本

工具包按提交编号安装和声明。`docs/依据.md` 记录每条外部事实的出处和核对日期。工具包自身的开发不走它自己的功能流程，因为第一版的档案（Java、TypeScript、Vue）都不适用于一个 Python 加 shell 的命令行工具。

## 17 维修和操作安全

### 17.1 维修窗口

- 用 `sop repair` 启动，适用于本机的机器、工具、网络、Docker、工具包自身出故障。线上故障见 7.9。
- 启动时流程命令把体检报告和最近的运行日志交给它。
- 它要执行的命令由脚本按一张清单分成两类：
  - **可以撤销的**（重启服务、重装工具包管理的工具、重建开发环境文件）：直接执行，记入日志。
  - **不能撤销的**（删除数据、改系统配置、需要管理员权限的）：先由另一个模型复核，再用一句大白话向小白说明后果，小白同意后执行；需要管理员密码时由小白自己输入。
- 它不能改项目代码、事件日志和受保护路径。
- 判断是工具包自身的错误时：用 `sop self rollback` 退回上一个版本，并在工具包仓库里登记问题。

维修窗口解决不了红线内的问题。

### 17.2 操作安全

- 查看别人的 PR 时不自动执行其中的任何脚本。
- 删除命名数据卷、删除未合并的工作目录，一律先问小白。流程里没有强制推送。
- Docker 按 rootless 使用：不用 sudo，不用宿主机网络，端口映射到 1024 以上，持久数据放命名卷。
- 访问 GitHub 或拉取镜像失败时不反复重试，停下、显示原始报错，并提示检查网络设置或启动维修窗口。

### 第 1 期：内核和机器层

内容：引导脚本、机器层、受限运行器、内核、事件日志、检查库的通用部分和总检查、「假 AI」适配器、Claude Code 适配器、wt 接入。

验收标准：

- 在全新虚拟机上从第零步走到 `sop machine doctor` 全部通过。
- 隔离自检通过。
- `sop project new` 建出第 5 节的结构；在另一台虚拟机上 `sop project clone` 得到相同的位置，并重建进行中的工作目录。
- 流程沙箱用「假 AI」把功能流程和工单流程离线跑通，包含失败、修复、深入诊断、技术决策、重新确认、中断恢复。

- 总检查通过。
- Claude Code 适配器的交互启动、自动调用、续接、技能触发、结果文件实测通过。

### 第 2a 期：最小主链

内容：`backend-java-spring` 和 `web-admin-vue` 两份档案、产品流程、功能流程、工单流程（一次只做一张、逐张验收）、验收环境。

验收标准：

- 两份档案通过合规测试和门禁自检，选型经另一个模型复查。
- 用一个小型管理后台样例做完骨架这一个功能，在本机的验收环境里能运行。（原来还要求部署到预发；部署相关的开发暂缓，这一条去掉，见第 3 期。）
- 用户本人按小白手册从头操作一遍，记录卡住的地方并修正。这是用户第一次真正上手。
- 给出这个功能的实际 AI 花费和 GitHub 时长消耗。

从第 0 期留下来、明确放到本期补验证的事（第 0 期的九项试验都不管它们，本期开工时先做）：

- 专供受限侧的 Docker 上跑 Compose、构建镜像、Testcontainers，以及走代理联网拉镜像（S2 没试）。
- 受限环境里安装依赖、运行 Java 和 Node（S2、S0 只试了 Git、Docker 和 Python 标准库）。受限环境的环境变量是清空的，代理要另外配进去。
- 让 AI 在受限环境里亲自用一次专用 Docker（S2 两样是分别试的）。
- 让 AI 来解决合并冲突（T14）。S3 里冲突是手工解决的。
- 多张工单同时建工作目录时 `wt new` 之间会不会互相干扰。S3 里是先后建的；S7 里是由窄接口一个一个排着建的。

### 第 2b 期：完整的开发流程

内容：导航外壳和通用契约、页面原型的完整流程、多张工单并行、整份统一验收、带路窗口、技术决策角色、规范变更、功能的变更和放弃。

### 第 2c 期：原样运行 `implement-spec`

内容：窄接口、项目规则和任务包里对应 7.6 的说明、事后核对。开工前先做 W25 的验证。

验收标准：样例的一个功能用这条路径做完；人为让 AI 绕过窄接口建一个目录，事后核对能发现。

### 第 3 期：上线和运维

**本期里和部署有关的部分暂缓**（用户 2026-11-17 定：暂时不做部署等相关流程的开发）。什么时候恢复由用户定。暂缓期间：

- 不做的：参考部署档案、发布流程（7.7）、紧急修复流程（7.8）、线上体检和处置脚本以及日常运行（7.9）；项目初始化里的部署流程和部署环境（7.2 的 I6 里那一部分）；选定平台后的注册和实测（W23）。这几节的设计留在文中不删，恢复时接着用。

内容：参考部署档案（全部）、发布流程、紧急修复流程、线上体检和处置脚本、体检流程、维修窗口。

验收标准：样例发布到生产环境；R3 的各项在预发上实际演练通过；人为制造一次程序故障走通紧急修复；人为制造一次线上环境故障走通线上体检；人为弄坏一次本机环境走通维修窗口。

### 第 4 期：第二套后端

内容：`backend-ts` 档案。

验收标准：不修改内核和流程定义就能接入，通过合规测试，并跑通同一个样例。

### 第 5 期：其余三个 AI 工具

内容：Codex、OpenCode、Pi 三个适配器的完整适配。第 0 期已经做过它们的基本试验，接口在第 1 期就按四个工具的情况来定。

验收标准：每个适配器实测；能自动调用的走自动路径，不能的走粘贴路径；隔离在每个工具上的实现情况写入依据文件；不支持子代理的工具按 10.1 的退路运行。

其他端档案；国内部署平台的档案（含备案）；接入已有的旧项目。

**技能文件保持原样，不打补丁**（用户 2026-11-17 定：技能会更新，更新会把改动盖掉）。技能副本只是固定在某个版本的原样拷贝，升级就是整个目录换成新版本，没有东西要重新核对。

本工具包自己的约定只能写在技能之外，共四处：

- 技能的配置文件 `docs/agents/`。它是技能自己的安装步骤本来就要为每个项目生成的文件，属于项目，不属于技能。
- 项目规则 `AGENTS.md`。
- 每一步的任务包。
- 受限环境和流程命令：让不该做的事做不成，或者在步骤结束后由脚本补做。

技能原文和本设计对不上的地方，各自怎么办：

| 对不上的地方 | 不改技能的办法 | 验证过吗 |
|---|---|---|
| 提问要标【业务】【技术】 | 写在项目规则里 | S0 实测有效 |
| 技术题不要问小白 | 在项目规则里预置技术决定 | S0 实测有效 |
| 工单要有覆盖行和风险行 | 写在项目规则或工单格式的配置文件里 | 没有 |
| `handoff` 把交接文件存到系统的临时目录，而设计要它在仓库里 | 受限环境给它一个专用的临时目录；步骤结束后由脚本把文件搬到 `.scratch/<功能>/` 下并提交 | 专用临时目录 S0 用过，文件确实写在里面；搬运没有试 |
| 技能里 AI 自己推送临时分支 | 受限环境里没有凭据，推不了；项目规则写明改为经窄接口请求 | 没有 |
| `implement` 结尾自己调用 `code-review` | 保留（W15） | S0、S7 里一直在跑 |
| 7.6 列出的五处 | 见 7.6 | 没有（W25） |

S0 的观察（记录在 `docs/试验/S0-主链试走.md`）：

- 把「每个问题标【业务】或【技术】」写在项目规则里，AI 全部照办了，27 个问题没有漏标。
- 在项目规则里预置技术决定之后，追问阶段一道技术题都没有问。
- `handoff` 原文要求把交接文件存到系统的临时目录、不要存在项目里。这和 4.7、7.4 假定的「交接文件在仓库里」相反。技能不改，改由脚本在步骤结束后把文件搬进 `.scratch/<功能>/`（见上表）。
- `implement` 做完工单后不会去改工单文件里的状态行。哪些工单做完了只看事件日志。（`implement-spec` 的原文要求改状态行，S7 里它照做了。）
- 规则里要写明「向用户汇报也用中文大白话」。S0 里只规定了界面、文档、提交说明用中文，结果做到后面几张工单时汇报变成了英文。
- 复制技能时要整个目录一起复制，目录里有给 Codex 用的文件和技能引用的附带文件。

S1 后续部分的观察（记录在 `docs/试验/S1-自动调用下的技能.md`）：

- `code-review` 不给比较起点时不会问，自己选一个（实测选了 `main`）。流程命令调用它时必须写明起点：工单复查的起点是功能分支，功能复查的起点是 `main`。
- `tdd` 的测试切入点要在规格阶段定好并写进决策记录或档案。没定的话它什么都不做、以问题结束。
- `research` 的帮手在主会话结束前跑完，笔记写在项目里但不提交，流程命令要自己提交（P6）。
- `code-review` 的报告是英文的，尽管项目规则要求用中文。凡是要给小白看的产出，任务包里要再强调一次用中文大白话。
