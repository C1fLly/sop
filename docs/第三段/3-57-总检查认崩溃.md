# 3-57 总检查：检查脚本一导入就崩时会被当成「报对了」

2026-11-20 做完（主控窗口派的子代理做的）。没有调用 AI，0 美元。没动隔离，没碰 GitHub、Docker、虚拟机。

## 发现

- 总检查原来只看退出码：「应报错」样例退出码是 1 就算符合。Python 碰上没被兜住的错，退出码也是 1，所以检查脚本在 `import` 那一步崩、或者在 `lib.cli` 的兜底之外崩（例如打印完结论、写 JSON 报告时崩），都会冒充「报出了问题」（16.1「检查自己崩了不能冒充发现了问题」）。
- 只是导入就崩的话，「应通过」的样例也一样崩、退出码 1，总检查整体还是不合格，问题会被发现，只是那条「应报错」样例的结论是假的。**真正会漏过去的是另一种**：只在「报错」那条路上崩，比如报告里放了一样 JSON 写不出的东西（集合），结论打印完、写报告时崩。改之前总检查整体是「全部符合」，退出码 0。

改之前在 `/tmp` 里造了两个坏检查跑总检查（`SOP_CHECKS_DIR` 指过去），原样结果：

```
符合   dumpcrash/fail-b：退出码 1（应为 1） 按样例名判        ← 其实是写报告时崩了
符合   dumpcrash/pass-a：退出码 0（应为 0） 按样例名判
符合   importcrash/fail-b：退出码 1（应为 1） Traceback ... ModuleNotFoundError   ← 导入就崩，算成报对了
不符合 importcrash/pass-a：退出码 1（应为 0） Traceback ...
```

## 做了什么（从根上：只认检查自己写出的结论）

- `checks/lib.py` 的 `finish`（所有检查都经 `lib.cli` 走它收尾）在 JSON 报告里写上这次的「退出码」和「结论」两项；先整个转成文字再写文件，转不了就在写文件之前崩，不会留下半截报告。报告原有的内容不变（只多两项；内核是直接调各检查的 `run()`，不读这份报告，不受影响）。
- `checks/total_check.py` 每个样例跑之前先删掉临时副本里的 `report.json`（样例自带的、造现场时写的都不算），跑完要求报告读得出、是对象、里面记的退出码和进程的退出码一样；不然判「检查自己崩了（进程退出码 N，没写出报告／报告读不出或没记退出码／报告里记的退出码是 M）」，并显示错误输出的最后一段。「应通过」「应报错」的样例都这样要求。
- 没有改每个 `check.py`（任务清单里提的「把导入挪进兜底里」要改 13 个文件，而且挪不了 `from checks import lib` 本身；看报告里的结论一处就够，也兜住了导入以外的崩法）。
- `checks/README.md` 加了一条说明这个约定。

## 测试怎么做的、结果

- 单元测试 `tests/unit/test_total_check.py` 加 3 项（264 → 267）：导入就崩的检查，「应报错」样例判不符合、说「检查自己崩了」；只在报错那条路上写报告时崩的检查，总检查整体不合格（「应通过」那个照旧符合）；样例里自带一份写着「退出码 1」的假报告、或者检查写完结论又改用别的退出码退出，都判不符合。
- 反着试：把 `checks/lib.py`、`checks/total_check.py` 暂时退回改之前（`git stash`），新加的 3 项都失败；改回来 6 项全过。
- 改之后再跑上面 `/tmp` 里那两个坏检查：4 个样例里 3 个不符合（两个崩了的「应报错」、导入就崩的「应通过」），只有 `dumpcrash/pass-a` 符合，和该有的一样。
- 真的总检查：89 个样例照旧全部符合。**没有原来靠崩溃蒙过去的样例**：每个样例都写出了自己的结论、退出码对得上。

自测：做之前（主控窗口跑的）单元测试 264 项、流程沙箱 24 个剧本、总检查 89 个样例，全部通过。做完（代码全部改好之后跑的一遍）：单元测试 267 项、流程沙箱 24 个、总检查 89 个样例，全部通过。

## 没做的

- 检查脚本被别处当成独立程序运行、靠退出码判断时（以后在 GitHub 上跑的项目检查、守门检查），同样的问题也在：导入就崩退出码是 1，会被当成「不通过」而不是「无法判断」。那边不通过也不会放行，所以不会冒充「通过」，但原因会说错。现在还没有这样的调用方（内核是直接调 `run()`），等接 GitHub 上的检查时（3-24 之后、3-41 那一批）按同一个办法看报告里的「退出码」就行，没有单独拆任务，写在这里。
