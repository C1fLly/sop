# 第一段：专用 Docker 的五样（含 W33、W8 的一部分）

状态：已完成（2026-11-18）。五样都在虚拟机 vm-a 里试了：数据放硬盘、重启后自己起来、两个项目各起一个并量出占用、容器里面联网、给容器限资源。前三样照设计成立；后两样和设计书写的不一样，要改设计书。

没有调用 AI，没有花钱。都在虚拟机里，没有碰这台电脑上的 Docker。脚本在 `docs/试验/脚本/第一段/专用Docker/`。

## 怎么做的

- vm-a 上已有规定位置的免管理员 Docker（`~/tools/docker`，W27 迁移之后）。
- 每个项目的专用 Docker 照 S9 的做法起：启动前用 `dockerd-wrap.py` 把它的根目录换成只含白名单的目录（S9 那一份改成按项目带参数）。不同的是：这次做成**用户级后台服务**（`sop-docker-<项目名>.service`，设成跟着用户的服务一起起来），数据放在硬盘上的 `~/tools/docker-sop/<项目名>/`。两个项目：demo1、demo2。
- 为了还原这台电脑上的情形（代理只在本机内部 `127.0.0.1:7890` 开着），在虚拟机里也起了一个只在本机内部开着的代理转发，专用 Docker 的后台程序用它。

## 结果

### 一、数据放在硬盘上；二、重启后自己起来

- 数据目录在 `~/tools/docker-sop/demo1/`、`demo2/`，在主目录那块盘上。
- 重启虚拟机，登录之后两个专用 Docker 都自己起来了，镜像都还在；demo2 的资源上限（见下）重启后仍有效。规定位置的那一份 Docker 和它的卷也在。
- **「重启后自己起来」准确地说是「用户登录后自己起来」。** 用户级后台服务默认只在用户登录期间运行：没开「不登录也常驻」（linger）时，用户最后一个会话退出后它们就停，下次登录再起来。试验时每个新的 SSH 会话刚开始的几秒，专用 Docker 的通道还不存在，就是这个原因。这台电脑也没开（`Linger=no`），所以它原来的 Docker 也是登录桌面后才起来的。对一台开发电脑，登录后起来就够了；要「开机不登录就起来」得开 linger，要一次管理员密码，第一版不需要。

### 三、两个项目各起一个，占多少

| | demo1 | demo2 |
|---|---|---|
| 专用 Docker 本身的进程实际占的内存（不算文件缓存，4 个进程） | 178 MB | 179 MB |
| 数据目录（各存一份 alpine 和 postgres 两个镜像） | 418 MB | 418 MB |
| 走本机内部的代理拉这两个镜像 | 17 秒 | 19 秒 |

- 系统给这个服务记的内存数是 530 MB 左右，那是把拉镜像留下的文件缓存也算进去了，不是它实际要的。
- 镜像每个项目各存一份（S2 就说过这是代价）。项目多、镜像大时磁盘占用按项目数成倍涨。
- W8 要的「一台电脑撑得住几个项目」：每个项目常驻约 180 MB，加上它跑的数据库、后端、浏览器测试。上限仍在第 2b 期定。

### 四、容器里面联网

先查了这台电脑本身：不走代理直接连 GitHub，回答 200，也就是**这台电脑直连就能上 GitHub**。

| 情形 | 结果 |
|---|---|
| 专用 Docker 的后台程序走 `127.0.0.1:7890` 拉镜像 | 可以。它的后台程序在电脑的网络里（网络放法是 `--detach-netns`） |
| 容器直接上网（不走代理） | 可以 |
| 容器连本机内部的代理（默认的网络放法） | 连不上。容器里的 `127.0.0.1` 是容器自己；默认关着「容器能连到本机内部」，几个地址都试了 |
| 打开「容器能连到本机内部」的开关，但仍用默认的网络放法（gvisor-tap-vsock） | 仍连不上 |
| 装上 slirp4netns、改用这种网络放法，再打开开关 | 容器能经 `10.0.2.2:7890` 连上本机内部的代理 |
| 上一行的代价 | 本机内部的其他服务，容器也都连得上：随便开的一个网页服务、本机的 SSH 服务都通 |

所以：**默认不打开「容器能连到本机内部」，容器直接上网**；这台电脑上可行。只有遇到「代理只在本机内部开着、又不能直连」的电脑，才需要打开它，代价是容器能连到本机所有只对内开放的服务（6.5 的「受限环境没有隔开网络」那一条更宽了），而且要装 slirp4netns（一次管理员密码）。第一版不打开；遇到这种电脑，流程命令如实说明，建议把代理设成对局域网开放的地址，由小白决定。

### 五、给容器限内存和处理器

| 做法 | 结果 |
|---|---|
| 给单个容器设上限（`--memory 128m --cpus 0.5`），在**不换根**的规定位置的 Docker 上 | 生效（容器里看到 128 MB、半个核） |
| 同样的写法，在**专用 Docker**（换了根）上 | **不生效**：专用 Docker 报「免管理员模式下没有 cgroups，要有 systemd 才行」。换根之后它连不上系统的服务管理器 |
| 给专用 Docker 的后台服务设上限 | 不生效：容器里的进程不在这个服务的组里，而在和它平级的另一个组里 |
| **把专用 Docker 放进它自己的一个「分组」（slice），上限设在分组上**（demo2：内存 300 MB、处理器 1 核） | **生效**：容器的进程落在这个分组里；要 600 MB 内存的进程被系统杀掉（退出码 137），专用 Docker 本身没事；四个进程一起算，限成 1 核的用了 3.06 秒，不限的 0.95 秒 |

让专用 Docker 连上系统的服务管理器也能按容器限，但那要把用户的会话通道放进它的视野。这条通道也通往系统钥匙串（GitHub 凭据可能存在里面），还能让服务管理器在受限环境外面起任何程序，等于把凭据隔离拆了，不能这样做。

所以：**资源上限按项目设，不按容器设。** 每个项目的专用 Docker 放进一个分组 `sop-<项目名>.slice`，上限设在分组上，管住这个项目在本机跑的一切容器。单个容器的上限做不到；技术栈档案里写的按容器的上限只在 GitHub 上（干净环境）有效。

## 结论

1. 数据放硬盘、两个项目各起一个：可行。每个专用 Docker 常驻约 180 MB 内存，镜像按项目各存一份。
2. 「重启后自己起来」是「用户登录后自己起来」；第一版不开 linger。
3. 容器里面联网：默认直连；本机内部的代理默认连不上，要连得装 slirp4netns 并打开开关，代价是容器能连本机所有对内的服务。第一版默认不打开。
4. 资源上限只能按项目（分组）设，不能按单个容器设。
5. 白名单仍有效：把整个根目录挂进容器，主目录下只看得到 `Project` 和 `tools`，看不到 `.ssh`。
