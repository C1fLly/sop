# 哪些工单要标风险（初稿，第 1 期第一段，W26）

## 风险标记管什么

规划阶段（F6 拆工单时）给每张工单写一行「风险」。带风险标记的工单：

1. 单独做一次独立复查（T9，约 1.2 到 1.5 美元一次）；没标的跳过 T9，靠写代码的 AI 自查、结果校验、门禁，问题要到整个功能的复查（F16）才被独立地看到。
2. 脚本建议小白逐张验收（F13），而不是整份做完统一验收。

写法：`风险：无`，或 `风险：<类别编号>，<一句大白话说明>`，可以写几个类别。

## 标的标准：命中下面任一条就标

| 编号 | 类别 | 举例 |
|---|---|---|
| R1 | 登录和权限 | 登录、退出、找回密码、会话过期；谁能看、谁能改哪条数据（含「只能看自己公司的数据」）；角色和授权；审计日志 |
| R2 | 钱和数量 | 金额、价格、折扣、税费、余额、积分、库存、工时、请假天数等的计算或累加；四舍五入；对账；按日期跨月跨年拆分的统计 |
| R3 | 数据的结构和去留 | 数据库结构变更（迁移文件）；删除数据、批量修改数据；导入、导出；数据的保留和清理 |
| R4 | 对外的约定和外部服务 | 改接口契约（`contracts/openapi.yaml`）；对外发送（邮件、短信、站内通知、回调）；调用第三方服务（支付、身份、地图等） |
| R5 | 不能撤回的动作 | 提交后不能撤回的业务操作（审批通过、结算、发货）；定时自动执行的任务 |
| R6 | 个人信息 | 处理身份证号、手机号、住址、银行卡等个人信息（产品风险分级 P1 里命中个人信息时） |
| R7 | 同时操作和时间 | 多人同时改同一条数据；排队、抢占、重复提交；跨时区、跨天的时间计算 |
| R8 | 把关本身 | 改已有的测试；改构建配置、检查工具的配置；新增「跳过这个测试」「这一行不检查」的标记 |
| R9 | 修复 | 由验收不通过、功能复查、功能门禁、GitHub 检查失败生成的修复工单，一律标（设计书 7.4） |

## 一般不用标的

只改显示的文字和样式；新增只读的、不涉及权限判断的展示页面；纯粹的重构且已有测试全部覆盖（「已有测试全部覆盖」由门禁的覆盖率核对，不靠 AI 说）。注意：看似只读的列表页，如果涉及「谁能看到哪些数据」，属于 R1。

- 规划阶段写工单的 AI 按本标准写风险行（规则写在项目规则 `AGENTS.md` 里，本标准随工具包版本走）。
- 规划复查（F9）逐张审风险行标得对不对；漏标的算阻断问题。
- 脚本兜底（T4）：这张工单实际改到了档案声明的敏感位置，即使没标也做 T9。敏感位置由各技术栈档案列出，至少包括：

**一、漏掉了哪些可能出大问题的情形**

这里区分一下：“删除数据”“重复提交”“第三方支付”等已经列了，不算漏项。真正需要补的是下面这些明确规则。

1. **密钥、服务凭据和系统安全设置。**  
   例如把服务端密钥打包到浏览器里、关闭证书校验、放宽跨域访问、误用生产环境凭据。这些不一定改登录模块，也不一定处理个人信息，但可能让别人取得整个系统或外部服务的访问能力。R1 讲的是用户登录和权限，不能指望 AI 自动把这些都归进去。

2. **把用户输入拿去执行、读取文件或访问网址的地方。**  
   例如上传和解压文件、拼数据库查询、运行系统命令、显示用户写的富文本、根据用户提供的网址抓取内容。出错可能导致恶意代码执行、服务器文件被读取，或用户浏览器被攻击。当前标准没有明确涵盖。应标的是这些输入的处理、安全限制发生变化，不是所有带输入框的页面。

3. **业务状态和关键业务限制，即使操作能够撤销。**  
   例如已取消订单还能继续处理、审批人批准自己的申请、未满足条件就进入下一步。它们不一定涉及金额、权限代码或“不能撤回”，但会让业务规则失效。R5 只抓不可撤回操作，范围偏窄；应补充“改变关键状态流转或前置条件”。

4. **生产部署、运行配置和实际使用的依赖变化。**  
   例如部署到错误环境、配置错误导致服务无法启动、升级依赖导致线上不兼容、回退版本后读不了新数据。R8 的“构建配置”能覆盖一部分，但没有明确覆盖部署文件、环境配置、依赖版本和锁文件。这里应针对影响实际运行的变化，不必把普通开发辅助工具升级全部标上。

5. **非个人信息的保密数据。**  
   例如公司报价、合同、经营报表、内部文件。访问权限属于 R1，导出属于 R3，但把这些内容写进日志、缓存到公共位置或展示在错误信息里，未必触发现有条目。R6 只列个人信息，不能代替“敏感数据泄露”的规则。

6. **备份恢复，以及影响整套服务可用性的操作。**  
   例如恢复时覆盖现有数据、修改备份范围后漏掉关键文件；又如改变大批量查询、上传大小限制或任务执行方式，导致服务器资源耗尽。前一类可能被勉强归进 R3，后一类很难归类。应明确触发条件，重点是会覆盖数据、阻塞核心操作或影响整体服务的改动，而不是所有性能优化。

**二、哪些条目太宽，容易白花复查的钱**

1. **R8“改已有的测试”把普通维护也全部算进去了。**  
   改测试名称、整理测试数据、给旧测试增加断言，都会命中。建议把必标条件集中在：删除测试、削弱断言、减少测试范围、改测试预期以接受新的业务行为、改变测试是否执行。否则越认真补测试，越容易多付复查费。

2. **R9“所有修复工单一律标”不区分失败原因。**  
   错别字验收不通过、格式检查失败、页面间距不对，和权限漏洞修复被同等处理。只要项目经常有修复工单，风险比例就会被明显推高。建议保留实质功能、安全、数据问题的必标规则，并为确实只涉及文案、样式、格式的修复设置明确例外。这需要同步处理它引用的设计书要求，不能只改表格。

3. **R3“数据库结构变更、导入、导出”覆盖面很大。**  
   给尚未上线的新表加一个可选字段，与删除线上字段不同；下载当前已显示的数据，与导出全公司资料也不同。应区分是否影响已有数据、兼容性、敏感范围、批量写入或服务器负载。否则数据类功能很可能整批被标。

4. **R4“调用第三方服务、对外发送”没有后果门槛。**  
   改地图展示选项、调整普通通知文案，都可能命中。更值得必标的是改变接收人、发送范围、发送时机、重试方式、凭据、付费调用，或者把第三方返回结果用于关键业务决定。

5. **R5“定时自动执行的任务”一刀切。**  
   定时清理业务数据值得标；定时刷新一个允许短暂过期的公共展示缓存，风险可以低得多。应根据任务会不会改数据、发消息、花钱，以及失败或重复运行的后果来判断。

6. **R2“数量、计算或累加、四舍五入”缺少用途限制。**  
   AI 可能把页面上“共 12 项”、展示百分比保留一位小数也标上。建议明确：影响结算、权益、资源分配或正式业务记录的计算必须标；纯展示且不影响业务结果的计算通常不标。

另外，**“拿不准时就标”适合兜住少量边界，不能代替明确边界。**当前规则里含糊处多，再加这句话，三到五成的预估就缺少可靠依据。多标还会增加使用者逐张验收的时间，成本不只是复查费。

**三、哪些措辞含糊，AI 会拿不准**

1. **“类别”和“举例”究竟哪个决定是否命中？**  
   表头叫“举例”，意味着清单并不完整；但又没有给每个类别一个可判断的定义。AI 只能自己猜“类似到什么程度才算”。建议每类补三项：必须标的条件、明确不标的情况、容易混淆的例子。

2. **“一般不用标”与“命中任一条就标”发生冲突时，谁优先？**  
   例如只改登录页提示文字，既是文字修改，又属于登录；重构权限模块，既可能符合重构例外，又命中 R1。必须明确：是否以实际改变的行为为准，哪些例外能够覆盖类别规则。

3. **“纯粹的重构且已有测试全部覆盖”不能靠覆盖率直接认定。**  
   覆盖率能显示哪些代码被测试运行过，不能证明权限边界、失败路径、并发情况都被正确检查了。即使覆盖率很高，也不能据此认定重构安全。建议取消这个笼统免标条件，至少不能让它自动豁免敏感逻辑的改动。

4. **R6 的“处理个人信息”和括号里的 P1 条件不明确。**  
   展示、搜索、日志记录、缓存算不算处理？如果产品分级没做、做错了，工单是不是就可以不标？应让实际接触的数据和行为决定是否标记，不能把此前分级当成唯一开关。

5. **“不能撤回”是指没有撤销按钮，还是无法消除实际后果？**  
   邮件可以删除发送记录，但收件人已经看到了；发货可以退货，但物流费用已经产生。建议按“是否已经产生无法完全恢复的外部影响”判断，并说明后续补偿不等于撤回。

6. **“改接口契约”是只看指定文件，还是也看实际行为？**  
   代码改变了返回字段、错误码、默认排序或字段含义，却没更新 `contracts/openapi.yaml`，照样会影响调用方。应明确实际对外行为变化也触发，不能以有没有改那个文件为准。

7. **R7 的“多人同时改同一条数据”容易被理解得过窄。**  
   同一个人开两个页面、后台任务与人工操作同时进行，或者两条不同记录共同消耗同一份额度，也会冲突。“重复提交”虽已列出，仍应把核心判断写成：多个操作是否争用同一份资源、状态或限制。

8. **“一句大白话说明”没有要求写什么，可能变成空话。**  
   “涉及数据，风险较高”符合格式，却无法复核。建议要求说明“改了什么，出错会影响谁、造成什么”。例如：“调整公司数据筛选，写错可能让甲公司看到乙公司的订单。”

**四、“脚本兜底”的敏感位置还漏了什么**

敏感位置应由项目档案填写具体路径，不能让脚本临时猜。建议至少补下面这些类别：

1. **核心业务规则的位置。**  
   金额、库存、额度、状态流转、结算、对账等代码。现在脚本清单主要覆盖登录、迁移和工程配置，R2、R5 很多重要改动没有对应兜底位置。

2. **普通数据访问和数据库定义的位置。**  
   数据模型、ORM 映射、数据库查询、触发器、初始化数据，以及批量修复、备份恢复脚本。改坏数据不一定要经过迁移文件。

3. **外部服务与异步任务的位置。**  
   支付、邮件、短信、回调处理、定时任务、队列消费者、重试和去重逻辑。这些直接对应 R4、R5、R7，现有清单没有明确列出。

4. **个人信息和其他保密数据流经的位置。**  
   脱敏、日志、错误上报、分析统计、缓存、文件存储、导入导出模块。只守登录目录，挡不住数据从其他出口泄露。

5. **输入安全和系统安全配置的位置。**  
   文件上传、解压、富文本处理、命令执行、动态查询，以及跨域、证书、凭据加载等配置。应列明相关路径和配置项，而不是把所有页面文件都设为敏感。

6. **部署文件、依赖清单和锁文件。**  
   CI/CD 工作流、容器配置、基础设施配置、环境配置模板、依赖版本及锁文件。现稿只点名 `package.json` 的脚本和检查设置，依赖部分容易漏掉。

7. **接口的其他定义来源。**  
   路由、请求和响应类型、消息格式、生成接口定义的源文件。项目未必只靠一个 OpenAPI 文件定义对外约定。

8. **风险判断和复查流程自身。**  
   本标准、存放相关规则的 `AGENTS.md`、技术栈敏感位置档案、识别风险的脚本、决定是否执行 T9 的配置。否则一次改动可以让后面的风险检查失效。若 `AGENTS.md` 内容很多，可针对相关段落判断。

还有两个比补目录更关键的执行缺口：

- **要检查最终完整改动，并识别新增、删除、重命名和移出敏感目录。**文件叫 T4 并不能说明它在什么时候运行；如果它在改代码之前判断，或者只查部分改动，就可能漏掉后来新增的敏感修改。
- **脚本补中的风险要写回工单，并传给验收建议。**当前只说补做 T9，没有说明是否同时触发 F13。否则代码虽然复查了，使用者仍可能收不到逐张验收的提示。

路径匹配只能提供兜底，不能保证找出所有风险。尤其敏感逻辑第一次被写进新文件时，应有更新敏感位置档案的规则。

**五、总的结论和最该改的三处**

**可以作为第一版的底稿，但不建议原样作为正式执行标准。**它适合提醒人“哪些地方要小心”，距离让 AI 稳定、一致地标记，还差明确的判定规则。

最优先改这三处：

1. **补齐高后果漏项。**  
   明确加入密钥与安全设置、不可信输入处理、关键业务状态、生产运行变化、非个人保密数据，以及备份恢复。否则有些严重问题连明确的类别都找不到。

2. **给每类写清触发条件和例外，并统一冲突优先级。**  
   优先收紧 R8、R9 的一刀切，取消“覆盖率足够即可免标重构”的判断。这样才能同时减少漏标和无效复查。

3. **把脚本兜底做成完整流程。**  
   敏感位置要覆盖业务、数据、部署和检查规则自身；最终改动触发后，要更新工单风险、执行 T9，并同步验收提示。否则纸面规则和实际执行会脱节。

最后，风险标记应附带**使用者能做的具体验收动作和预期结果**。例如“用甲公司账号打开乙公司的订单，应被拒绝访问”。对密钥泄露、并发一致性这类使用者无法直接确认的问题，应写明依靠什么技术检查，不能把“建议逐张验收”当成已经有人把住了关。
