# 《AI 开发 SOP 工具包 设计书》草案 v0.2 第二轮独立审查报告

## 总评

v0.2 比 v0.1 扎实，上一轮的 21 条问题大部分是真改了，不是换说法。真改的有：进度改成带证据的记录、新电脑加了第零步、线上密钥不放开发电脑、验收环境有了设计、工具包可多版本并存、检查的边界如实写了出来。

但 12 条要求里，仍然只有第 4 条（位置固定）可以说落实。其余要么只在纸面上成立，要么成立的前提还没验证。最要紧的是四件事：

1. **第 6 节的地基还是虚的。** 设计只限制了「AI 这个进程」。但 AI 写的测试和程序，还会被不受限制的流程命令亲自运行。上一轮第 3 条指出的洞没有补上。而且设计书说「第三层做不到就靠第二层和第四层」，可第四层正是靠第三层才成立的。
2. **新的「完成记录」带来了新的自相矛盾。** 记录靠「文件内容没变」判断是否有效，但后面的步骤会正常地改这些文件，做到一半的功能会被打回前面的步骤。记录和代码放在一起，写一条记录就多一次提交，GitHub 上刚通过的检查和刚做完的验收就对不上了。
3. **「原样运行 implement-spec」这条路对不上。** 它和隔离做法、和 wt 的实际行为都有冲突，第 0 期又没有任何试验覆盖它。
4. **上线运维的关键内容是空的。** 部署档案连候选平台都没有；线上服务器自己出故障时，没有任何角色能处理。

我没有修改任何文件。下载的技能原文放在 `/tmp/review-skills-QL7Mh7`，自己写的两个小查询脚本放在 `/tmp/review-scripts-x1`。

用到的几个词先解释一下：

- **PR**：合并申请，把一条分支的改动并入另一条分支前在 GitHub 上开的单子。
- **钩子**：某个动作前后自动执行的小脚本。
- **变基**：把自己的提交挪到最新代码后面重排，会改写历史。
- **指纹**：按文件内容算出的一串校验码，内容一变它就变。
- **子代理**：AI 自己再派出去的帮手。
- **受限环境**：把 AI 关在读不到登录凭据、写不了别处的小范围里。

## 一、确定的问题

### 严重

**1. AI 写的代码会被不受限制的流程命令亲自运行，上一轮第 3 条的洞没补上**

- 位置：6.2 第三层、7.5 的 T5、9.2、第 13 节
- 原文：
  - 「AI 进程读不到 GitHub 登录凭据和 SSH 密钥，因此不能推送、不能合并。只有流程命令能。」
  - T5「工单门禁｜脚本」
  - 「声称通过的命令由脚本重新运行」
  - 「从要验收的那个工作目录启动整套系统」
- 问题：上一轮指出的是「测试代码是 AI 写的，测试运行时什么都能读写」。v0.2 只把「AI 进程」关了起来，下面这些地方照样在运行 AI 写的代码，而且是流程命令带着全部登录凭据在运行：
  - 本机门禁（T5、F15）跑测试。
  - 9.2 重新运行 AI 声称通过的命令。
  - `sop accept` 启动整套系统。
  - wt 的 `post-create` 钩子按锁文件装依赖（wt 说明书原文），依赖包里的安装脚本会被执行。
  - 项目若装了提交钩子，它放在所有工作目录共用的 `.git/hooks` 里（wt 模板钩子的注释原文），流程命令每次提交都会触发。
- 设计书全文没有一处说这些也要在受限环境里运行（我检索了所有「受限」「隔离」的出处）。

**2. 「第三层做不到就靠第二层和第四层」这条退路不成立**

- 位置：6.3、6.2 第二层和第四层、第 20 节 W2 和 W3
- 原文：
  - 「第三层若最终只能部分实现，把关就主要依靠第二层和第四层。」
  - 「AI 不能推送，所以改不了锚点。」
  - 「GitHub 免费计划的私有仓库不支持分支保护。」
  - 「能否合并，以 GitHub 上检查流程的结果为准。」
- 问题：
  - 第四层自己写明它靠的是「AI 不能推送」，这正是第三层的内容。第三层不成，第四层的锚点就能被改。
  - 没有分支保护时，GitHub 只负责「出结果」，不负责「拦住」。真正拦的是本机的流程命令。
  - 所以 W2 和 W3 若都选「不做」，剩下的只有写给 AI 看的规则。设计书没有把这个后果讲明白，你按现在的写法做不了这个决定。
  - 另外第一层的标题「开发电脑上没有值钱的密钥」也不准确：GitHub 登录凭据和 SSH 密钥就在这台电脑上，拿到它就能推送、合并、触发部署。

**3. 完成记录的失效规则，会把正常推进的功能打回前面的步骤**

- 位置：8.2、7.4 的 F4 和 F10、9.3、7.5 的 T7
- 原文：
  - 「记录是否有效，看它的输入指纹是否仍与当前文件一致。」
  - 「当前步骤是流程定义里第一个没有有效记录的步骤。」
  - F4「记录存在，且绑定的页面代码版本未变」
  - 「实现阶段把假数据换成真实接口」
  - F10「指纹与当前规格、工单、验收包一致」
  - 「答案追加到工单的评论区」
- 问题：这是上一轮第 4 条换了个形式又出现。后面的步骤会正常地改前面确认过的东西：
  - 实现阶段必然要改原型页面的代码，F4 的记录随之失效。
  - 业务问题的答案要写进工单文件，F10 的记录随之失效。
  - 技能原文要求工单做完后把状态改掉（implement-spec 原文「every ticket resolved the way the issue tracker closes work」），工单文件又变了。
  - T7 允许「修改规格的技术部分」，F17 不通过会新增修复工单，同样让 F10 失效。
- 按「第一个没有有效记录的步骤」这条规则，功能做到一半会被判回 F4 或 F10。

**4. 完成记录放在哪条分支没有说；和代码放在一起会让检查结果、验收结果对不上**

- 位置：8.2、7.5 的 T10 到 T14、7.4 的 F17 到 F22、7.3 的 P1 到 P7
- 原文：「记录放在仓库的 docs/records/ 下，由流程命令单独提交并立即推送。」
- 问题：
  - 写一条记录就是一次新提交。T10 等到 GitHub 检查通过后写记录并推送，分支上多了一个提交，GitHub 会重新跑检查，T12 合并时面对的是「还没查完」的状态。T11 的验收记录、第 13 节的「更新视觉基准」同理。
  - 工单 PR 合并后（T12 到 T14），工单分支已经没了。wt 的清理命令又不允许合并后本地还有新提交（wt 说明书列的反例「合并后本地又有提交」）。这几步的记录写到哪里没有说。
  - 功能合并后的 F19 到 F22，以及根本没有功能分支的 P1 到 P7，记录只能直接推到主线。这和「一切经过 PR 和检查」矛盾；W3 若选择开启分支保护，这样的直推会被拦住。
  - 多张工单并行时，几个流程同时往同一条功能分支推记录，会互相顶掉，设计没提怎么排队。
  - 每次推送都会触发 GitHub 上的检查，免费时长消耗会成倍增加（见疑问 2）。

**5. 「原样运行 implement-spec」这条路和隔离、和 wt 的实际行为对不上，第 0 期也没有试验覆盖它**

- 位置：7.6、6.2 第三层、6.3、4.3、4.7
- 原文：
  - 「任务包规定子代理只能通过工具包提供的一个命令来建，这个命令内部调用 wt、执行钩子、分配端口，并留下一条记录。」
  - 「这条路径与 wt 的规则有两处出入」
  - 「最多丢失一个正在进行的步骤」
- 问题（对照 wt 脚本和技能原文）：
  - `wt new` 每次都先从 GitHub 拉取，拉取失败就中止（脚本里的 `fetch_all`）。拉取要用 SSH 密钥，而第三层规定 AI 进程读不到它。这个「工具包提供的命令」在受限环境里跑不起来。
  - 端口登记在 `~/.config/sop/`（4.3），在项目根之外。受限范围只放宽到项目根，分配端口写不进去。
  - 这条路里 AI 不能推送，功能分支的新内容只在本机。后面的工单若仍按 5.4 从 `origin/feat/<功能>` 建目录，拿不到前面工单已合入的代码。
  - 出入不止两处。技能原文还要求：探索用的子代理把笔记存到仓库之外的目录（第 2 步）；AI 自己开草稿 PR 并在最后转成正式（第 3、8 步）；AI 自己清理所有工作目录（第 9 步）。这几处和「AI 不能推送」「清理由流程命令做」都冲突，设计书没提。
  - 整个实现在流程里只算 F14 一个步骤。这期间没有推送，旧电脑坏了丢的是整个功能的实现。上一轮第 6 条说的「一个功能可能做好几天，中途坏掉就没了」，在这条路上依然成立。
  - 第 0 期的 S3 只试「5.4 的分支和 PR 结构」，不含这条路。它第一次真正运行是在第 2 期末尾。

**6. 线上出了事，没有人能修；部署档案是空的**

- 位置：7.7 的 R2、7.8、17.1、第 19 节、第 20 节
- 原文：
  - 维修窗口「适用于机器、工具、网络、Docker、工具包自身出故障」
  - O2「止血｜脚本（小白确认后退回上一个程序版本）」
  - R2「生成平台操作单（没有现成档案时）｜AI 交互」
  - 第 2 期「参考部署档案里骨架需要的部分」
- 问题：
  - 维修窗口只管开发电脑。线上服务器磁盘满、数据库挂掉、证书过期、欠费停机、被攻击，这些不是「退回上一个版本」能解决的，设计里没有任何角色或流程处理。
  - 「参考部署档案」全文没有说是哪个平台、哪种部署方式，第 20 节的未决事项里也没有这一项。后端档案至少列了候选（11.5），部署档案连候选都没有。上一轮第 10 条「档案是空的」在这里原样存在。
  - 告警怎么送到手机，用什么渠道、要不要另开账号，没有写。
  - 没有现成档案时由 AI 在对话里现写部署、回滚、备份脚本。在没有专业人员的前提下，这是全流程里最危险的一步。

### 中等

**7. F8 排在 F9 前面，却要审查 F9 才产出的东西；验收卡的内容没有人审**

- 位置：7.4
- 原文：
  - F8 说明「大白话摘要是否如实反映规格」
  - F9 产出「每张工单一份验收卡，加一份大白话摘要」
  - F9 出口检查「每条验收标准至少对应验收卡一个步骤」
- 问题：摘要在 F9 才写出来，F8 审不到。验收卡是你唯一的把关工具，却只查了格式。卡上写的「预期结果」是否符合规格，没有任何步骤审。

**8. 视觉基准只能在验收时更新，但截图对比的门禁排在验收之前**

- 位置：5.2、14.2、第 13 节、7.4 的 F15 和 F17
- 原文：
  - 「视觉基准截图（只由验收步骤更新）」
  - 「截图与视觉基准的差异在允许范围内」
  - 「全部通过时，为涉及的页面截图，更新视觉基准」
- 问题：一个功能有意修改已有页面时，F15 的截图对比必然不通过，而能更新基准的 F17 排在 F15 后面，走不到。逐张验收的方式同理（T10 在 T11 前）。

**9. 「验收绑定代码版本」有两种互相矛盾的说法**

- 位置：7.4 的 F17 和说明、7.2 的 I1
- 原文：
  - F17「每张验收卡都有绑定当前代码版本的通过记录」
  - 「后来的提交如果改到了这张工单改过的文件，这张验收卡重新打开」
  - I1「只允许 Squash 合并」
- 问题：
  - 逐张验收是在工单分支上做的。合并时多次提交被压成一次，提交编号变了；别的工单合入后「当前代码版本」又变了。按 F17 的字面，所有卡都要重验。
  - 按说明里的规则则只看文件。但后来的工单不碰同一个文件也可能弄坏已验收的行为；菜单、路由这类公共文件每张工单都会碰，卡会不停被重新打开。
  - 两种说法以哪个为准没有定。

**10. T13 让 AI 变基，和「历史没有被改写」的检查、和「强制推送先问小白」都冲突**

- 位置：7.5、14.2、17.2
- 原文：
  - 「T13 是唯一允许 AI 在工作目录里执行变基的步骤」
  - 历史延续「本地历史是远程的延续，没有被改写」
  - 「强制推送，一律先问小白」
- 问题：
  - 工单分支此时已推送并开了 PR，变基后只能强制推送。
  - 变基就是改写历史，第四层的锚点检查必然报错。
  - 每次冲突都要你批准一次你判断不了的强制推送。

**11. 技术决策角色的权限和它要做的事对不上；「小白不参与」也对不上**

- 位置：3.4、7.5 的 T7 说明、8.2
- 原文：
  - 技术决策「只能新增决策记录」
  - 「把工单拆小、修改规格的技术部分、建议放弃这条行为。只有最后一种需要问小白」
- 问题：
  - 拆工单要改工单文件，改规格要改规格文件，都超出「只能新增决策记录」。由谁来改没有说。
  - 规格和工单一改，按 8.2，F10 的确认就失效，你必须重新确认规划。这和「只有最后一种需要问小白」矛盾。

**12. 「第一个没有有效记录的步骤」这条规则处理不了循环和有条件的步骤；失败不留记录**

- 位置：8.2、7.4、7.5
- 原文：
  - 「一个步骤的出口检查全部通过后，流程命令写一条完成记录」
  - 「修复轮数、已完成功能数这类计数，从记录条数得出。」
- 问题：
  - 流程里有回头路：T6 回 T4、T13 回 T5、F17 不通过回 F14。
  - 流程里有条件步骤：F3、T8、T11、T13、R2。这些步骤不执行时算不算「没有记录」，没有说。
  - 记录只在通过时才写。失败的那几轮没有记录，「修复了几轮」和失败轮次的花费就无从得出。

**13. 受保护路径清单有漏项**

- 位置：5.6、4.7、5.2
- 原文：
  - 「sop.toml、.github/workflows/、技能文件、docs/records/、docs/baseline/」
  - 「项目的 wt 钩子｜仓库内 ops/wt-hooks/｜克隆时安装到 .shared/hooks/」
- 问题：下面这些同样决定把关松紧，或会被流程命令带着凭据执行，却不在清单里：
  - `ops/wt-hooks/`，以及仓库之外的 `.shared/hooks/`：流程命令每次调用 wt 都会执行它们。
  - `AGENTS.md` 和 `CLAUDE.md`：以后每个 AI 会话都读的规则。
  - `.claude/` 下的设置文件：能改权限、能挂钩子。本机 `claude --help` 写明，自动调用时会跳过「是否信任此目录」的确认。
  - `docs/agents/`：技能的配置，工单必须带覆盖行、风险行就写在这里。
  - `docs/standards/`：复查用的规范。
  - 提交钩子的配置文件。

**14. 几个流程没有定义完，或者没有入口**

- 位置：5.6、7.4 的 F21 说明、16.5、7.8、7.9、8.4
- 原文：
  - 「只有三种专门的步骤可以改：工具包升级、规范变更、验收（更新视觉基准）」
  - 「属于项目规范的走「规范变更」步骤」
- 问题：
  - 「规范变更」和「工具包升级」在第 7 节任何一张流程表里都没有：谁发起、谁确认、出口检查是什么都没写。尤其「放宽规则」只要另一个 AI 同意就行，你不知情，谁来判断是「收紧」还是「放宽」也没说。
  - 8.4 的命令表里没有发起发布、体检、规范变更的命令，这几个流程从哪里开始没有着落。
  - 7.8 的运维流程表没有「出口检查」一列；7.9 的体检流程没有步骤表。这和 Y2「每个步骤一个出口检查」、8.1「每个步骤声明出口检查」不一致。

**15. 「粘贴」这条路上的 AI 不在受限环境里**

- 位置：10.1、6.2 第三层
- 原文：「工具不支持自动调用时，流程命令打印任务包，小白复制到 AI 窗口」
- 问题：这个 AI 窗口是你自己打开的，不是流程命令启动的，第三层的限制对它不起作用。

**16. 原型这一段有三处没接上**

- 位置：7.4 的 F2、F3、F4、F5
- 原文：
  - F2 产出「术语表和决策记录的更新、追问结论」
  - 「F3 是这条链中途的岔路，在另一个全新会话里做，输入是 F2 的追问结论」
  - F4「原型确认｜人｜确认记录」
- 问题：
  - 追问技能的原文只更新术语表和决策记录，不产出「追问结论」。这份东西由谁写没有着落。
  - F5 续接的是 F2 的会话，那个会话不知道原型做成了什么样、你看了之后说了什么。技能作者的做法是来回各写一份交接文件（ask-matt 原文），设计里没有这一步。

**17. 技能自己会向你提技术问题，设计只处理了 F2**

- 位置：7.4 的 F2 说明、F5、F6，7.3 的 P9，7.9
- 原文：「AI 仍然问到技术题时，小白回「按档案」，带路窗口负责核对推荐答案与档案一致。」
- 问题：
  - F2 里要你自己先分清一道题是技术题还是业务题，这本身就是你做不了的判断。带路窗口在另一个窗口里，怎么看到这边的问题也没说。

  - P9（通用契约：鉴权接法、错误格式、分页）照功能流程走，也要你追问、确认、做行为验收。这些内容你验不了。
  - 体检里的 `improve-codebase-architecture` 原文是出一份报告，然后问「你想深入哪一个」。由谁来挑没有写。

**18. 三处要你动手或拍板、其实该由脚本做的事**

- 位置：17.1、16.3、5.5
- 原文：
  - 「每条会改变系统的命令都先用大白话向小白说明做什么、有什么后果，小白同意后才执行」
  - 「把这个测试的预期结果改掉然后提交，应当看到检查失败」

  - 维修窗口：你只能依据 AI 自己的说明来批准，这就是 Y6 反对的「采信自述」。管理员密码一输，「不能改项目代码和完成记录」也没有任何东西拦着。

  - 遗留的数据卷属于哪个已删除的目录，脚本按名字就能算出来，不该问你。

**20. 骨架（P8）要求部署到预发，但开通账号排在后面的发布流程里**

## 二、只是疑问（需要实测或由你决定）

1. **GitHub 触发方式。** 我知道的一种做法是让检查定义取自 PR 的「目标分支」。工单 PR 的目标是功能分支，不是主线，那么「定义取自 main」对工单 PR 是否成立？另外这类做法通常会让 PR 里的代码接触到仓库里存的密钥，而第一层正好把线上密钥放在那里。S4 应一并验证「PR 里的测试代码读不到线上密钥」。
2. **免费时长。** 每张工单一个 PR，每推一次记录又触发一次。据我所知，免费私有仓库每月 2000 分钟（未联网核对）。全量门禁含端到端测试、变异测试、连续多次运行，一个功能可能就用完。
3. **Claude Code 自带的建工作目录功能。** wt 的 AI 规则专门点名禁止它。它建的目录不在项目根的第一层，7.6 的事后核对只看项目根下的工单目录，会不会看不到？
4. **技能原文里 AI 自己推送的做法。** wayfinder 要把调研结果推到一条临时分支；prototype 要把原型提交到一条临时分支。这些和「AI 不能推送」冲突，是靠配置压住还是打补丁？
5. **S1 应多试三件事。** tdd 原文要求「先和用户确认切入点才写测试」，自动调用时会卡住还是自行决定？code-review 原文要求用户给出比较的起点，没给就要问。research 要开后台帮手，自动调用下主会话结束时它跑完了吗？
6. **订阅和额度。** 用订阅而不是按量付费时，「花费」怎么算？额度用完或被限流时，做到一半的步骤留下的半截改动由谁清理、怎么续？
7. **TypeScript 那套的前端。** 之前讨论记的是「TypeScript 全栈」。设计让两套后端共用一份 Vue 档案，这是你的本意吗？
8. **整体原型。** 现在只有每个功能自己的原型，加一个导航外壳（P10，排在骨架和通用契约之后）。开工前看不到整个产品的样子，是否可以接受？
9. **wt 与 Ubuntu 24.04。** wt 说明书的「已验证」表里有 22.04 和 26.04，没有 24.04，而设计书把 24.04 列为支持版本。
10. **仓库只有 GitHub 一处。** 账号被锁或误删仓库时没有备份。
11. **旧项目。** `~/Project` 下已有的项目要不要接入，设计没提。
12. **工具包版本。** 检查脚本按版本号从公开仓库取。版本号对应的内容之后能不能被改？公开仓库本身可以免费开分支保护，设计没提要不要开。
13. **截图环境。** 基准是在你电脑上验收时截的，对比在 GitHub 的机器上做，两边字体和渲染不同，会不会经常误报？
14. **第零步的下载命令。** 用什么下载？全新 Ubuntu 桌面版没有 curl。
15. **Codex、OpenCode、Pi 的资料。** 附录 C 的出处是第三方网站和「搜索摘要」，设计书自己也标了未核对。这三列目前不能当依据。

## 三、几个专项的结论

### 第 6 节四层做法

- **第一层**（线上密钥不放开发电脑）：站得住，是 v0.2 最实在的改进。弱点见问题 2 末尾和问题 19。
- **第二层**（GitHub 当裁判）：方向对。但没有分支保护时它只出结果、不拦人（问题 2）；实现方式未定且有副作用（疑问 1）；受保护路径有漏项（问题 13）。
- **第三层**（受限环境）：整节的承重墙，目前完全是「待试验」。有四处问题：
  - 字面上做不到。原文「AI 进程只能写自己的工作目录」，但所有工作目录共用项目根下的 `.git`（wt 的结构如此），AI 要提交就必须能写它，而那里面有配置和钩子。
  - 只管了 AI 进程，没管 AI 写的代码（问题 1）。
  - 粘贴路径不受限（问题 15）。
  - implement-spec 路径与它冲突（问题 5）。
- **第四层**（事后发现）：依赖第三层（问题 2）。另外「核对本地历史是远程的延续」没写是不是每次都去 GitHub 现查。如果只看本机存的那份远程记录，AI 能写 `.git` 就能改它。「流程命令核对工具包与公开仓库一致」是自己查自己。

### 第 19 节分期

- 先试验再动工是对的，S1 和 S2 确实抓的是大风险。
- S3 没覆盖 implement-spec 路径和换电脑（问题 5、22）；S5 与 W5 矛盾（问题 23）；S6 应加上问题 3、4、12 的场景。
- 漏掉的、更该先试的四件事：
  - **真人走一遍主链。** 不用工具包，你本人用 Claude Code 手动走一次「追问、规格、工单、实现」做一个小功能，记下哪里答不上、哪里看不懂、花了多少钱和时间。这是整套设计最大的未知数，现在排在第 2 期末尾。
  - **implement-spec 路径在受限环境和 wt 下能不能跑。**
  - **GitHub 这头。** 没有分支保护时到底拦得住什么；记录推送触发多少次检查；PR 里的代码能不能读到密钥。
  - **部署平台。** 现在就要选，备案现在就要启动。
