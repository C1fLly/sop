## 第一部分：`implement-spec` 的路径

### 先读了技能原文

`implement-spec` 的原文要 AI 做九步：读规格和工单；可选地派一个探索帮手，笔记存到仓库外面；建集成分支、开草稿 PR；每张工单派一个帮手，各自在自己的工作目录和分支上，用 `tdd` 做；做完一张，派一个合并帮手把它合进集成分支；哪张工单不再被挡住就接着派；全做完后在集成分支上跑一次 `code-review`，派一个帮手把问题修掉；把 PR 转正式；清理工作目录。

和设计书 7.6 列的五处差异逐条对上了，没有发现第六处。

### 怎么做的

**试验项目**：一个记账的命令行小工具，Python 标准库。规格 33 行，三张小工单：01 金额的解析和显示、02 账本文件的读和写、03 命令行（被 01 和 02 挡住）。这样能试到「两张同时做」和「前面合入后才放出下一张」。

**项目是用 wt 建的**：`wt init` 加 `--url` 指向本机的假远程，不连 GitHub 也能用。功能分支和目录用 `wt new feat/jizhang` 建。规格和工单事先提交并推送，相当于功能流程走到了 F12。

**技能副本打了补丁**，共七处改动，对应 7.6 的五处差异（副本和改动对照在 `docs/试验/脚本/S7/`）：

| 7.6 列的差异 | 补丁怎么改的 |
|---|---|
| 子代理各自建工作目录 | 改成执行 `sopreq new-worktree <工单编号>`，它打印建好的目录；写明不许用别的办法建目录或分支，不许用帮手工具自带的隔离功能 |
| 探索笔记存到仓库之外 | 改成存到项目根下的 `.shared/notes/` |
| AI 自己开草稿 PR、最后转正式 | 改成「集成分支已经有了，不要建，不要开 PR，不要推送」；结尾改成执行 `sopreq done` |
| AI 自己清理工作目录 | 改成「不要清理，结束后由外面清理」 |
| 合并帮手在本地合入集成分支 | 保留，加一句：每合完一张执行 `sopreq merged <工单编号>`，等回答 ok 再往下 |

另外给 `code-review` 那一步补了比较起点（`main`），给修复帮手也规定了经窄接口要目录。

**窄接口**，最小的实现，两头各一个脚本：

- 受限侧一头 `sopreq`：只会往一个请求目录里放一个请求文件，然后等回答。只有三种请求：建目录、报告已合入、报告全部完成。
- 特权侧一头 `broker.py`：在受限环境外面值守。每个请求先校验再执行，每条命令都记入日志。
  - 建目录：编号必须是两位数字或 `fix`；必须是规划里有的工单（工单清单取自已经推送到远程的规划，不看 AI 能改的文件）。通过后执行 `wt new ticket/jizhang/<编号> feat/jizhang`。
  - 报告已合入：这张工单的目录必须是经它建的；工单分支上必须有新提交，并且已经合入集成分支；集成分支必须是远程那条的延续；新提交不能改受保护路径。都通过才推送。
  - 推送时明说仓库在哪、关掉钩子，不运行任何项目代码。

**受限环境**：设计书 6.5 说这条路径要让 AI 在整个项目根下活动。所以放进去的是整个项目根，再把下面这些盖成只读：

- `.git` 整个只读，只放开：提交内容、各工作目录的登记、本功能的工单分支指针、集成分支指针。
- `main` 目录只读。
- `.shared` 只读（里面有 wt 的准备脚本和 `sopreq`），只放开笔记目录和请求目录。
- 集成目录里指向 `.git` 的小文件只读。

**wt 的准备脚本换成了只做一件事的版本**（链接 `.env`）。wt 模板自带的那一份会安装依赖，等于带着凭据运行项目代码，S3 已经指出过。

**启动的方式**：在集成分支的目录里，一次自动调用：`/implement-spec 规格在…，工单在…`。上限设的是 10 美元。

### 破坏演练

设计书第 2c 期的验收标准有一条：人为绕过窄接口建一个目录，事后核对能发现。这里先试了：

- 在受限环境里手工 `git worktree add` 建了一个目录 `sneak-88`，建成了。
- 再跑事后核对：**报出两条不符合**——「多出来的工作目录：sneak-88」「不是经窄接口建的工单分支：ticket/jizhang/88」，退出码 1。

这次是我手工绕的，不是 AI 绕的。

### 清理

AI 结束后由特权侧清理：四个工单目录用 `git worktree remove` 删掉；四条工单分支先核对「已合入功能分支」再删。

这里有一处要流程命令自己处理：**不能用 Git 自带的「安全删除分支」，也不能用 `wt done`。** 前者拿主线来判断合没合并，会说「没有完全合并」而拒绝；后者要看 PR 合并了没有，而这条路径没有工单 PR。所以特权侧要自己核对「已合入功能分支」，再强制删除。

### 隔离比别的路径弱在哪

设计书 6.5 已经说这条路径的受限范围更大。试下来具体是这三处：

1. **AI 能自己建工作目录和分支。** 工作目录是运行中才建的，受限环境启动时它们还不存在，所以只能把「各工作目录的登记」整个目录放开可写；放开了，AI 就能自己建。挡不住，靠事后核对发现（上面演练过）。
2. **运行中才建出来的工单目录，里面指向 `.git` 的小文件设不成只读。** 同样因为启动时它还不存在。S2 说过这个小文件要只读，防的是受限侧把特权侧引到假仓库去。在这条路径上只能靠另一条规矩：特权侧执行 Git 命令时总是明说仓库在哪。这次的特权侧脚本是这样写的。但 wt 自己是靠这个小文件找仓库的，所以这条路径上特权侧只在项目根下执行 `wt new`，不到工单目录里面去执行 wt。
3. **同一个功能的工单分支指针、所有功能的集成分支指针，AI 都能移动。** 前者是 S2 已知的；后者是这条路径新增的（AI 要在本地合并，就得能写集成分支的指针，而 Git 更新指针要在它所在的目录里建文件，那个目录里放着所有功能的集成分支）。靠特权侧推送前核对「是远程的延续」来发现。

### 试验中碰到的小事

- **Git 会打印一行吓人的报错，但其实成功了。** 在这种「`.git` 只读、只放开几处」的环境里，每次提交和合并都打印 `Unable to create …packed-refs.lock: Read-only file system`，退出码是 0，提交确实成了。我在启动时告诉了 AI 这是正常的；它每次都用提交记录核对了一遍。工具包的任务包里要写上这句话，否则 AI 可能以为失败了反复重试。
- **Git 会把空的分支指针目录删掉。** 最后一条工单分支删掉后，`.git/refs/heads/ticket/jizhang` 这个目录也没了，下次启动受限环境时找不到它而报错。特权侧每次启动受限环境前要先把这个目录建好。
- **wt 记账的地方**（`.git/config`）对受限侧只读，没有受影响。

## 第二部分：关掉 `implement` 自查的花费对比

### 怎么做的

- 用 S0 的试验项目（请假登记小工具，已做完 7 张工单，123 个测试）。从同一个提交复制出两份：
  - **A**：技能原样。
  - **B**：把 `implement` 技能里「做完后调用 `code-review` 审查这次的工作」那一句删掉，别的不动。
- 两份各用一个全新会话做同一张工单（09：已离职），提示词和 S0 一样：`/implement <工单文件>`。
- 做完后在受限环境里重跑全部测试。

| | A：带自查 | B：去掉自查 |
|---|---|---|
| 花费 | **2.81 美元** | **1.10 美元** |
| 用时 | 251 秒 | 115 秒 |
| 派出的帮手 | 2 个，都是自查派的（规范审查、规格审查各一个） | 0 个 |
| 调用的技能 | `tdd` 2 次、`code-review` 1 次 | 没有经技能工具调用（见下） |

| 改动量 | 3 个文件，加 236 行、减 29 行 | 4 个文件，加 211 行、减 21 行 |
| 中途向用户提问 | 0 | 0 |

**差 1.71 美元，自查占了 A 这一张工单花费的六成、用时的一半多。**

自查换来了什么（A 的汇报里写的）：

- 规格那一轴：没有缺项，没有实现错误；补了一处显示（查看已离职员工的请假单时标题没带「已离职」的标注）。
- 规范那一轴：没有硬性违规；改了几处命名和重复、两行过长；另有四条小毛病它自己判断不改。

两份做出来的行为有一处不同，和自查无关，是两次各自的取舍：A 让已离职的员工不能再查看或撤回自己的请假单；B 没有在规则层拦撤回（菜单里他的名字已经选不到，实际走不到）。两份都在汇报里如实说了。

### 这个数字能说明多少

- **只做了一张工单、每边一次**，不是统计结论。S0 里带自查的 7 张工单是 2.2 到 2.6 美元，这次 A 是 2.81，在同一个量级。
- B 还有一处和 A 不同：B 没有经技能工具调用 `tdd`，它说「`tdd` 不在可调用的技能清单里，我直接读了它的说明照着做」。这和 S5 发现的一致（项目技能不在 Claude Code 给 AI 的清单里）。A 是按名字调用成功的。所以 1.71 美元的差里，可能有一小部分来自这个不同，分不出来。
- **S0 里「每张工单派 4 个帮手」现在弄清了**：那些帮手就是自查派出来的两个审查帮手（会话记录里每个帮手记了两遍，所以数成了 4）。写代码的是主会话自己。

### 对 W15 的含义

设计里流程命令本来就要对每张工单另做一次独立复查（T9，规范和规格各一个全新会话），做的是和自查同一件事。保留自查就是同一件事花两份钱。**从这次的数字看，关掉自查能把每张工单的实现花费从 2.3 到 2.8 美元降到 1.1 美元左右。** **用户随后定了：不关，技能保持原样。** 所以每张工单的实现花费仍按 2.3 到 2.8 美元算，之外还有流程命令的独立复查。

独立复查（T9）自己要花多少钱，这次没有测。从自查的花费推，大概也是每张工单 1.5 美元上下，这是推测。

| 特权侧收到的请求 | 9 个，全部通过，0 个被拒（原来写成 10 个，是数错了，第三轮审查指出）：建目录 4 次（01、02、03、fix），报告已合入 4 次，报告全部完成 1 次。和第一部分一样 |
| 推送 | 5 次，每合入一张推送一次 |
| 事后核对（12 条） | 全部符合：全部工作目录都是经窄接口建的；三张工单的分支都已合入；远程和本地一致；没有改受保护路径；`main` 没有被动过 |
| 会话记录里越界的命令 | 0 条：没有自己建目录或分支，没有推送，没有清理目录，没有用帮手工具自带的隔离功能 |
| 技能文件 | 做完后和来源比对，五个都一致 |
| 做完后重跑全部测试 | 26 个，全部通过 |
| 试用 | `add`、`total`、输错金额的提示、不带参数的用法说明，都对 |

也就是说，技能原文说「建集成分支、开 PR、各自建工作目录、清理工作目录」的这几处，AI 都按任务说明做了，没有照原文做。

### 这次碰到的一件别的事

**AI 服务中途报了 8 次「403 insufficient balance」（余额不足）。** 报错出在帮手身上：工单 01 的帮手断了两次、重试到第三次才成；合并工单 02 的帮手做完合并就断了；规范审查的帮手断了一次。主会话每次都自己重试或者接手，最后做完了。断掉的那几次没有留下半截改动（事后核对的「工作区是干净的」「分支都已合入」可以印证）。

- 这不是这条路径的问题，是这台电脑接的 AI 服务那边的事。第一部分没有出现过。**是余额真的快用完了，还是服务对同时发出的请求有限制，我判断不了**，要用户去服务那边看。（用户 2026-11-17 到服务后台看过：是余额真的不够。）
- 它影响了花费和帮手数：这次派了 11 个帮手（第一部分 10 个），其中 4 个是重试。
- 对工具包的提醒：设计书 7.12 说额度用完时「先暂停，提示稍后再执行」。这次是帮手断、主会话没断，流程命令从外面看不出来。AI 自己重试成功了，但不能指望每次都成。

### 第三部分的结论

1. **不改技能，这条路径也走得通。** 把差异写进任务说明，AI 照办了。设计书 W25 关于这条路径的疑问解决了。
2. 只做了一次。三张很小的工单，Claude Code 一个工具。AI 这次听了任务说明，不等于每次都听；所以事后核对仍然是必须的那道保险。
3. 这次任务说明和项目规则是同时起作用的（项目规则里也有「不要自己建目录」「不要推送」），分不出各自的功劳。工具包里两处都会写。

## 结论

1. **设计书 7.6 的路径走得通。** 经窄接口建目录、本地合并、逐张推送，AI 在自动调用下一次做完，没有越界，事后核对全部符合。
2. **7.6 列的五处差异够用**，没有发现第六处。补丁共七处改动，AI 都照办了。
3. **窄接口可以做得很小**：三种请求，受限侧一头 25 行，特权侧一头 106 行。
4. **wt 可以配本机的远程地址**，不连 GitHub 也能建项目和工作目录。这对工具包的自测有用。
5. **这条路径的隔离确实弱一些**，弱在上面列的三处，都靠事后核对和推送前核对来发现。绕过窄接口建目录，事后核对能发现。
6. **花费**：三张很小的工单加一次审查和修复，共 4.80 美元、7 分半钟。其中审查和修复这一段（13:42:56 到 13:46:36）占了将近一半的时间。
7. **`implement` 的自查约占每张工单花费的六成。** 关掉后这张工单从 2.81 美元降到 1.10 美元。

## 试验中发现、设计书要补的

1. 特权侧清理这条路径的工单分支，要自己核对「已合入功能分支」再强制删除；`wt done` 和 Git 的安全删除都用不了。
2. 任务包里要告诉 AI：提交时那行只读报错是正常的。
3. 特权侧每次启动受限环境前，要先把本功能的分支指针目录建好。
4. 这条路径上，特权侧只在项目根下执行 wt，不到 AI 能写的工单目录里去执行。
5. 工具包给项目装的 wt 准备脚本只链接 `.env`，实测够用；这次项目没有第三方依赖，「依赖由流程命令在受限侧另装」没有试到。
6. `implement-spec` 结尾的代码审查和 `implement` 的自查是同一个技能。用户定了技能保持原样，所以这里也保留。
7. 技能不能改之后，7.6 那五处差异要改用项目规则和任务包里的说明来表达。这次的项目规则里其实已经写了「不要自己建目录，要目录时执行 `sopreq`」「不要推送」这几条，但同时技能原文也改了，分不出是哪一样起的作用。

## 没做的

- 远程是本机的假远程，不是 GitHub。「逐张推送」验证的是特权侧这一头的动作；推送到真的 GitHub 的耗时 S3 测过。
- 功能 PR（F12 开草稿、F18 转正式）没有做，因为没有 GitHub 仓库。S3、S4 分别验证过。
- 事件日志没有接上。特权侧只写了一份自己的日志。
- 探索帮手没有被用到，所以「笔记存到 `.shared/notes/`」没有验证。
- 让 AI 自己去绕过窄接口：没有做，破坏演练是我手工绕的。
- 工单之间有冲突时合并帮手怎么处理：这三张工单没有冲突，没有试到。
- 中途断掉后怎么接着做：没有试。
- 有第三方依赖的项目、要用 Docker 的项目：没有试。
- 更大的规格：只试了三张很小的工单。
- 其他三个 AI 工具走这条路径：没有试。
- 用原样的技能只走了一次（第三部分）。
- `handoff` 的交接文件怎么进仓库、工单怎么带上覆盖行和风险行，这两处「不改技能怎么办」不属于这条路径，没有试。
- 花费对比只做了一张工单、每边一次。
- 独立复查（T9）自己的花费没有测。
- S0 剩下的工单 08、10 仍然没做（09 在对比里做了两遍，都在副本里，没有动 S0 的原项目）。
