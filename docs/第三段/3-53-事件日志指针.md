# 3-53 流程沙箱偶尔停在 T1：`wt` 拉取时撞上写事件日志

2026-11-20。由主控窗口派出的子代理做。没调用 AI，没花钱，没开虚拟机。

**这次动了事件日志的正式代码（`kernel/journal.py`）。** 按交接里的规矩（动了隔离、放行事件、事件日志三处之一，要再开一次独立审查），这一条要告诉用户。

## 原因（坐实了）

本机的裸仓库里有一个指针 `refs/remotes/origin/sop/journal`，记着「远程的事件日志到哪儿了」。改它的有两方：

1. 事件日志自己（`kernel/journal.py`）：取回时 `fetch origin +refs/heads/sop/journal:refs/remotes/origin/sop/journal`；推送成功后 `update-ref`；另外 `git push origin ...` 用 `origin` 这个名字推送时，Git 也会**顺手**更新这个指针。
2. `wt`：`wt new` 等命令里的 `git fetch --all --prune` 按拉取规则 `+refs/heads/*:refs/remotes/origin/*` 把 `refs/remotes/origin/` 下的**所有**指针都更新一遍，包括这一个。

Git 改指针时先记下旧值、改的那一刻核对旧值没变；两边同时改，后改的那边就报 `incorrect old value provided`。事件日志的取回碰到这个报错会重试，`wt` 不会，一次失败流程就停在 T1。

3-52 的判断（事件日志不拿 `gitlock`）方向对，但**只拿锁不够**：

- `git push origin` 顺手改指针这一处不经过 `update-ref`，要锁也得把推送整个锁住；
- 另一个窗口里的 `sop status`、`sop cost` 也会取回事件日志、改这个指针，它们在别的进程里，进程里的锁管不到；
- 把推送锁进 `gitlock` 会让事件日志的推送和合并、推分支互相等，改变了「一个写入线程、合并推送」那一套的节奏。

## 重现

`/tmp/sop-3-53/repro.py`：一个临时裸仓库加一个假远程，用正式的 `Journal` 不停写事件，同时另一边像 `wt` 那样不停 `git fetch --all --prune`。

## 修法（从根上：不再两方改同一个指针）

事件日志不用 `refs/remotes/origin/sop/journal` 了，改用自己的指针 `refs/sop/journal`。`refs/remotes/origin/` 下的东西只归 `wt` 和普通的取回管。改了三处，一共十来行：

- `TRACK` 改成 `refs/sop/journal`；
- 取回加 `--refmap=`（不然 Git 按拉取规则也会顺手改 `refs/remotes/origin/sop/journal`，实测过）；
- 推送（建日志分支和写入线程两处）直接推到 `git remote get-url --push origin` 给出的地址，不用 `origin` 这个名字（用名字推送 Git 会顺手更新那个指针，实测过）。地址按 Git 自己的规则展开（`insteadOf` 也算进去），SSH 复用连接照旧。

**事件日志的做法一点没变**：还是一个进程一个写入线程、每个事件等推上去才往下走、同时排着的合成一次推送、被抢先就取回重来、断网就停下。远程上的分支名、文件放法、守门检查读的地方都没变。旧项目里留着的 `refs/remotes/origin/sop/journal` 不用管，`wt` 拉取时照常更新它，没人再和它抢。

没选的办法：拿 `gitlock`（上面说的三点，不够也更复杂）；T1 碰到这个报错重试（治标，别的拿着 `wt` 拉取的地方，如 `wt done`、`wt sync`，也会碰上）。
