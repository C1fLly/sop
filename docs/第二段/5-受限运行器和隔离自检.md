# 第二段第 5 步：受限运行器、状态目录、隔离自检

2026-11-18。代码在 `runner/`、`kernel/precheck.py`；测试 `tests/unit/test_runner.py`；虚拟机里跑的是 `runner/docker/selftest_docker.py`。

## 做了什么

- `runner/placement.py`：按步骤的种类搭 bubblewrap（6.3 的表），6 种放法：`ticket_impl`、`planning`、`std_draft`、`readonly`、`restricted_script`、`implement_spec`。共同的：系统目录只读；主目录、`/tmp`、`/run` 换成空的；环境变量全部清空，只放回白名单；`.shared/.env` 只读；任务包只读放在 `/sop/task`，结果目录可写放在 `/sop/out`；专用 Docker 的通道（有的话）放在 `/run/sop-docker.sock`。要放进去的程序、运行时、依赖缓存由调用方给（以后由适配器和档案的 `toolchain.toml` 给），运行器里不写死。
- `runner/sandbox.py`：启动。对话步骤（不脱离终端）启动前先查「往终端塞按键」已禁用，没禁用就不启动（6.3 三）。
- `runner/aistate.py`：AI 工具的状态目录（6.3 三）。放在 `~/tools/sop/state/<项目名>/ai-state/<工具>/<会话名>-<序号>/`；全新会话每次从适配器给的模板现建，名字用过就加序号，绝不复用旧的；用完封存成只读。
- `kernel/precheck.py`：特权侧用之前核对（6.4 第四层）。特权侧执行 wt、Git、`gh` 之前调用；特权侧自己改完 `.git/config`（wt new 等会写）之后重新记下指纹。指纹在 `~/tools/sop/state/<项目名>/`，不在项目根下。
- `runner/docker/dockerd_wrap.py`：专用 Docker 的换根脚本。定稿的是审查后试验里的改法版：项目根整个放进去，`.git`、各工作目录里指向 `.git` 的小文件、`.shared`（依赖缓存除外）盖成只读。`runner/docker/start_test.sh` 是测试用的临时启动办法；正式的用户级后台服务、用时才起、资源分组在第三段做（开工时用户同意第二段只做最小版本）。
- 隔离自检分两份：
  - 本机这份 `runner/selftest.py`：在 `/tmp` 下造一个和 wt 一样结构的假项目，对 6 种放法逐项试，和 6.3 的表对照。试写已有的文件只「以追加方式打开、什么都不写」，不改任何东西。
  - 虚拟机里那份 `runner/docker/selftest_docker.py`：见下。

## 结果

### 本机：159 项全部符合

- 机器：往终端塞按键已禁用；仓库的公共配置里没开「工作目录专用配置」的扩展。
- **对照**：受限环境外面确实看得到 `~/.ssh`、钥匙串的通道 `/run/user/1000/bus`、SSH 代理的通道 `/run/user/1000/gcr`、`~/.config/gh`、复用连接的通道目录。所以下面「里面看不到」是有意义的。
- 6 种放法各 23 到 26 项，共 6 组：
  - 都看不到：`~/.ssh`、钥匙串和 SSH 代理的通道、复用连接的通道目录、`~/.config/gh`、`~/tools/sop/state`、机器级配置、别的项目；环境变量里没有密钥和通道。
  - 都改不了：工作目录里指向 `.git` 的小文件、`.git/config`、`.git/hooks`、登记里的 `commondir` 和 `gitdir`、别的工作目录的登记、`.shared/hooks`、`.shared/.env`；都移不动 `main` 的指针。
  - 按种类不同：只有 `ticket_impl` 和 `implement_spec` 提交得了、移得动本功能的工单分支指针；`readonly` 写不了工作目录；`implement_spec` 的 `main` 目录和别的功能的目录只读，本功能的功能分支指针移得动；**它也移得动别的功能的功能分支指针**，这是 7.6 写明的已知弱点（靠推送前核对「是远程的延续」）。
- 状态目录：前一个会话往状态目录里写了一个设置文件（对照：确实写进去了）；用完封存成只读；后一个全新会话读不到它，也看不到前一个的状态目录；现建的不复用旧名字。

### 虚拟机 vm-a：专用 Docker 的 13 项全部符合

用 Docker 官方的 `debian:stable-slim`（带 util-linux 的 `mount`），经本机代理拉的。

| 挂法 | `.shared/hooks/post-create` | `.git/config` | `.git/hooks`（加 `pre-push`） |
|---|---|---|---|
| 普通挂载 | 改不了（只读挡住了），核对照常放行 | 改不了 | 改不了 |
| 不连带底下几层（`bind-recursive=disabled`） | **改成了 → 核对发现并拒绝执行** | **改成了 → 发现并拒绝** | **改成了 → 发现并拒绝** |
| 管理员容器摘掉只读层 | **改成了 → 发现并拒绝** | **改成了 → 发现并拒绝** | **改成了 → 发现并拒绝** |

另外，普通容器和管理员容器把整个根目录挂进去：对照项看得到 `/host/usr`（根目录确实挂进去了），看不到 `~/tools/sop`、`state`、复用连接的通道目录、`/run/user`。

这就是第二段验收里 v0.9 加的那几项：「借专用 Docker 用三种挂法改 `.shared/hooks`、`.git/config`、`.git/hooks` 之后，特权侧『用之前核对』都发现并拒绝执行；复用连接的通道文件、`~/tools/sop/state/` 在受限环境和专用 Docker 里都看不到」。

做完把虚拟机复原了：假项目、`state/sopdk`、这个专用 Docker 的数据（借 rootlesskit 删的）都删了，临时服务停了；demo1、demo2 没动；虚拟机已关。`~/sop-dev`（代码的副本）留在 vm-a 里，第二段结束时删。

## 没做的

- 6.3 那张表要求的「运行项目代码时另外放进去的东西」（JDK、Maven、Node、Compose 插件、依赖缓存映射到各工具习惯的位置）：运行器留了接口（`ro`、`rw`、`env`），具体清单要等第 2a 期的档案 `toolchain.toml`。
- 对话方式的受限环境（不脱离终端）只写了开关和前置检查，没有用真的对话窗口试（Claude Code 适配器是第三段）。
- vm-a 是服务器版云镜像，没有钥匙串和 SSH 代理的通道；这两样只在本机这份自检里验了（本机有）。第三段在桌面版上再跑一遍（第 19 节）。
- vm-a 里没装 bubblewrap，所以受限环境和专用 Docker 接在一起的那一种（受限环境里只给专用 Docker 的通道）没在虚拟机里跑；本机有 bubblewrap，但本机不起专用 Docker（不动这台电脑的 Docker）。两样分开验过，接在一起由 S2、S9 验过。

## 自己出的错

- 第一次在虚拟机里跑，「管理员容器改 `.shared/hooks`」没改成：`.shared` 下面还挂着可写的 `cache`，直接摘 `.shared` 失败。这一项虽然判成「符合」（没改成、核对放行），但验收要的是「改成了之后核对能发现」，等于没验到。改成先摘 `cache` 再摘 `.shared`，第二次改成了，核对发现了。
- `implement_spec` 那一项的说明一开始写成「移动不了别的功能的分支指针」，期望值却是「做得到」（7.6 的已知弱点）。结果没错，说明会误导人，改了。
