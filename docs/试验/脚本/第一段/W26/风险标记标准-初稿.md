# 哪些工单要标风险（初稿，第 1 期第一段，W26）

## 风险标记管什么

规划阶段（F6 拆工单时）给每张工单写一行「风险」。带风险标记的工单：

1. 单独做一次独立复查（T9，约 1.2 到 1.5 美元一次）；没标的跳过 T9，靠写代码的 AI 自查、结果校验、门禁，问题要到整个功能的复查（F16）才被独立地看到。
2. 脚本建议小白逐张验收（F13），而不是整份做完统一验收。

写法：`风险：无`，或 `风险：<类别编号>，<一句大白话说明>`，可以写几个类别。

## 标的标准：命中下面任一条就标

| 编号 | 类别 | 举例 |
|---|---|---|
| R1 | 登录和权限 | 登录、退出、找回密码、会话过期；谁能看、谁能改哪条数据（含「只能看自己公司的数据」）；角色和授权；审计日志 |
| R2 | 钱和数量 | 金额、价格、折扣、税费、余额、积分、库存、工时、请假天数等的计算或累加；四舍五入；对账；按日期跨月跨年拆分的统计 |
| R3 | 数据的结构和去留 | 数据库结构变更（迁移文件）；删除数据、批量修改数据；导入、导出；数据的保留和清理 |
| R4 | 对外的约定和外部服务 | 改接口契约（`contracts/openapi.yaml`）；对外发送（邮件、短信、站内通知、回调）；调用第三方服务（支付、身份、地图等） |
| R5 | 不能撤回的动作 | 提交后不能撤回的业务操作（审批通过、结算、发货）；定时自动执行的任务 |
| R6 | 个人信息 | 处理身份证号、手机号、住址、银行卡等个人信息（产品风险分级 P1 里命中个人信息时） |
| R7 | 同时操作和时间 | 多人同时改同一条数据；排队、抢占、重复提交；跨时区、跨天的时间计算 |
| R8 | 把关本身 | 改已有的测试；改构建配置、检查工具的配置；新增「跳过这个测试」「这一行不检查」的标记 |
| R9 | 修复 | 由验收不通过、功能复查、功能门禁、GitHub 检查失败生成的修复工单，一律标（设计书 7.4） |

拿不准时就标。标多了只多花复查的钱；漏标的代价是问题晚发现。

## 一般不用标的

只改显示的文字和样式；新增只读的、不涉及权限判断的展示页面；纯粹的重构且已有测试全部覆盖（「已有测试全部覆盖」由门禁的覆盖率核对，不靠 AI 说）。注意：看似只读的列表页，如果涉及「谁能看到哪些数据」，属于 R1。

## 谁标、谁审、脚本怎么兜底

- 规划阶段写工单的 AI 按本标准写风险行（规则写在项目规则 `AGENTS.md` 里，本标准随工具包版本走）。
- 规划复查（F9）逐张审风险行标得对不对；漏标的算阻断问题。
- 脚本兜底（T4）：这张工单实际改到了档案声明的敏感位置，即使没标也做 T9。敏感位置由各技术栈档案列出，至少包括：
  - 登录和权限模块所在的目录；
  - 数据库迁移文件的目录；
  - `contracts/openapi.yaml`；
  - 已有的测试文件（被修改或删除）；
  - 构建配置（`pom.xml`、`package.json` 里的脚本和检查设置、`vite.config.*` 等）、检查工具的配置文件；
  - 新增的跳过或不检查标记。
- 紧急修复流程里的工单总是做 T9（设计书 7.5）。

## 预计的比例和花费

一个一般的业务功能，估计三到五成的工单会被标。按一个功能 10 张工单、标 4 张算，逐张复查约 5 到 6 美元。这是推算，第 2a 期按实际比例校正。
