## 做了什么

### 正式的后台服务和分组（`runner/docker/service.py`，新文件）

- 每个项目生成两份用户级登记文件，放在 `~/.config/systemd/user/`：
  - 服务 `sop-docker-<项目名>.service`：放进这个项目的分组；经换根脚本起 `dockerd-rootless.sh`（`DOCKERD` 指向拷到 `~/tools/docker-sop/<项目名>/dockerd-wrap.py` 的换根脚本，项目根、数据目录、程序目录用环境变量给它）；数据、运行目录、通道都在 `~/tools/docker-sop/<项目名>/` 下（`data`、`exec`、`run/docker.sock`）；拉镜像的代理从网络设置取，用环境变量给后台程序；`Delegate=yes`、`KillMode=mixed`（第一段的写法），加了 `Restart=on-failure`。**没有 `[Install]`、不 enable**：用户定的「用时才起、闲了停」，不是登录后自己起来（第一段那样）。
  - 分组 `sop-<项目名>.slice`：`MemoryMax`、`MemorySwapMax=0`、`CPUQuota`（第一段手工加的那三行）。
- **分组名里项目名的「-」写成 `\x2d`**：服务管理器把分组名里的「-」当成上下级，`sop-my-app.slice` 不转写会挂在 `sop-my.slice` 下面，项目 `my` 的上限就把 `my-app` 也算进去了。转写之后所有项目的分组都直接挂在 `sop.slice` 下（虚拟机里看到的路径：`…/user@1000.service/sop.slice/sop-demo\x2dx.slice/sop-docker-demo-x.service`）。
- 两份登记文件都是 0600（代理地址里可能带账号密码）；有变化才写、写了才让服务管理器重读，被手改过就按工具包的重写；写进去的路径只允许字母数字和 `/._+@-`，有空格引号的不写；上限的写法不对不写（防止往登记文件里塞别的行）；项目名长到通道路径超过系统上限时明说。
- 第一版默认上限（没给时）：内存是这台电脑的一半（`50%`），处理器是一半的核、至少 1 核。W8 第 2b 期才定真正的数，按项目怎么配也还没有地方写（见「没做的」）。
- 函数：`install`（只写文件）、`start`（装好、没在跑就起、等它答话，返回通道）、`stop`、`remove`（停掉、删掉两份登记文件，数据不动）。命令行 `python3 -m runner.docker.service install|start|stop|remove <项目名> [项目根] [--memory 300M] [--cpu 100%]`，3-18 做好之前给虚拟机验证用。

### 超内存时专用 Docker 自己也会被杀（拆到 3-54）

内核日志看到的过程：分组超了上限，系统先杀了吃内存的容器进程；紧接着容器的 `containerd-shim` 收尾时又要一点内存，分组还是满的（被杀的进程内存没还完），系统再挑一个杀，这一次挑中了 `dockerd`（它占的约 100 MB 是除容器外最大的，而它和容器进程的「先杀谁」分数一样，都是 200）。

试过的（虚拟机里手工试，没进代码）：

- 容器进程的分数跟着 `dockerd` 的走（把 `dockerd` 的调成 100，容器也是 100），所以单靠调低 `dockerd` 的分数拉不开差距；普通用户也不能把分数调得比起来时低（调到 0 被拒）。
- 换了根的专用 Docker 不管容器的分组（`Cgroup Driver: none`），`--cgroup-parent` 不生效，不能把容器放进一个单独的子分组、只给容器设上限。
- 第一段那一次「专用 Docker 本身没事」是只试了一次，碰巧没挑中它。

可能的改法（留给 3-54 试）：服务起来时分数设高（例如 900）、换根脚本在 `exec dockerd` 之前把自己调成低的，同时让容器默认用高的（Docker 的 `--oom-score-adj` 每个容器能设，但默认值怎么改、免管理员模式下认不认要试）；或者给服务本身留一块不被挤占的内存（`MemoryMin`/`MemoryLow`，要看分组下的子分组怎么算）；或者接受、只靠 `Restart=on-failure` 拉起来并在设计书里写明代价（同一项目在跑的别的容器跟着停）。

## 没做的

- **超内存时专用 Docker 自己也会被杀**：见上，拆成 **3-54**。
- **每个项目的上限从哪来**：现在 `start()` 收一个上限参数，没给就用默认（内存一半、一半的核）。项目在哪声明自己的上限（`sop.json`？技术栈档案？）设计书没写，W8 第 2b 期定数。调用 `start()` 的地方是 3-18（`sop` 用时才起），那时一起定从哪取；没另拆任务。
- **还没有任何流程命令调用它**：受限运行器把专用 Docker 的通道放进受限环境（`placement.py` 的 `docker_sock`）早就有，但谁在什么时候起、给哪条通道，是 3-18 的事。
- 本机没真跑（会建 systemd 用户服务、起专用 Docker）。
- 用户级服务在最后一个登录会话结束时会停（虚拟机里 SSH 断开后专用 Docker 跟着没了，设计书 6.3 二已写；不开 linger）。用时才起的话这不碍事，3-18 要知道。
- 两个项目同时开是 3-19；桌面版上跑自检是 3-38。

## 和设计书的出入（留给 3-48 并入）

1. **分组的真名是 `sop-<项目名里的「-」写成 \x2d>.slice`**（例如 `sop-my\x2dapp.slice`），所有项目的分组挂在 `sop.slice` 下。6.3 二写的是 `sop-<项目名>.slice`。
2. **超内存时「专用 Docker 本身没事」不总成立**（6.3 二、5 期表那一行「各试了一次」）：6 次里 1 到 2 次专用 Docker 也被杀，服务管理器几秒后拉起来，同一项目里在跑的别的容器跟着停。等 3-54 的结论再改。6.5「一个项目里某张工单的测试吃光了这个项目的额度……」那一条可以补上这一点。
3. **服务不 enable、没有 `[Install]`**（用户定的用时才起）；加了 `Restart=on-failure`。
4. **两份登记文件 0600**（代理里可能带账号密码）；登记文件由工具包按项目生成、有变化才写，被手改过下次起时重写。
5. **默认上限**：内存一半、一半的核（至少 1 核），不用交换区。设计书没写数（W8）。
6. **隔离自检里专用 Docker 那份用正式服务起**，项目名 `sopdk`，跑完删掉两份登记文件（3-11 的出入第 1 条可以合进来）。
7. 改上限只要重写分组文件、让服务管理器重读，不用重启专用 Docker（虚拟机里看到当场生效）。

## 自己出的错

1. 第一遍虚拟机：「没设成登录后自己起来」我用 `! systemctl is-enabled` 判，没有 `[Install]` 的服务回答是 `static`、退出码 0，判成了「不对」。改成看回答是不是 `static`。
2. 第一遍处理器上限那一步量出来 0.01 秒：前一步专用 Docker 被杀了还没拉起来，容器根本没起；我又没等它答话就接着跑。加了「先等它答话」，并把忙的量加大五倍（原来 0.5 秒左右，误差占比太大）。第二遍 1.11 对 0.49 没过「慢 2.5 倍」的线，改成「至少慢一倍」，量加大后是 5.2 对 1.6。
3. 第一遍把「超内存时专用 Docker 自己也被杀」当成偶发，花了几轮手工试才看清是规律性的（内核日志里每次都是 `containerd-shim` 收尾时触发第二次）。
4. 中途手工试的时候，一次 SSH 会话结束后专用 Docker 跟着停了（用户级服务在最后一个会话结束时停），下一条命令连不上，误以为出了别的问题。
5. 起不来时去读系统日志的那一段原来在「没装 Docker」时也会跑；单元测试里那样会在本机跑一次 `journalctl --user`（只读，没改东西），改成没装 Docker 就直接明说、不读日志。
6. 把 `_proxy` 起成了下划线开头又在别的文件里用，改成了 `proxy`。
