# 试验 S4：GitHub 这一头

状态：已完成（2026-11-17）。用户已亲手在网页上点了合并，他的反馈是「都能找到，分得清」。**两个试验仓库已按用户的指示删除**（见末尾）。没做的部分列在末尾。

没有调用 AI，没有花钱。用了 GitHub 的免费额度（私有仓库上跑了 25 个检查任务，每个 5 到 13 秒）。

**在用户的 GitHub 账号下新建了一个公开的试验仓库 `C1fLly/sop-spike-s4-public-test`**（用户事先同意）。里面全部是假内容：一个说明文件、一个两行的文本文件、几份只会打印文字的检查流程。两个试验仓库都没有删。

放到 GitHub 上的「密钥」是两个一看就是假的字符串（`FAKE-NOT-A-REAL-KEY-sop-spike-s4-…`），没有放任何真的密钥。

没有碰 `~/Project`、`~/tools/wt`、`~/999_`。本机的工作目录在 `/tmp/sop-spike-s4/` 下。

## 要验证什么

设计书第 19 节的五项，加上 S6 留下的两项，共七项：

1. 功能 PR 和工单 PR 的检查定义各取自哪里。
2. PR 里的代码读不读得到部署用的密钥。
3. 一个功能消耗多少免费时长。
4. 公开仓库的分支保护。
5. 私有仓库手动点合并的体验。
6. 往日志分支 `sop/journal` 推送是否不触发检查。
7. GitHub 上谁能往日志分支推送、要不要加保护。

## 先说两个名词

GitHub 上「PR 来了就自动跑检查」有两种触发方式，这次试验的关键就在它们的区别：

- **普通触发**（GitHub 里叫 `pull_request`）：可以运行 PR 里的代码。
- **守门触发**（GitHub 里叫 `pull_request_target`）：按主线上的定义运行，适合做不运行 PR 代码的检查。

## 做了什么

两个仓库：

| 仓库 | 公开还是私有 | 用来试什么 |
|---|---|---|
| `C1fLly/sop-spike-s3`（S3 留下的） | 私有 | 第 1、2、3、5、6 项，第 7 项的私有部分 |
| `C1fLly/sop-spike-s4-public-test`（新建） | 公开 | 第 4 项，第 7 项的公开部分，第 1、2 项各复核一次 |

每个仓库的主线上放了三份检查流程（副本在 `docs/试验/脚本/S4/`）：

- 项目检查：普通触发。打印「我是哪个版本的定义」，试读假密钥，再运行仓库里的一个检查脚本（仓库里有 `BROKEN` 文件就不通过）。
- 守门检查：守门触发。打印「我是哪个版本的定义」，试读假密钥；公开仓库上的那一份还会查这个 PR 有没有改检查流程和检查脚本，改了就不通过。它不取出、不运行 PR 里的代码。
- 部署：只在主线有新内容时跑，只打印文字、试读假密钥，不部署任何东西。

假密钥放了两处：一个是仓库级的；一个放在名叫 `production` 的「部署环境」里，并给这个环境加了一条规则「只有 `main` 分支能用」。

## 结果

### 第 1 项：检查定义取自哪里

| 情形 | 普通触发 | 守门触发 |
|---|---|---|
| 功能 PR（目标是 `main`），没改检查定义 | 跑的是 PR 合并后的那一份（内容与主线相同） | 跑的是主线上的那一份 |
| 工单 PR（目标是功能分支），**PR 自己改了检查定义** | **跑的是 PR 改过的那一份** | 跑的是主线上的那一份 |
| 上面那张工单合入功能分支之后的功能 PR | **跑的是改过的那一份** | 跑的是主线上的那一份 |
| 工单 PR 的目标（功能分支）上的定义已被改，再来一张新的工单 PR | 跑的是改过的那一份 | **仍然是主线上的那一份**，不是功能分支上的 |
| PR 和目标分支有冲突 | **不跑** | 照跑 |

依据是每次运行自己打印的「定义来源」：普通触发显示来源是 `refs/pull/<PR号>/merge`，守门触发显示来源是 `refs/heads/main`。

结论：

- **设计书 6.4 说「功能 PR 上的检查，定义取自主线」，在普通触发下不成立。** 普通触发下，PR 可以把检查改成永远通过，跑出来的就是它改过的版本。
- **守门触发的定义永远取自主线**，功能 PR 和工单 PR 都是。PR 改不了它。
- 所以要用两个检查配合：项目检查（普通触发，运行代码）加守门检查（守门触发，不运行 PR 的代码，只查 PR 有没有动受保护路径）。两个都通过才算通过。第 4 项实测了这个配合挡得住。
- 有冲突的 PR 上项目检查根本不会跑。流程命令在 T12 等检查之前，要先确认 PR 没有冲突，否则会一直等下去。

### 第 2 项：PR 里的代码读不读得到部署密钥

| 谁在读 | 仓库级的假密钥 | 部署环境里的假密钥（限定只有 `main` 能用） |
|---|---|---|
| 主线上的部署流程 | 读得到 | 读得到 |
| 功能 PR 上的项目检查 | **读得到** | — |
| 工单 PR 上的项目检查 | **读得到** | — |
| 守门检查 | 读得到 | — |
| 工单 PR 把检查改了，加一个任务声明要用部署环境 | — | **读不到。任务没有启动就被拒绝** |
| 工单分支里加一份「一推送就跑、声明要用部署环境」的流程 | — | **读不到。任务没有启动就被拒绝** |

被拒绝时 GitHub 给出的原因：`Branch "refs/pull/5/merge" is not allowed to deploy to production due to environment protection rules.`（这个分支不允许使用 production 环境）。

「读得到」的判断办法：检查流程打印密钥的长度和指纹的前 12 位，和本机算出来的一致；GitHub 会自动把日志里的密钥原文遮住。

结论：

- **仓库级的密钥，PR 里的代码读得到。** 同一个仓库里的分支开的 PR，GitHub 照常把仓库级密钥给它。设计书 6.4 写的「存在 GitHub 上的线上密钥只供主线上的部署流程使用，PR 里的代码读不到」，如果密钥放在仓库级就**不成立**。
- **放进部署环境并限定只有 `main` 能用，就成立了。** PR 上的任务、分支上的任务都被拒在门外。
- **这条限制在私有仓库的免费计划上也能设、也生效**（实测）。公开仓库同样。
- 所以设计要写明：线上密钥一律放在部署环境里，环境限定只有 `main`；仓库级不放任何密钥。项目初始化时由脚本建好这个环境和这条规则。

### 第 3 项：一个功能消耗多少免费时长

这一项只量出了**次数**，没量出真实的分钟数。原因：试验里的检查是空壳，每个任务只跑 5 到 13 秒；真实项目的检查要跑多久，要等有了真实的技术栈档案才知道（第 2a 期）。

实测的次数（私有仓库，功能 d，一张工单）：

| 动作 | 触发的任务 |
|---|---|
| 开功能 PR（草稿） | 项目检查的快档、守门检查，各 1 次。全档被跳过 |
| 开工单 PR | 快档、守门，各 1 次。全档被跳过 |
| 工单 PR 合入功能分支 | 功能 PR 上的快档、守门，各再跑 1 次。全档仍被跳过 |
| 功能 PR 转正式 | 快档 1 次、**全档 1 次** |
| 功能 PR 合入主线 | 部署 1 次 |

由此得出一个功能的任务数（N 是工单数，每张工单平均推送 p 次）：

- 工单 PR 上：N × p × 2
- 功能 PR 草稿期间：(N + 1) × 2
- 转正式：2（其中 1 个是全档）
- 合入主线：1

例：10 张工单、每张推送 1.5 次，约 55 个任务，其中只有 1 个是全档。

两点实测到的省时长办法：

- **全档只在「目标是 `main` 且已转正式」的 PR 上跑**，这个条件可以写在检查定义里，实测有效：草稿期间和工单 PR 上全档都显示「跳过」，跳过的任务不计时长。
- **每合入一张工单，功能 PR 上的检查就会重跑一遍。** 10 张工单就是 11 遍。如果让草稿期间的功能 PR 连快档也跳过，这部分可以省掉。要不要这样做留给第 1 期定。

计费规则，读的是 GitHub 官方文档（经网页摘要工具读取，不是逐字原文）：

- 公开仓库用标准机器跑检查不计费：「GitHub Actions usage is free for standard GitHub-hosted runners in public repositories」。
- 私有仓库：免费计划每月含一笔额度。页面上写的是金额而不是分钟数：免费计划每月 12 美元，Linux 2 核机器每分钟 0.006 美元。折算下来约 2000 分钟（这个折算是我算的）。
- 额度用完又没绑付款方式时，检查停用，不会扣钱：「usage is blocked once you consume the included compute usage」。
- 「每个任务不足一分钟按一分钟算」这条规则，在读到的两个页面里都没有找到。**没核实。** 如果成立，上面的 55 个任务最少就是 55 分钟。

这次试验实际消耗：私有仓库 31 个任务，其中 3 个被跳过、3 个被环境规则拒绝没启动、25 个真的跑了，实际运行时间合计 116 秒。按「不足一分钟算一分钟」算是 25 分钟。**账号上到底扣了多少我查不到**：查用量的接口要一项现有登录凭据没有的权限（`user`），我没有去申请。

### 第 4 项：公开仓库的分支保护

给公开仓库的 `main` 开了保护：必须走 PR；必须通过「快档」和「守门」两项检查；对管理员同样生效；禁止强制推送和删除。全部是用脚本设的。

| 尝试 | 结果 |
|---|---|
| 直接往 `main` 推送 | 被拒：`Protected branch update failed` |
| 用脚本合并检查是红色的 PR | 被拒：`the base branch policy prohibits the merge` |
| 加上管理员开关强行合并红色 PR | 被拒：`Required status check "fast" is failing` |
| 用脚本合并检查全绿的 PR | 成功 |
| **PR 把项目检查改成永远通过，同时带一个本该不通过的文件** | 项目检查变绿了（它跑的是 PR 改过的版本），但守门检查是红的（发现 PR 动了检查流程）。**合不进去** |
| **上一条再升级：PR 里另加一个也叫「守门」的假任务，永远通过** | 页面上出现一红一绿两个同名检查。**合不进去** |
| 让那个假的同名任务晚一点再跑一遍，成为最新的结果 | 仍然合不进去 |

结论：

- **公开仓库的分支保护在免费计划上可用，脚本能设，对管理员也生效。** 设计书 6.4 第三层在公开仓库上成立。
- **但前提是有守门检查。** 只靠普通触发的项目检查，PR 自己改一下定义就能变绿。
- 每项必须通过的检查，名字要在所有检查流程里唯一。官方文档也这样要求（经摘要工具读取）：「make sure that job names are unique across all workflows」。
- 特权侧手里的登录凭据是仓库主人的，它能把保护关掉。这在设计里是允许的（特权侧是可信的那一侧），但要写明。这一点是按权限推出来的，没有真的去关一次。
- 只有一个账号，没法要求「必须有另一个人批准」，所以批准人数设的是 0。

### 第 5 项：私有仓库手动点合并

**用户已亲手点了。** 2026-11-17 18:50（北京时间），他在网页上把全绿的 PR #8 合进了主线。合并 3 秒后主线上的「部署」流程自动跑了一次，读到了仓库级和部署环境里的两个假密钥，和设计一致：只有主线上的部署流程读得到部署环境里的密钥。

事后问他感受，他的回答是：**都能找到，分得清**（按钮找得到，绿和红分得清）。「红色的时候按钮照样点得动，靠手册里写一条硬规矩够不够」这一问他没有单独回答。

另外测到的事实：

- 私有仓库的免费计划上，分支保护用不了。接口的回答是：`Upgrade to GitHub Pro or make this repository public to enable this feature.`
- **私有仓库上，检查是红色的 PR，脚本照样能合并**（实测：把一张检查不通过的工单 PR 合进了功能分支，成功）。GitHub 这一头没有任何东西拦。
- 所以私有仓库上「只在全绿时合并」完全靠两样：合入主线靠用户在网页上看颜色；脚本合并工单 PR（T13）之前，流程命令自己必须先查检查结果。后一条设计书已经有（T12），这次确认了它是唯一的防线。

### 第 6 项：往日志分支推送是否不触发检查

| 做法 | 结果 |
|---|---|
| 私有仓库：主线上放一份「不限分支、一推送就跑」的流程，再往 `sop/journal` 推送一个事件 | 没有触发任何检查。推送前后运行总数都是 2 |
| 公开仓库：往 `sop/journal` 推送两个事件 | 这两个提交上的检查数是 0 |

原因：GitHub 按「被推送的那条分支上有没有检查流程文件」来决定跑不跑。日志分支上只有事件文件，没有检查流程，所以怎么推都不跑。

结论：**设计书 8.2「往这条分支推送不触发 GitHub 上的检查」成立。** 前提是日志分支上永远不出现检查流程文件。日志是特权侧写的，只写事件文件，这个前提由设计保证；稳妥起见，回放时可以顺带核对日志分支上没有别的文件。

### 第 7 项：谁能往日志分支推送，要不要加保护

- 两个仓库上有写权限的都只有仓库主人一个账号（接口查到的）。别人推不了。
- **公开仓库：可以给日志分支加保护，而且不妨碍正常写入。** 实测：只开「禁止强制推送、禁止删除、对管理员同样生效」，不要求走 PR、不要求检查。之后正常追加事件成功；改写历史被拒；删除分支被拒。
- **私有仓库（免费计划）：加不了保护。** 只能靠本机这一头：受限侧拿不到凭据（S2）、改不了本机的日志分支指针（S6 补测）；特权侧每步开始前核对历史是延续的（设计书 6.4 第四层）。
- 「只允许指定的人推送」这种限制，官方文档说只有组织名下的仓库才有（经摘要工具读取）。个人账号下的仓库用不了，也用不着，因为本来就只有主人能推。

结论：**公开仓库的项目，初始化时给 `sop/journal` 加上这条保护**；私有仓库不加，如实写明靠本机隔离和事后核对。

## 结论

1. **设计书 6.4 有两处要改，都是这次试验推翻的：**
   - 「检查的定义取自主线」只对守门触发成立。要改成两个检查配合。
   - 「PR 里的代码读不到线上密钥」只对「部署环境里、限定只有 `main` 能用」的密钥成立。仓库级的密钥 PR 读得到。
2. 公开仓库的分支保护成立，脚本能设，对管理员也生效。
3. 私有仓库没有任何东西拦住红色 PR 被合并，全靠流程命令自己查和用户看颜色。
4. 往日志分支推送不触发检查；公开仓库可以给它加保护而不影响写入。
5. 全档检查可以限定只在转正式的功能 PR 上跑，实测有效。

## 试验中发现、设计书要补的

1. **守门检查会拦住一切改动受保护路径的 PR**，包括工具包升级、规范变更这两个本来就要改它们的专门流程（设计书 7.11）。这两个流程怎么让守门检查放行，这次没有试。可行的方向：专门流程用特定的分支名，守门检查只对这种分支名放行；受限侧不能推送，所以造不出这种分支。留到第 1 期定。
2. 有冲突的 PR 上项目检查不跑。T12 要先看 PR 有没有冲突。
3. 每合入一张工单，功能 PR 上的检查就重跑一遍。
4. 公开仓库意味着任何人都看得到代码、检查日志和日志分支上的事件（里面有花费、步骤、确认记录）。这是选公开还是私有（W3）时要告诉用户的。
5. 公开仓库上陌生人可以从自己的副本开 PR。守门检查不运行 PR 的代码，所以这本身是安全的；但守门检查里永远不能加「取出并运行 PR 代码」的步骤。官方文档有同样的警告（经摘要工具读取）：「Avoid using this event if you need to build or run code from the pull request.」
6. 特权侧的登录凭据不含修改检查流程文件所需的那项权限（`workflow`）。这次能把检查流程推上去，是因为推送走的是 SSH。记下来备查。
