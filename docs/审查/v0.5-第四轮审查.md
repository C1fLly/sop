审查日期：2026-11-17。审查对象：`docs/设计书.md`（v0.5，1788 行，从头读到附录 D）。

我没有修改任何已有文件，只新建了本文件。没有调用任何要花钱的 AI 工具，没有在 GitHub 上建、改、删任何东西，没有用 sudo，没有改动你的 Docker（只执行过一次只读的查询），没有碰 `~/Project`、`~/999_`，`~/tools/wt` 只读。没有读 `docs/交接.md` 和 `docs/历史/`。没有打开密钥文件，没有读任何 AI 会话记录的内容（只看过试验留下的状态目录里有哪些文件夹、数过文件个数）。

每条判断后面的括号是依据，共三种：

- **读了原文**：设计书、试验记录和脚本、上一轮审查报告、技能原文、wt 的说明书和脚本、工具的帮助说明。
- **自己验证过**：我在 `/tmp/sop-review-v05/` 下亲手做了一遍，或在本机只读地查了一下。
- **推断**：按道理推出来的，没有实测。

先解释几个绕不开的词：

- **PR**：合并申请。把一条分支的改动并入另一条分支之前，在 GitHub 上开的单子。
- **主线**：`main` 分支，正式代码所在的那条线。
- **功能分支、工单分支**：一个功能一条分支；功能拆成的每张工单再各有一条分支，做完并回功能分支。
- **特权侧、受限侧**：拿着 GitHub 登录凭据的流程命令 `sop` 本身；被关在小范围里、读不到凭据的 AI 和项目代码。
- **受保护路径**：决定把关松紧的那些文件（检查规则、技能文件、项目声明、页面基准截图等），普通步骤不许改。
- **守门检查**：GitHub 上的一道检查，规则永远取自主线，专门查「这个 PR 有没有动受保护路径」。
- **放行事件**：v0.5 新加的做法。正当要改受保护路径时，特权侧在日志分支上记一笔「这个提交我放行」，守门检查看到这一笔才放过。
- **压成一次提交的合并**：合并 PR 时，GitHub 把这条分支上的所有提交压成一个**新的**提交放到目标分支上。新提交的编号和原来的都不一样。
- **专用 Docker**：每个项目另起的一个只给受限侧用的 Docker，和你原来的 Docker 互不相干。
- **免管理员的 Docker**：不需要管理员权限就能运行的那种装法（设计书里叫 rootless）。

## 一、总评

**这份设计到了什么程度。** v0.5 比 v0.4 又扎实了一截。上一轮的 3 条严重问题：一条靠补做试验 S9 真解决了（以最小的例子为限）；另两条有了方案，但方案本身各有一处走不通。16 条一般问题里，10 条改到位了（其中几条还只是纸面上改了、没有试），5 条部分解决，剩下 1 条（第 3 条，含六个小项）五项改了、一项如实列为未决。试验记录总体诚实，设计书引用它们时比上一版克制，没有发现把「没试」写成「试过」的。

它仍然是一份**大部分只在纸面上成立**的设计。14 条要求里，能说「做到了」的仍只有 2 条（第 3 条 wt、第 13 条不改技能），9 条是「纸面成立、还没验证」，2 条没做到（第 6 条多端、第 11 条上线运维，都是你自己决定推后的），第 14 条有了设计但你举的那个例子（Docker）按现在的写法走不通。

**最要紧的五件事：**

1. **放行事件按「提交编号」放行，而仓库只允许「压成一次提交的合并」，这两样对不上，不用等试验就推得出来。** 你逐张验收存下的截图，提交在工单分支上；工单并回功能分支时被压成一个新编号的提交，原来那条放行事件就对不上了，功能 PR 上守门检查一定是红的。设计书把它写成「还没验证」，实际是「按现在的写法不通」。写的退路也走不通。（严重 1）
2. **环境迁移里 Docker 那一行，只对一种情况成立，而且不是最常见的那种。**「停掉后把整个数据目录复制过去」只适用于「原来就是免管理员的装法、只是位置不同」。新电脑上最常见的是用系统自带方式装的、需要管理员的那种，它的数据不能这样搬。另外设计书没有规定 Docker 的数据「应该在哪」，迁移没有目标。还有一处没说清的代价：SOP 自己根本不用你原来 Docker 里的数据，风险最大的这一行换来的只是位置整齐。（严重 2）
3. **v0.5 有三处改动没有改到底。** 上一轮查出的隔离漏洞在普通路径上堵住了（我亲手重做了，确实改不动），但「原样运行 `implement-spec`」那条路径上没跟着堵；「进行中的功能钉住旧版本」在 GitHub 那一头不成立；受限环境只写了「做工单」这一种步骤怎么放，功能级的 AI 步骤（追问、原型、规格、工单）怎么放、谁来提交没有写。（一般 1、2、3）
4. **还有几处 AI 能走捷径的口子。** 最值得注意的一处是新发现的：每个项目给 AI 工具的那个「状态目录」是整个可写的，而且所有步骤共用，里面除了会话还有 AI 工具的设置和记忆。写代码的那个会话可以在里面留话，被之后「全新会话」的复查读到，而步骤结束后没有任何东西检查这个目录。（一般 8）
5. **第 1 期的正式编码现在还不能开工，但离开工不远。** 先在纸面上改掉第八节列的 6 处，再做设计书自己列的那五个开头试验，试验通过后才写正式代码。第 1 期本身偏大，建议拆开。

另外，做一个功能的花费，设计书现在给出了合计（约 21 到 41 美元，不含修复）。算术和出处我都核对了，对得上；但口径是玩具项目，缺几项，也没有整个项目的量级。（一般 10）

## 三、确定的问题

### 严重

**严重 1. 放行事件按提交编号放行，和「只允许压成一次提交的合并」对不上；退路也走不通**

- 位置：6.4 第三层、5.6、7.2 的 I2 和 I7、7.5 的 T11 和 T13、第 20 节 W21。
- 原文：
  - 6.4：「由特权侧在改动提交之后往日志分支写一条放行事件，记下那个提交的编号和它改了哪些受保护路径」「PR 里每一个动了受保护路径的提交，都要有一条对得上的放行事件，否则不通过」。
  - 7.2 的 I2：「它同时设置只允许压成一次提交的合并、合并后删分支」。
  - 7.5 的 T11：「通过时更新视觉基准并提交」；T13：「合并工单 PR」。
  - 6.4：「放行事件这个做法……还没有验证：……压成一次提交合并之后还对不对得上，要在第 1 期开头用一个试验仓库试」「试不成的退路是：受保护路径的改动一律单独开一个 PR，由小白在网页上点合并」。
- 问题：
  - **对不上是推得出来的。** 过程是这样：你逐张验收通过，截图提交在工单分支上（设它的编号是甲，特权侧给甲写了放行事件）。工单 PR 并回功能分支时，GitHub 把它压成一个新提交（编号乙），截图的改动现在在乙里。真正算数的是功能 PR 上的守门检查，它看到的「动了受保护路径的提交」是乙，日志里只有甲的放行事件。结果：红。wt 的脚本里确实把仓库设成了只允许这一种合并（读了 `~/tools/wt/wt` 第 571 到 573 行；S3 记录也这样写）。受影响的正是第 2a 期第二步要走的路：带页面、逐张验收。（前半是读了原文，结论是推断；我不能建 GitHub 仓库，所以没有实测）
  - **先后顺序也有问题。** 乙的编号在合并之前不存在。合并那一下 GitHub 立刻在功能 PR 上重跑检查，这时不可能已经有乙的放行事件。要想通过，只能事后由特权侧补写一条、再让检查重跑一遍。谁补、补之前核对什么、怎么触发重跑，设计书都没写。（推断）
  - **「对得上」是什么意思没有定义。** 只对提交编号，还是连改了哪些路径也要对？一个提交既改了截图又改了检查规则怎么办？特权侧写放行事件之前要核对什么（例如「这个提交只动了截图目录下的图片」），四种情形没有一种写了。6.5 说「特权侧如果有错，守门检查拦不住」，那么特权侧按什么规则不出错就是关键，现在是空的。（读了原文）
  - **退路走不通。** 公开仓库上分支保护「对管理员同样生效」（I6），守门检查是红的 PR 在网页上也点不动（S4 记录：加上管理员开关强行合并红色 PR，被拒）。截图也没法「单独开一个 PR」进主线：它对应的代码还在功能分支上没合并。再者，一个受保护路径的改动正不正当，你判断不了。（读了原文；后两句是推断）
  - **I7 没有验证放行这条路。** 新项目建好时验三个试验 PR：出错的、改了检查定义的、正常的。没有「改了受保护路径并且带放行事件的，应当通过」这一种。（读了原文）
- 后果：公开仓库上，第一个带页面、逐张验收的功能合不进主线。私有仓库上，功能 PR 的守门检查是红的，而手册的硬规矩是「只在全绿时点」。
- 建议：
  - 放行不要按提交编号，改成按「路径加文件内容的指纹」。指纹是 Git 给每一份文件内容算出来的编号，内容一样指纹就一样，和它在哪个提交里无关。特权侧放行的是「这个路径上的这一份内容」；守门检查比的是这个 PR 相对主线最终多出来的改动里，每个受保护路径上的文件指纹是不是都在放行名单里。这样压成一次提交、合并提交都不影响。
  - 四种情形各写一条：特权侧写放行事件之前核对什么。
  - 写明顺序：先写放行事件，再推送；检查已经先跑了的，由特权侧触发重跑。
  - 退路重写。I7 加第四个试验 PR。
  - W21 的试验按改后的做法试，并明确包含这几项：工单 PR 压合之后功能 PR 仍然是绿的；解决冲突产生的合并提交；日志分支上有几千个事件时读一次要多久。

**严重 2. 环境迁移里 Docker 那一行只对一种情况成立；数据该搬到哪没有规定；最大的风险换来的东西 SOP 自己用不上**

- 位置：4.8 的「各样东西怎么搬」表、4.3、第 19 节第 1 期的验收标准。
- 原文：
  - 4.8：「Docker 的数据（镜像、数据卷、容器）｜停掉 Docker 后整个数据目录复制到新位置，再启动核对：镜像数、数据卷数、每个数据卷的文件数与搬之前一致」。
  - 4.3：「Docker（rootless）｜`~/tools/docker`」。
  - 4.8：「小白逐样选择搬还是不搬；不搬的那样，机器体检仍不通过」。
  - 第 1 期：「先装一个位置不对的 Docker、放几个镜像和一个有数据的数据卷，迁移后数量和内容一致」。
- 问题：
  - **数据该在哪，没有规定。** 4.3 只规定了程序的位置。这台电脑上数据实际在 `~/tools/docker/data`（自己验证过：只读地查了一下 Docker 的信息），但设计书没写。没有规定，体检就没法判断数据的位置符不符合，「复制到新位置」也没有目标。
  - **电脑上原来是哪一种 Docker，没有分。** 常见的有四种：一、用系统自带方式装的、需要管理员的（最常见，数据在系统目录里）；二、snap 版；三、Docker Desktop（数据在它自己的虚拟机里）；四、已经是免管理员的装法，只是在默认位置。「停掉后整个目录复制」只对第四种成立。第一种：停它就要管理员密码；它的数据文件属于系统管理员，原样复制过来，免管理员的 Docker 用不了（两种装法下文件归谁所有的记法不一样）。稳妥的做法是镜像导出再导入、数据卷一个一个打包再还原、容器不搬而是重建。设计书在专用 Docker 那里用的正是导出再导入。（推断，依据是 Docker 的工作方式；没有实测）
  - **即使是第四种，普通的复制也复制不全。** 免管理员的 Docker 里，容器内部的非管理员账号写出来的文件（比如数据库的数据目录），在外面属于一段「附属用户号」，你自己的账号读不了。要借 Docker 自己的身份进去复制，或者用管理员权限。「核对每个数据卷的文件数」同理。（推断）
  - **验收只测了一种。** 第 1 期的验收只说「装一个位置不对的 Docker」，没说哪一种。
  - **没说清的代价（这是你的决定带来的）。** SOP 自己不用你原来 Docker 里的数据：受限侧只用专用 Docker（6.2 写明「碰不到用户原来的 Docker」），验收环境也在受限侧。SOP 需要的只是 `~/tools/docker` 下的那份程序。所以风险标为「大」的这一行，换来的只是位置整齐，不是 SOP 能不能用。而 4.8 又规定「不搬的那样，机器体检仍不通过」，等于不敢搬数据的人就用不了 SOP。你的第 14 条写的是「可以进行环境迁移」，设计把它做成了「必须迁移」。（读了原文）
- 后果：你举的例子正是 Docker。新电脑上最可能碰到的是第一种，按现在的写法，要么做不了，要么搬过去用不了。
- 建议：
  - 4.3 补上数据的规定位置。
  - 4.8 按四种情况分别写做法，第一到第三种用「镜像导出导入、数据卷逐个打包还原、容器重建」。
  - 请你定一件事（见第四节疑问 1）：是否接受「只在规定位置装一份程序，旧的 Docker 和它的数据原地不动，也算合格」。这样风险最大的一步可以不做。
  - 第 1 期的验收至少测第一种和第四种。

### 一般

**一般 1.「原样运行 `implement-spec`」那条路径，没有跟上隔离漏洞的修补**

- 位置：7.6、6.3、试验脚本 `S7/s7env.sh`。
- 原文：
  - 6.3：「`commondir` 和 `gitdir` 两个文件再单独设成只读……上面三个小文件必须全部锁死，这是 wt 能安全执行的前提」。
  - 7.6：「再把 `.git`（只放开提交内容、各工作目录的登记、本功能的工单分支指针、功能分支指针）……盖成只读」「运行中才建的工单目录里指向 `.git` 的小文件设不成只读」。
- 问题：上一轮查出的漏洞是：受限侧能改掉一个告诉 Git「仓库在哪」的小文件，之后特权侧在那个目录里执行 Git 会读到假仓库的配置。v0.5 在普通路径上堵住了，我亲手重做了一遍，锁住后确实改不动、提交照常（自己验证过，见第五节）。但 7.6 的路径里「各工作目录的登记」是整个放开的，其中就有**功能目录**的那个小文件。功能目录在这条路径开始之前就存在，之后特权侧还要在里面做事（功能门禁、转正式、清理）。7.6 只提了「运行中才建的工单目录」，没提功能目录；事后核对的清单里也没有「这几个小文件没被改过」。S7 的脚本里只把 `main` 目录的登记盖成了只读，功能目录的没有。（读了原文和脚本；后果是推断）
- 另外，7.6 这一版新加的两条（别的工作目录盖成只读；每次「报告已合入」时比对已确认内容）是纸面上加的，S7 的脚本里没有，没有试过。设计书没有标出来。
- 建议：7.6 写明功能目录、`main` 目录的登记里那两个小文件一样锁死；运行中才建的目录，结束后由特权侧核对这两个小文件的内容是否符合预期，再去碰它。

**一般 2.「进行中的功能钉住旧版本」，在 GitHub 那一头不成立；启动器怎么找版本也没跟着改**

- 位置：7.11、6.4、3.2。
- 原文：
  - 7.11：「这个功能从头到尾用这一个版本的流程定义和检查……`sop.json` 里新的版本声明只对之后新开的功能生效」。
  - 6.4：「项目检查用到的检查脚本，按主线上 `sop.json` 声明的版本从公开的工具包仓库拉取」。
  - 3.2：「启动器：按项目声明的版本找到对应目录并执行」。
- 问题：升级的 PR 合进主线之后，主线上的 `sop.json` 就是新版本了。进行中的功能在本机按旧版本跑检查，在 GitHub 上却按主线声明的新版本拉检查脚本。两边用的不是同一套，「从头到尾用这一个版本的检查」只在本机成立。结果可能是本机绿、GitHub 红，流程走到 F19 的那条规则：「说明本机和 GitHub 的环境有差别……流程停下」。另外 3.2 的启动器是按 `sop.json` 找版本的，没有改成「按这个功能开轮时记下的版本」。（读了原文；后果是推断）

**一般 3. 功能级的 AI 步骤，受限环境怎么放、谁来提交，没有写，也没有试**

- 位置：6.3 第一点、7.3 的 P5 到 P9、7.4 的 F2、F3、F5、F6、F8、F11。
- 原文：6.3：「`.git` 整个只读，只放开四处可写：提交内容、本工作目录的登记、本功能的工单分支指针、对应的指针变更记录」。
- 问题：这四处是按「做一张工单」写的。追问、原型、规格、工单、验收包这些步骤，AI 是在**功能目录**里干活，产出要提交到功能分支；产品流程是在规划分支上。提交就要移动功能分支（或规划分支）的指针，四处里没有它。两种可能：AI 自己提交，那就要放开功能分支的指针，而那个位置上放着所有功能的指针；或者 AI 不提交、由脚本在步骤结束后提交，那设计书要写明，而且技能自己会不会顺手提交也要管。现在哪种都没写。F11 叫「提交规划」，而 F4a 已经写了「并提交」，F10 的确认又要「带被确认内容当时的提交编号」，三处合起来看不出规划到底在哪一步提交。S9 里规划是试验人手工提前提交好的，受限环境只放进了工单目录。（读了原文和 `S9/s9env.sh`）
- 后果：受限运行器是第 1 期要造的，它得知道每一种步骤各放开什么。
- 建议：6.3 按步骤的种类各写一份放法（工单步骤、功能级步骤、规划分支上的步骤），并写明每种步骤由谁提交。第 1 期开头在功能目录里试一次。

**一般 6. 骨架阶段谁来写那些受保护的规范配置文件，没有说**

**一般 8. AI 还能走捷径、没有东西拦住或很晚才发现的地方**

这是你问的第 5 个问题。推送、合并、改检查规则这些大路，设计堵得认真；上一轮指出的几处这一版也大多补了脚本检查。下面是还开着的：

- **a. AI 工具的状态目录整个可写、所有步骤共用，步骤结束后没人检查它。**
  - 位置：4.3、6.3 第三点。
  - 原文：6.3：「各工具真实的配置目录（`~/.claude`、`~/.codex` 等）不放进去。里面有用户的设置和钩子，受限侧如果能写，就能留下一段等用户在外面使用时才执行的代码」「每个项目给每个工具一个专门的状态目录，留在受限环境外面，用来存会话」。
  - 问题：试验脚本里，这个状态目录是整个作为 Claude Code 的配置目录、可写地放进受限环境的（读了 `AI共用/sbx.sh`）。它不只存会话：我看了 S9、S7 留下的状态目录里有哪些文件夹（没有读任何会话内容），里面有设置文件、插件目录，还有按项目建的「记忆」文件夹（自己验证过：文件夹存在，目前是空的）。设计书担心真实的配置目录被写入，同样的担心对这个目录也成立，只是范围限在受限环境里面：写代码的那个会话可以在这里留下设置或记忆，下一个「全新会话」启动时会读到，其中就包括独立复查的那个会话。记忆文件夹是按项目建的，不分工作目录，所以写代码的、复查的、做规划的会话都共用它。每步结束后的「可改范围」检查只看工作目录，不看这里。（目录的情况是读了脚本、自己看到的；「后面的会话会读到」是推断，按 AI 工具记忆功能的一般做法，没有实测）
  - 后果：「独立复查用全新会话」「每张工单一个全新会话」这两条的干净程度打折扣，而且不需要 AI 有意为之，工具自带的记忆功能就可能做到。
  - 建议：状态目录里只把存会话的那一块放成可写，设置和记忆那几块只读或每步清空；或者给复查角色单独一个状态目录。隔离自检加一项。
- **b. 验收环境跑的是哪一种构建，没有写。**
  - 位置：7.4「F3 的原型就是正式页面」、第 13 节。
  - 问题：原型阶段页面的数据是假数据层给的。脚本只检查「正式构建里不含假数据层」。但你验收时看到的那套环境是不是正式构建，第 13 节没写。如果验收环境跑的是开发方式、假数据层还开着，你验的可能是假数据。（读了原文；后果是推断）
  - 建议：第 13 节写明验收环境用正式构建，并在启动时核对假数据层不在。
- **c. 改构建配置、新增「跳过」标记，不会触发逐张的独立复查。**
  - 位置：7.5「独立复查做多密」、14.2。
  - 原文：7.5：「如果这张工单实际改到了档案声明的敏感位置（登录和权限、数据库迁移、接口契约、已有测试），即使没有风险标记也做 T9」。14.2：「跳过和不检查的标记……标记加得正当不正当（由复查审）」。
  - 问题：v0.5 加了脚本把新增的跳过标记、构建配置里的跳过开关列出来，交给复查审。但没有风险标记的工单是跳过逐张复查的，敏感位置的清单里又没有「构建配置」和「新增了跳过标记」。所以这类改动要等到功能级的复查才有人独立地看，那时已经混在整个功能的改动里。（读了原文）
  - 建议：这两种情况也算敏感位置，一出现就做 T9。
- **d. 页面变了算「待验收」还是「失败」，靠的是 AI 自己写的标记；你看不看得到新旧对比，没有写。**
  - 位置：7.4「F15 里的界面变化」。
  - 原文：「门禁把这类差异列为『待验收的界面变化』，不算失败……没有对应验收卡的界面差异才算失败」。
  - 问题：一处页面变化「有没有对应的验收卡」，是靠测试上的标记对应的，标记是写代码的 AI 写的。它把一处无意中改坏的页面挂到某张验收卡名下，这处变化就从「失败」变成「待验收」。到了你验收时，设计书没写会不会把「原来的样子、现在的样子、哪里不同」摆给你看；你照着验收卡的步骤点，未必注意到卡上没提的变化，通过之后基准就被更新了。（读了原文；后果是推断）
  - 建议：每一处待验收的界面变化，验收时都并排给你看旧图、新图和差别，你逐处点头。
- **e. 已经合进主线的数据库变更文件可以被改，没有检查。** 数据库变更文件一旦在某个环境执行过就不该再改，只能新加。验收环境每次是全新的数据库，改了旧文件也看不出来；部署又暂缓，没有一个真的数据库来暴露它。等恢复部署时会一次碰上。（推断）建议加一项脚本检查：主线上已有的变更文件不许改。
- **f. 两处小的。** 依赖缓存是可写的，而且长期给所有工单共用，里面的东西被换掉会影响之后本机的每一次门禁；好在 GitHub 上的检查用的是干净环境。提交内容那个目录是可写的，受限侧能删掉里面的东西，把本机仓库弄坏（自己验证过：删得掉，之后 Git 检查报错）；已推送的可以从远程取回，没推送的会丢。这两处都不像是「为了通过任务」会走的捷径，记在 6.5 的已知弱点里即可。
- **g. 设计书已经承认、这里只提一句的：** 验收用的数据是写代码的 AI 一并交付的；要不要逐张独立复查由规划阶段的 AI 自己标，标准还没定（W26，设计书自己写了「定下来之前这道闸等于没有」）；AI 不问、自己猜一个继续做，脚本认不出来（9.3）。

**一般 9. 有几件交给你的事，你其实判断不了**

这是你问的第 6 个问题。上一轮指出的五处，这一版基本都改了（实现路径改成脚本建议、几处点头改叫「知情」、公开还是私有给了对比表）。下面是这一版还有的：

- **风险标记的标准「由用户确认」（W26、第 19 节）。** 哪些工单算有风险（登录权限、金额计算、数据迁移……），是一个技术判断。你能做的只是知情。应当和别处一样：由另一个模型复核，你知情。（读了原文）
- **环境迁移的「逐样选择搬还是不搬」（4.8 的 Q2）。** 清单会告诉你大小、要多久、风险大中小。但「数据卷里可能是别的项目的开发数据」值不值得冒险，你要知道那些数据是什么；备份放哪、备份是不是真的能还原，你也验不了。建议清单里把每个数据卷属于哪个项目、最近什么时候用过列出来，备份做完由脚本试着还原一次再往下走。

## 七、还缺什么；第 1 期能不能开工

### 该有而完全没提的

1. **工具包交付之后自己出了错，怎么修。** 谁发现、谁修、在哪修、修完谁把关、修好之前项目怎么办。现在只有「登记」和「退回上一个版本」。没有专业人员兜底的情况下，这会是你最常碰到的麻烦。
2. **已经合进主线的功能想整个退掉。** 7.12 只有「做到一半想改」和「放弃一个进行中的功能」。
3. **事件日志长期增长怎么办。** 没有定期汇总或归档的设计。
4. **同一个项目同时开了两个 `sop`**（两个终端）会怎样，没有写互斥。
5. **已合入主线的数据库变更文件不许再改**的检查。见一般 8 的 e。
6. **磁盘怎么清。** 每个项目一份镜像、一份依赖缓存、运行日志、AI 的状态目录，只增不减。也没有「删除一个项目」「卸载工具包」的命令。
7. **追问那个会话会越来越长。** 追问、规格、工单在同一个会话里，之后规划校验和规划复查不通过时又各续接它最多 2 轮。第 15 节防「会话过长」的办法是每张工单一个全新会话，管不到这一个。
8. **整个项目的花费量级和建议的预算上限。** 见一般 10。
9. **代码本身的安全扫描。** 见轻微 7。
10. **放在 `.shared/.env` 里的第三方测试密钥，受限侧读得到。** 设计书说了 AI 服务的密钥读得到，没说这一类。应当写明这里只许放测试用的、丢了不心疼的密钥。

### 分期计划合不合理

- 大的顺序是合理的：先内核和机器层，再最小主链，再完整流程，再第二条实现路径。第 2a 期拆成「先不带页面连起来走一遍，再加页面由你上手」，比上一版好。
- 不合理的地方见一般 11：第 1 期偏大，五件验证算在期内，两样没验证的东西没排期。

### 结论

**第 1 期的正式编码现在还不能开工。可以马上开始的是它开头的那几件验证，但开始之前，先在纸面上改掉下面 6 处**，否则验证试的是错的东西，或者试完还要返工。这 6 处都只是改设计书，不用花钱：

1. 放行事件改成不依赖提交编号的做法，写明特权侧放行前核对什么、先后顺序、退路，I7 加一个试验 PR。（严重 1）
2. 环境迁移：规定 Docker 数据的位置；按原来是哪一种 Docker 分别写做法；你回答疑问 1 和 2。（严重 2）
3. 7.6 的路径补上那两个小文件的锁和事后核对。（一般 1）
4. 定下「有进行中的功能时升不升级」，让 7.11、6.4、3.2 三处说法一致。（一般 2）
5. 写明每一种步骤的受限环境各放开什么、由谁提交；什么时候推送只留一种说法。（一般 3、一般 4）
6. 状态目录里哪些可写、哪些只读定下来。（一般 8 的 a）

改完之后的顺序：先做验证（设计书列的五件，加上容器里联网、在功能目录里跑一个功能级步骤这两件），出结论、再改一次设计书，然后才写正式代码。其余问题可以在第 1 期进行中修订设计书，不挡开工。
