## 做出来了什么

| 模块（3.1） | 在哪 | 说明 |
|---|---|---|
| 内核 | `kernel/` | 事件日志（一个写入线程、每个事件等推上去才往下走、同时排着的合成一次推送、放行序号、归属名查重）；流程定义的读取和回放；流程引擎（连续执行、并行工单、停下时打印四件事）；各步的处理函数；任务包；项目锁、端口登记；特权侧用之前核对；启动器和版本机制（修补版、大版本、升级）；花费记录和提醒；`sop` 命令的入口 |

| 流程定义 | `flows/` | 功能流程、工单流程 |
| 检查库 | `checks/` | 12 个通用检查，62 个样例；守门检查；总检查 |
| 提示词库 | `prompts/` | 功能流程、工单流程里每个 AI 步骤的任务包模板 |

## 没做的、和设计书的出入

- **第二段的验收没有经过独立审查。** 设计书写的是第二段不单独审，并到整期结束那一次；这里列的「做到了」都是写代码的我自己跑的测试，样例和代码出自同一个 AI（16.1 说的局限）。
- 从第三段借来的几样只做了最小版本（开工时用户同意）：专用 Docker 只有换根脚本和测试用的临时启动办法，正式的用户级后台服务、用时才起、资源分组都没做；wt 只做了一层调用；没有 Claude Code 适配器（真实调用那一次是测试脚本直接调的）；没有 `sop project new`、`project clone`（沙箱里用测试代码建项目）。
- 第 2a 期以后的：技术栈档案（门禁命令、和档案有关的 10 来个检查）；产品流程；验收环境；规范变更；`implement-spec` 的路径（受限环境的放法和隔离自检做了，窄接口没做）；对话步骤真的接上 AI 工具。
- **新项目模板里的项目检查**（`templates/project/.github/workflows/sop-check.yml`）：门禁命令第 2a 期才接档案，在那之前它故意一跑就失败。两个检查流程文件都只在本机的沙箱里由假 gh 模拟过，没有在真的 GitHub 上跑过。
- **守门检查从公开的工具包仓库按版本取**：沙箱里用的是本机的工具包仓库，走的是同一套逻辑（检出主线、按 `sop.json` 取版本、跑守门脚本），没有在真的 GitHub 上试（第一段的轻微 3 仍然成立）。
- 设计书第二段期间只补了两处事实（3.2 的 `state/`、W40），设计没改。写代码时补的几处做法写在各步的记录里，下一次改设计书时要并进去：
  - 流程定义里补了 `F7fix`、`F9fix`、`F14fix` 三个编号（设计书文字里有、表里没有的那几步），T14 和 F14fix 加了次数上限；
  - 事件种类加了「记录」（`note`）；
  - 修补版和大版本按实际内容比（`flows/`、`skills/` 逐字一致），不靠版本自己声明；
  - T4 加了「一个提交都没有不算做完」；
  - 门禁连报告都没写出来算工具包的问题，不生成修复工单；
  - 每一轮同一个范围最多走 200 步的总保险；
  - 规划文件（规格、工单、验收卡）的格式定在 `checks/README.md`，技能实际产出的样子第 2a 期核对（W25）。
