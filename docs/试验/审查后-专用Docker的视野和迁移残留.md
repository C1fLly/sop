## 一、专用 Docker 能不能改项目根下的东西

### 做法

在 vm-a 的 `~/Project/demo1` 里造了一个假的项目结构：`.git`（里面一个 `config`）、一个工作目录 `main`（里面指向 `.git` 的小文件）、`.shared/hooks/post-create`（只链接 `.env` 的准备脚本）、`.shared/.env`、`.shared/cache`、一个封存成只读的状态目录 `.shared/ai-state/claude/F9-1/`、`.shared/runs`。然后对 demo1 的专用 Docker 下命令，等于受限侧能做的最大动作。

### 第一步：现在的做法（第一段的换根脚本，整个项目根可写，只有 `.git` 和那个小文件只读）

| 尝试 | 结果 |
|---|---|
| 普通容器挂项目根，往 `post-create` 里加一行 | **改成了** |
| 同上，改 `.env` | **改成了** |
| 同上，先把封存的状态目录里的文件改回可写，再往里加东西 | **改成了**（容器里的管理员就是用户本人的账号，「只读」的文件权限挡不住它） |
| 同上，改 `.git/config` | 改不了（只读） |
| **要了管理员能力的容器（`--privileged`），把 `.git` 重新挂成可写，再改 `.git/config`** | **改成了** |
| **普通容器挂项目根时声明「不要连带底下盖着的几层」（Docker 自带的 `bind-recursive=disabled`），再改 `.git/config`** | **改成了**，不需要任何管理员能力 |

所以审查人推断的那条路是真的：受限侧经专用 Docker 改 `.shared/hooks/post-create`，特权侧下一次 `wt new` 就会带着凭据执行它。**而且比审查人说的更宽**：设计书一直以为挡住了的「`.git` 在专用 Docker 的视野里只读」，用一个普通的 Docker 选项、或者一个要了管理员能力的容器，都能绕过去。改了 `.git/config`，特权侧下一次带着凭据执行 Git 或 wt 时，就可能照着里面写的去运行别的程序。这个洞从 S2 起就在：S2 的「经容器改 `.git` 的配置，做不到」只试了普通的挂法；它的最高权限容器试的是找凭据、钻进别的进程，没有试重新挂成可写。

### 第二步：把 `.shared` 也盖成只读（依赖缓存除外）

换根脚本在挂好项目根之后，再把 `.shared` 盖成只读，`.shared/cache` 从外面原路径重新绑成可写（`dockerd-wrap-改法.py`，后来去掉了第三步那一段）。

正常用法，都成功：

| 做的事 | 结果 |
|---|---|
| 容器往工作目录 `main` 写文件 | 成功 |
| **专用 Docker 起来以后才建的工单目录**，容器挂项目根往里写；只把这个目录挂进容器往里写 | 都成功 |
| 容器写依赖缓存、读 `.env` | 成功 |
| 构建一个镜像 | 成功 |
| 起数据库容器并查询 | 成功，2 秒就绪 |

越界：

| 尝试 | 结果 |
|---|---|
| 普通容器改钩子、改 `.env`、改封存的状态目录、在 `.shared` 里新建文件 | 都挡住了 |
| 管理员容器把 `.shared` 重新挂成可写再改钩子（挂项目根、单独挂 `.shared` 两种） | **挡不住** |
| 管理员容器摘掉盖在 `.shared` 上的只读层再改 | **挡不住** |
| 管理员容器把 `.git` 重新挂成可写、摘掉 `.git` 上的只读层 | **挡不住** |
| 普通容器挂项目根、声明不连带底下几层，再改钩子 | **挡不住** |
| 管理员容器在容器里另挂一份项目根再改 | **挡不住** |

结论：「盖成只读」只挡得住最随手的那种挂法。

为什么不能干脆不放整个项目根、只放各工作目录（审查人的建议之一）：专用 Docker 是开着不停的，它的视野在它启动那一刻就定了；之后才建的工单目录，只有在「整个项目根都放进去」时它才看得到（上表第二行）。只放当时已有的工作目录，后建的工单就用不了 Docker。

### 第三步：试过、放弃的办法：再套一层用户空间把只读锁死

想法：换根之后再开一层「用户空间」，在里面启动 dockerd。Linux 的规矩是：外面一层设的只读，到了里面一层是锁死的，里面的管理员也改不回来、摘不掉。

- 第一次写这一层的身份对应表被拒，查出来是内核要求每一段对应都落在外层的某一段里，不能横跨两段（`套用户空间-身份对应表试验.py`：`0 0 65537` 被拒，`0 0 1` 加 `1 1 65536` 两行就成了）。
- 改对以后，dockerd 起不来：「进不了它自己的网络空间，没有权限」。免管理员的 Docker 的网络空间属于外面那一层，套进去的这一层没有资格进去；要绕开就得连网络一起重做。

**放弃。** 原样留在 `废弃-套用户空间的换根脚本.py`，备查。

### 由此定的做法（写进设计书 v0.9 的 6.3、6.4、6.5）

不靠专用 Docker 里的「只读」，改成两样：

1. **能挪出项目根的都挪出去**：AI 的状态目录、运行日志、`sop` 的锁、窄接口的请求和笔记，放到 `~/tools/sop/state/<项目名>/`。它不在专用 Docker 的视野里，经 Docker 根本看不到。项目根下只留 wt 必须的 `.shared/hooks`、`.shared/.env` 和依赖缓存。
2. **挪不出去的，特权侧用之前核对**：每次执行 wt、Git、`gh` 之前，核对 `.shared/hooks` 里的三个文件和工具包模板一字不差、`.git/config` 和特权侧上一次记下的一样、`.git/hooks` 里没有会被执行的钩子、没有「工作目录专用配置」、各工作目录的三个小文件符合预期。对不上就停，交维修窗口。这些都是几个小文件，一次核对不到一秒。

「盖成只读」照样加上，挡住最随手的那种挂法。

还剩一个口子，如实写进 6.5：受限侧要是在「核对完」和「真正执行」之间那一瞬间改掉文件，核对拦不住。这要专门写一个一直盯着改的程序，属于 6.1 说的蓄意，不是走捷径。

## 二、环境迁移之后系统盘上还剩什么（审查的一般 5）

在 vm-a 里用 sudo 只读地看了第一段迁移（卸掉系统自带的 docker.io）之后的样子：

| 项 | 实际 |
|---|---|
| containerd 服务 | 还在运行，开机自己起来 |
| 随 docker.io 自动装进来的软件包 | containerd、runc、bridge-utils、pigz、ubuntu-fan，都还在（apt 的记录里这几个都标着「自动」装的；卸的时候只 `purge` 了 docker.io） |
| `/var/lib/containerd` | **424 MB** |
| `/var/lib/docker`、`/etc/docker` | 已删 |
| `docker` 用户组 | 还在 |
| Docker 官方的软件源、钥匙文件 | 没有（这台本来就是用 Ubuntu 软件源装的） |

**424 MB 就是原来那几个镜像。** 这个版本的 Docker（29）新装时把镜像存在 containerd 的目录里，不在 `/var/lib/docker`。所以第一段的迁移原型：

- Q1 清点时只量了 `/var/lib/docker`（331 MB），**大头漏算了**；
- 「系统自带的卸干净了」不成立：系统盘上的镜像一个都没删，containerd 还在跑。

要改的（写进 4.8）：Q1 同时清点 `/var/lib/containerd`；Q6 的出口检查改成一张残留清单（相关软件包连同自动装进来的、系统服务、用户组、数据目录、软件源和钥匙文件），逐项为空才算卸完；第三段加一种 Docker 官网装法（docker-ce）的迁移。
