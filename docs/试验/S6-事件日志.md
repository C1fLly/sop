# 试验 S6：事件日志

状态：已完成（2026-11-17）。设计书 8.2 的做法成立。没做的部分列在末尾。

只用了本地的 Git，没有调用 AI，没有花钱，没有连 GitHub。「远程仓库」是临时目录里的一个本地仓库，充当 GitHub。

## 要验证什么

设计书把进度记在一条单独的分支 `sop/journal` 上，当前做到哪一步靠「把事件从头读一遍」得出（8.2）。第 19 节要求 S6 验证四件事：单独分支、并行写入、回放（含回头路和条件步骤）、换目录重建。

## 做了什么

试验目录 `/tmp/sop-spike-s6/`：

- `journal.py`：事件日志的最小实现，只用 Python 标准库和 `git` 命令，约 110 行。
- `flow.toml`：一份简化的流程定义，照设计书 7.5 的工单流程和 7.4 的规划几步写的。
- `run_tests.py`：全部测试，每项事先写明期望。

写入一个事件的做法：

1. 把事件写成一个 JSON 文件，文件名是「范围 / 纳秒时间加随机数」，不会重名。
2. 取回远程日志分支的最新位置。
3. 造一个新提交接在它后面，这个提交只多一个文件。**不需要把日志分支检出成一个目录。**
4. 推送。不用强制推送，所以如果别人抢先推了，这次推送会被拒绝，回到第 2 步重来。

回放的做法：按提交的先后顺序读出全部事件，照流程定义一步一步走。顺序以提交顺序为准，不以事件里写的时间为准，所以两台电脑的时钟不一致也没关系。

### 补测：受限侧改不了日志

用 S2 的受限环境（细的放法）试：在里面移动日志分支的指针，做不到，报「只读」。设计书 8.2 的「只有特权侧写入」在本机这一头成立。

## 结论

1. **设计书 8.2 的做法成立**：单独分支、一个事件一个文件、回放得出位置，都做得出来，而且实现很小。
2. **并行写入靠「被拒绝就重来」就够了**，不需要加锁。因为每个事件是一个不重名的新文件，重来时不会有内容冲突。
3. **事件的先后以提交顺序为准**，不依赖各台电脑的时钟。
4. **「每条分支以谁为基准」记在事件里是可行的**。设计书 4.7 说 wt 只把它记在本机，换电脑后要靠事件日志里的那一份，试验里新电脑据此把工作目录建了回来。

## 试验中发现、设计书要补的四点

1. **写一个事件要连两次远程**（取回、推送）。试验里远程是本地目录，一个事件约 0.02 秒。连真的 GitHub 时要多久没有测，放到试验 S3 里顺带测。如果一次要一两秒，一个功能几百个事件就是几分钟，可以接受但要知道。
2. **断网时写不了事件。** 这个做法以远程为准，推送不上去就记不下来。设计书应当写明：断网时流程停下，不在本地攒着。这和原则 Y4（能继续的一切都在远程）一致。
3. **流程定义改了之后，旧事件里的步骤编号可能对不上。** 试验里回放遇到不认识的编号时不猜、只计数。正式做时，回放必须用项目声明的那个工具包版本的流程定义；升级工具包（7.11）时要处理进行中的功能，这一点设计书还没写。
4. **回放每次都从头读。** 195 个事件用 0.28 秒，目前不是问题。事件上千之后可以改成一次读出全部文件，不必一个一个读。

## 没做的

- 推送到真的 GitHub 的耗时（S3 里顺带测）。
- 往日志分支推送是否不触发 GitHub 上的检查（属于试验 S4）。
- 远程那一头谁能往日志分支推送：本机靠 S2 的隔离保证受限侧推不了；GitHub 上要不要再加保护，属于 S4。
- 工具包升级后流程定义变了，进行中的功能怎么接续。
- 事件文件的格式校验、损坏的事件文件怎么处理。
