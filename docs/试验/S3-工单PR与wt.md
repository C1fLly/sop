# 试验 S3：工单 PR 与 wt

状态：已完成（2026-11-17）。设计书 5.4 的结构用 wt 现有的命令能走通，有四处要由流程命令自己补。没做的部分列在末尾。

没有调用 AI，没有花钱。**在用户的 GitHub 账号下新建了一个私有的试验仓库 `C1fLly/sop-spike-s3`**，试验做完后它还在，没有删（删不删由用户定；试验 S4 也要用一个 GitHub 仓库，可以接着用它）。

没有改动 `~/tools/wt`，只是使用它（wt 1.3.1）。没有碰 `~/Project`：两个项目目录都用 wt 的 `--dir` 参数建在 `/tmp/sop-spike-s3/` 下。

## 要验证什么

设计书 5.4：每个功能一条功能分支，功能 PR 指向 `main`；每张工单一条工单分支，工单 PR 指向功能分支；工单分支落后时用合并，不变基、不强制推送。第 19 节要求 S3 验证：显式指定目标分支、用合并解决冲突、清理、在另一个目录模拟换电脑后接着做。

## 做了什么、结果如何

用两个目录充当两台电脑：`pc-A` 和 `pc-B`。

| 步骤 | 命令 | 结果 |
|---|---|---|
| 建仓库和项目 | `wt init C1fLly/sop-spike-s3 --create --private --dir <目录>` | 成功，13 秒。它同时把仓库设成「只允许压成一次提交的合并、合并后自动删分支」。目录结构是设计书 5.1 的样子 |
| 环境检查 | `wt doctor` | 通过，1 项提醒（没装自动切换目录的包装函数，不影响） |
| 建功能分支和目录 | `wt new feat/a` | 成功，目录名 `feat-a`，基准记为 `origin/main` |
| 开功能 PR（草稿） | `wt pr --draft --base main --title …` | 成功，PR #1，草稿，目标 `main` |
| 从功能分支建两张工单 | `wt new ticket/a/1 origin/feat/a`，工单 2 同理 | 成功，目录名 `ticket-a-1`、`ticket-a-2`，基准记为 `origin/feat/a` |
| 开工单 PR，显式指定目标 | `wt pr --base feat/a --title …` | 成功，PR #2、#3，目标都是 `feat/a`（在 GitHub 上核对过） |
| 合并工单 1 | 在 GitHub 上压成一次提交合并 | 成功 |
| 清理工单 1 | `wt done` | 四项核对通过，删了目录和分支。**工单 PR 的目标不是 `main` 也能清理** |
| 工单 2 出现冲突 | 两张工单改了同一行 | GitHub 显示 PR #3 有冲突、不能合并 |
| 换电脑 | `pc-B` 上 `wt init C1fLly/sop-spike-s3 --dir <目录>`，再 `wt new ticket/a/2` | 成功。内容与旧电脑推送的一致。**基准只记在旧电脑上，新电脑上 wt 按 PR #3 的目标分支把基准补记成了 `origin/feat/a`** |
| 用合并同步功能分支 | 新电脑上 `wt sync --merge` | 它执行的是「把 `origin/feat/a` 合进来」，遇到冲突停下并给出处理办法。没有变基 |
| 解决冲突、推送 | 改好文件，提交，普通的 `git push` | 成功。是普通推送，不是强制推送。历史里多了一个合并提交，旧提交都还在 |
| 再同步一次 | `wt sync --merge` | 报告「已经基于最新的 `origin/feat/a`」 |
| 合并工单 2 | 在 GitHub 上合并 | PR #3 变为可合并，合并成功 |
| 清理工单 2 | 新电脑上 `wt done` | 四项核对通过 |
| 旧电脑上的旧目录 | 旧电脑上那个落后的 `ticket-a-2` 目录也执行 `wt done` | 四项核对通过，清理成功 |
| 功能 PR 转正式 | `gh pr ready` | 成功。wt 没有对应的命令 |
| 合并功能 PR | 在 GitHub 上合并 | 成功 |
| 清理功能分支 | `wt done` | 四项核对通过。远程只剩 `main`（和后面建的日志分支） |

试验里「在 GitHub 上合并」是用 `gh pr merge --squash` 做的，代替设计里的特权侧脚本（公开仓库）或小白在网页上点（私有仓库）。

功能分支上最后的内容是两张工单的改动都在，冲突处是解决后的那一行。

### 顺带测的：往真的 GitHub 写事件要多久

这是试验 S6 留下的一项。在试验仓库上建了日志分支 `sop/journal`，用 S6 的脚本写事件：

| 做法 | 每个事件用时 |
|---|---|
| 每次都新建连接 | 平均 6.9 秒 |
| 复用同一条 SSH 连接 | 平均 2.8 秒 |

取回并读出 6 个事件用时 3 秒。这台电脑连 GitHub 要走代理，别的网络环境下数字会不同。

往日志分支推送没有产生 PR，也没有改变别的分支。

## 结论

1. **设计书 5.4 的结构用 wt 现有的命令能走通**，包括工单 PR 指向功能分支、用合并解决冲突、清理、换电脑后接着做。不需要改 wt。
2. **换电脑后基准的问题，wt 1.3.1 自己已经处理了**：没有记录时按 PR 的目标分支补记。设计书 4.7 说「事件日志里另记一份」，可以保留作为双保险（S6 试过可行），但不是唯一依靠。
3. **wt 把基准和 PR 号记在 `.git/config` 里。** S2 定下 `.git/config` 对受限侧只读，所以 wt 只能在特权侧运行。这和设计一致。

## 要由流程命令自己补的四处

1. **本机的功能目录不会自动跟上远程。** 工单 PR 合并后，`wt done` 只更新 `main` 目录；本机 `feat-a` 目录落后远程。在功能目录里执行 `wt sync --merge` 也不行，它同步的是 `main`（功能分支的基准），不是把远程的功能分支拉下来。流程命令要在 T13 之后自己执行一次「把功能目录快进到远程」。
2. **wt 没有「PR 转正式」的命令。** F18 要直接用 `gh pr ready`。
3. **`wt new` 一定会执行准备脚本，而且是带着凭据执行的。** wt 没有跳过的选项（只有 `wt init` 和 `wt new --pr` 可以不执行）。模板里的准备脚本会安装依赖，安装依赖会运行项目里的代码。这和原则 Y12（特权侧不运行项目代码）冲突。处理办法不用改 wt：工具包给项目安装的 `.shared/hooks/post-create` 只做不运行项目代码的事（例如链接 `.env`），安装依赖改由流程命令在受限侧另做。设计书 7.6 里「特权侧调用 wt、执行准备脚本」这句要改。
4. **写事件比预想的慢。** 每个事件 3 到 7 秒。一张工单大约 15 步，每步「开始」「完成」两个事件，就是 1.5 到 3.5 分钟只花在记账上；一个 8 张工单的功能是十几到三十分钟。要么复用连接并把「开始」「完成」之外的事件合并推送，要么接受这个开销。设计书 8.2 要写明取舍。

另有一处小事：准备脚本把 `.shared/.env` 以软链接的形式放进工作目录。S2 的受限环境里看不到 `.shared`，这个链接是断的。受限环境要把 `.shared/.env` 只读地放进去。

## 没做的

- 让 AI 来解决冲突（设计里 T14 由 AI 做）。这次冲突是手工解决的，验证的是 wt 和 Git 这一头。
- 多张工单同时进行时 `wt new` 之间会不会互相干扰。这次两张工单是先后建的。
- GitHub 上的检查（工单 PR 上跑快档、功能 PR 上跑全档）。属于试验 S4。
- 分支保护开启后，脚本合并和手动合并的实际体验。属于 S4。
- 原样运行 `implement-spec` 时在本地合并工单分支的做法。属于 S7。
