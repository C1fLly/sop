# 第一段 W27：环境迁移（Docker）

状态：已完成（2026-11-18）。设计书 4.8 的 Q1 到 Q6 用试验原型脚本在两台虚拟机里各走了一遍，两种原来的装法都走通：装新的、带走镜像和数据卷、核对、卸载旧的；中途人为失败一次，旧的照常可用。发现两处要补进设计书。

没有调用 AI，没有花钱。都在虚拟机里，没有碰这台电脑上的 Docker。虚拟机里的 `sudo` 代表「小白输管理员密码」。Q3（小白选择）由试验代替：全部选「带走」。脚本在 `docs/试验/脚本/第一段/W27/`：造旧环境的两个、迁移原型 `迁移.sh`。它是试验原型，不是正式的工具包代码。

## 要验证什么

第 19 节第一段：在虚拟机里试两种原来的装法（系统自带方式装的、免管理员但位置不对的）：放几个镜像和一个有数据的数据卷，装新的、带走数据、核对、卸载旧的；中途人为让它失败一次，旧的照常可用。含 4.8 写的官方安装脚本那三处。4.8 末尾列的最没把握的四样：两份免管理员的 Docker 并存再交接默认名字；数据卷打包还原后文件的归属；系统自带的 Docker 卸干净后新的不受影响；官方脚本加 `--force` 装、再把默认指向切回去后两份各自正常。

## 发现、要补进设计书的

1. **Q4 要先停掉用这个卷的容器，而且任何一步出错都要把它重新起来。** 数据库正在运行时打包它的卷，备份可能不完整，所以要先停（4.8 的「旧的一样都不动」要写明这个例外：停一下、事后起回来，事先告诉小白）。第一次试的时候脚本没有这道保险：中途出错退出，停掉的旧容器就一直停着，正好违反「中途失败旧的照常可用」。加上「无论怎么退出都先把它起回来」之后，演练通过。
2. **临时卷的名字只能用英文字母、数字和几个符号。** 第一次用了中文名，Docker 拒绝。属于实现细节，正式代码里注意。
3. **第二种情况删旧数据目录**：数据目录里有属于容器内部账号的文件，用户自己可能删不掉，要借旧的 rootlesskit 删，所以先删数据、再删程序。这次 `rm` 直接删成了（用户能删自己目录下的东西），但写成「删不掉就借 rootlesskit」更稳。
4. 备份要的空间：这次按 Docker 报的大小是镜像 443 MB、卷 41 MB，备份位置剩 27 到 35 GB。Q4 的空间检查照 4.8 写的做。
5. 用时：每台从 Q1 到 Q6 大约几分钟（镜像小、数据少，没有逐步计时）。真实的电脑上镜像和卷大得多，时间主要花在导出导入镜像上。

「中途失败一次」原来设计的做法（把备份位置设成写不进去）在系统自带的 Docker 上没坏成：那种 Docker 的容器以真正的管理员身份写文件，目录权限挡不住。改成在停掉旧容器之后让还原失败。

## 结论

1. 4.8 的做法在两种原来的装法上都走得通，最没把握的四样都试过了。
2. 要补进设计书：Q4 停掉用卷的容器、并保证任何一步出错都把它起回来；第二种情况删旧数据时可能要借旧的 rootlesskit。
3. 这是试验原型。正式的 `sop machine migrate` 在第 1 期第三段写，交付前用正式的命令在虚拟机里再走一遍（第 19 节已有）。

## 没做的

- snap 版、Docker Desktop（第一版只指引，不自动带）。
- 旧 Docker 里有很多镜像和大数据卷的情况；备份位置空间不够的情况。
- 用 Compose 起的、带项目标签的卷（这次的卷是按名字归到项目的）。
- 小白在真实的提问界面上做选择（Q3、Q6 的再确认），这次由试验代替。
