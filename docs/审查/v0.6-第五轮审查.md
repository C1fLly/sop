我没有修改任何已有文件，只新建了本文件。没有调用任何要花钱的 AI 工具（只执行了四个 AI 工具的 `--help` 和 `--version`），没有在 GitHub 上建、改、删任何东西，没有注册账号，没有用 sudo，没有执行任何 `docker` 命令、没有碰你的 Docker 和它的数据（只读了 Docker 程序目录里一个安装脚本的文字和系统里一条安全规则的文字），没有碰 `~/Project`、`~/999_`，`~/tools/wt` 只读。没有读 `docs/交接.md`、`docs/历史/`，也没有读 `/tmp` 下写设计的人和以前审查人留下的工作目录。没有打开密钥文件，没有读任何 AI 会话记录。

每条判断后面的括号是依据，共三种：

- **读了原文**：设计书、试验记录和脚本、上一轮审查报告、技能原文、wt 的说明书和脚本、GitHub 官方说明、工具的帮助说明。
- **自己验证过**：我在 `/tmp/sop-review-v06/` 下亲手做了一遍，或在本机只读地查了一下。
- **推断**：按道理推出来的，没有实测。

先解释几个绕不开的词：

- **PR**：合并申请。把一条分支的改动并入另一条分支之前，在 GitHub 上开的单子。
- **主线**：`main` 分支，正式代码所在的那条线。
- **特权侧、受限侧**：拿着 GitHub 登录凭据的流程命令 `sop` 本身；被关在小范围里、读不到凭据的 AI 和项目代码。
- **受保护路径**：决定把关松紧的那些文件（检查规则、技能文件、项目声明、页面基准截图等），普通步骤不许改。
- **守门检查**：GitHub 上的一道检查，规则永远取自主线，专门查「这个 PR 有没有动受保护路径」。
- **放行事件**：正当要改受保护路径时，特权侧在日志分支上记的一笔；v0.6 改成按「归属、路径、内容指纹」记。
- **内容指纹**：Git 给每一份文件内容算出来的编号，内容一样编号就一样。
- **链接**（符号链接）：一个「指路牌」文件，打开它就跳到别处的真实目录。
- **分区**：一块硬盘划出来的一块地方。「系统盘」指装系统的那一块。
- **免管理员的 Docker**（rootless）：不需要管理员权限就能运行的那种 Docker 装法。

## 一、总评

**这份设计到了什么程度。** v0.6 是一次认真的纸面修订。上一轮的 2 条严重、13 条一般问题，绝大多数在全文里确实改了，没有发现「只换了个说法」的；放行事件改成按内容指纹放行，思路是对的，我没有找出能让它整体失效的漏洞。试验记录总体诚实：我抽查的十几个数字和「没做的」清单都和设计书引用的一致，S6 的 29 项测试我重跑了一遍，全部符合。

但它仍然是一份**大部分只在纸面上成立**的设计：14 条要求里能说「做到了」的仍只有 2 条（第 3 条 wt、第 13 条不改技能）；v0.6 新写的六块（放行事件、环境迁移、按步骤种类的放法、按会话分的状态目录、有进行中功能时不升级、第 1 期分三段）全部没有验证，设计书对这一点写得够明白。

**最要紧的五件事：**

1. **「有别的分区就不放系统盘」按现在的写法落实不了。** 设计书的办法是把 `~/tools`、`~/Project` 做成链接，并规定「所有脚本一律用 `~/` 开头的路径，不把链接解开」。我实测了：Git 记下的是解开链接后的真实路径，照设计书的放法进受限环境后 Git 直接报「不是 Git 仓库」。另外本机那条免管理员 Docker 必需的系统安全规则是按真实路径写死的，链接路径对不上。再加上新电脑上的第二个分区常常没挂上或者你写不了，设计书对这种情况只是「提示」，结果就是装回系统盘。这条是你明确说过「必须」的。（严重 1）
2. **工具包自己出了错，修好后却装不上。** 16.5 说修好后「各项目用 `sop self upgrade` 换上」、17.1 说出错时「`sop self rollback` 退回上一个版本」，而 7.11 规定「有进行中的功能时不升级」。工具包的错几乎都是在做功能的半路上撞到的，所以那个「带开关的例外」会变成最常走的路，而它没有试过，16.5 和 17.1 也没提它。（一般 1）
3. **全档检查「被跳过」时，GitHub 算它「成功」。** 设计书把「被跳过的检查算不算通过」列为没试。我查了 GitHub 官方说明原文：用条件跳过的任务报告的就是「成功」；PR 的默认触发也不包括「草稿转正式」这一下。如果检查流程不专门加上这个触发，功能 PR 转正式后全档根本不会跑，而分支保护看到的是那个「跳过 = 成功」。（一般 2）
4. **几处前后打架。** 退掉已合入的功能要「新加一个往回改的数据库变更文件」，而「迁移文件不含破坏性操作」这项检查会把它拦下（一般 3）；4.3 的表里 AI 状态目录还是「每个项目每个工具一个」，和 6.3 新改的「按会话分」对不上（轻微 1）；T14 解决冲突之后回 T5，跳过了核对「改动范围、已确认内容」的 T4（一般 6）。
5. **AI 还有一个现成的捷径：页面截图比对的松紧写在测试代码里。** 截图测试允许在测试里写「差多少像素算一样」「这块区域不比」，测试是写代码的 AI 写的，不属于受保护路径，也不在「跳过和不检查的标记」那项检查里。（一般 5）

另外两件不急但要早定的：你在新电脑上登录 AI 工具用「官方账号」还是「自己配的服务」（官方账号那种在受限环境里从没试过，一般 4）；免管理员 Docker 的官方安装脚本遇到系统自带的 Docker 会中止，装完还会把你 `docker` 命令的默认指向改掉（一般 7）。

**花费**：一个拆成 10 张工单的功能，设计书算的是约 21 到 41 美元（工具报告的金额，不含修复），算术我核对过是对的；口径是很小的项目，真实项目多半更贵。整个项目量级几百到上千美元起。**设计书完全没有估的是造这套工具包本身要花多少**（第 1 到第 5 期，W30），这多半才是你最先付的那一大笔钱。

**结论：第 1 期第一段（验证）在纸面上先改掉第八节列的几处后就可以开工；第二、三段（写正式代码）现在不能开工，要等第一段出结论、改完设计书、通过独立审查。**

## 三、确定的问题

### 严重

**严重 1.「有别的分区就不放系统盘」按现在的写法落实不了：链接的办法实测不通，没挂上的分区又只「提示」**

- 位置：4.3（「这张表背后的规矩」三条、「`~/tools` 是一个链接」那段）、4.2 第 2 步、W36、第 19 节第一段最后一条和第三段第一条。
- 原文：
  - 4.3：「主目录在系统盘上、另有别的分区的，在那个分区上建 `tools` 目录，`~/tools` 做成指向它的链接；这样所有地方写的路径仍然是 `~/tools`」。
  - 4.3：「所有脚本一律用 `~/` 开头的路径，不把链接解开成真实路径。」
  - 4.3：「只认已经挂上、当前用户能写、不是移动盘的分区；没挂上的空盘不替小白处理，只提示。」
  - 4.3：「已经在用的电脑上……把整个 `tools` 目录挪到另一个分区，第一版不自动做……做法未定（W36）。」
- 问题：
  - **Git 记下的是真实路径，不是链接路径。** 我在 `/tmp/sop-review-v06/symlink/` 下造了一个「`Project` 是链接、真身在另一处」的目录，通过链接路径建了裸仓库和工作目录。工作目录里那个指向 `.git` 的小文件、`.git` 里的登记文件，写的都是解开链接后的真实路径。（自己验证过）
  - **照设计书的放法进受限环境，Git 直接坏掉。** 受限环境把主目录换成空的，再按 `~/` 路径把项目放进去。我用 bubblewrap 照这个放法试：Git 报「不是 Git 仓库」，因为它去找真实路径，而真实路径在受限环境里不存在。改成按真实路径放进去就正常。（自己验证过）也就是说，「不把链接解开」这条规矩方向反了。
  - **免管理员 Docker 的那条系统安全规则是按真实路径写死的。** 本机 `/etc/apparmor.d/` 下那条规则的原文是 `"/home/sanchuanzl/tools/docker/bin/rootlesskit" flags=(unconfined) { userns, }`，而本机的系统开关 `kernel.apparmor_restrict_unprivileged_userns = 1` 是开着的，也就是没有这条规则，免管理员 Docker 起不来。系统的安全模块是按程序的真实路径来认规则的，`~/tools` 是链接时，程序的真实路径在另一个分区上，和规则里写的对不上。（规则原文和开关是自己验证过的；「按真实路径认」是这个安全模块的一般做法，我没法不用 sudo 实测，是推断）专用 Docker 用的是同一个程序，一样受影响。
  - **新电脑上第二个分区多半「没挂上」或「你写不了」。** Ubuntu 装好后，另一块盘或另一个分区常见的情况是：没有开机自动挂上，或者挂上了但属于管理员。把它挂到固定位置、改成你能写，要改系统配置、输管理员密码。设计书对这种情况「不替小白处理，只提示」，你自己做不了，结果就是 `tools` 装回系统盘。之后再挪又是「第一版不自动做、做法未定」。（读了原文；「常见情况」是推断）
- 后果：主目录在系统盘上、另有分区的新电脑，要么受限环境里 Git 用不了、Docker 起不来，要么 `tools` 装在系统盘上、违背你说的「必须」。你这台电脑主目录本来就在另一个分区（我查了：系统在 `nvme0n1p5`，主目录在 `nvme0n1p6`），所以在这台上试不出这个问题。
- 设计书自己写了「这个做法没有试」，排在第 1 期第一段，这一点是诚实的。但现在能确定的是「按现写法不通」，不只是「没试」。
- 建议：
  - 不用链接。改为第零步用一次管理员密码，由脚本把那个分区（或分区上的一个目录）**直接挂在** `~/tools`、`~/Project` 这两个位置上，并写进开机自动挂载的配置；这样真实路径就是 `~/tools`，Git、受限环境、安全规则都不用改。挂之前用大白话说明要做什么、改了哪个系统文件。这一步和装免管理员 Docker 那一次管理员密码可以放在一起。
  - 如果坚持用链接：把「不解开链接」改成「一律用解开后的真实路径」，安全规则按真实路径写；另外 Git 2.48 以后可以让工作目录用相对路径记（我在本机 Git 2.53 上试了，相对路径的工作目录通过链接放进受限环境能正常用，自己验证过），但它会在仓库配置里打开一个新的扩展开关，wt 支不支持没有试。
  - 「没挂上的分区」不能只提示：要么由上面那一步脚本处理，要么写明「这种电脑只能装在系统盘上」并请你确认接受。
  - 第 1 期第一段的 W36 试验照上面改过的做法试。

### 一般

**一般 1. 工具包出了错要修，修好的版本却因为「有进行中的功能时不升级」装不上；退回旧版本也一样**

- 位置：7.11、16.5 第 2 步和第 4 步、17.1 最后一条、W18。
- 原文：
  - 7.11：「**有进行中的功能时不升级。**……`sop self upgrade` 不执行，提示先做完或放弃。」「例外只有一种：旧版本有错，把进行中的功能卡住了。这时带一个明确的开关升级……没有试（W18）。」
  - 16.5：「退回上一个版本（`sop self rollback`……）」「然后才合并，各项目用 `sop self upgrade` 换上。」
  - 17.1：「判断是工具包自身的错误时：用 `sop self rollback` 退回上一个版本」。
- 问题：工具包的错，几乎都是在做某个功能的半路上撞到的（出口检查脚本崩了、本机过而 GitHub 不过、回放对不上，16.5 自己列的就是这些）。这时：退回上一个版本，等于换版本，同样违反「一个项目同一时刻只用一个版本」；修好后升级，被 7.11 拒绝。唯一能走的是 7.11 的「带开关的例外」，而 16.5、17.1 都没提它，它本身没有试过，第 1 期第二段只用流程沙箱走一遍。设计书说「第一版一个项目一次只做一个功能，等它做完不算久」，但被工具包的错卡住的功能恰恰做不完。（读了原文；「几乎都在半路撞到」是推断）
- 后果：没有专业人员兜底时最常碰到的麻烦，走的是一条没试过、文档里也没串起来的路。
- 建议：16.5 第 2 步和 17.1 改写成「做到一半撞上工具包的错」时的完整走法：要么先放弃当前功能（`sop feature drop`）再退回或升级，要么走 7.11 的带开关升级；写明各自丢什么。`sop self rollback` 在有进行中的功能时怎么处理也写明。第 1 期第二段验收时专门演一次「功能做到一半、工具包出错、修好、换上、接着做」。

**一般 2. 全档检查被跳过时 GitHub 算它「成功」；转正式那一下默认不触发检查（设计书列为没试，官方原文已有答案）**

- 位置：6.4 第三层「项目仓库公开时」一条、7.2 的 I6、7.4 的 F18 和 F19、14.2 末尾、W21。
- 原文：

  - 14.2：「全档只在『目标是 `main` 且已转正式』的 PR 上跑（这个条件写在检查定义里，S4 实测这个条件有效……）」。
- 问题：
  - GitHub 官方说明「排查必须通过的检查」一页原文写着：「A job is skipped by a conditional｜The job reports "Success"」，「Successful check statuses are `success`, `skipped`, and `neutral`」。也就是说，把全档列为必须通过，草稿期间它被跳过，GitHub 照样算通过。（读了原文：我下载了官方页面逐字查的，存在 `/tmp/sop-review-v06/dl/ghdocs/`）

### 问题 6：交给你、你其实做不了或判断不了的

- **把第二个分区挂上、改成你能写**（严重 1）。设计书写「只提示」，你做不了。
- **工具包出错时修工具包**（16.5）。你要另开一个不在受限环境里的 AI 窗口，让它改工具包。这个窗口里的 AI 拿得到你的 GitHub 凭据（6.5 写了，这份凭据能删仓库），「只碰 `~/tools/sop` 和 `/tmp`」靠约定。修得对不对，你判断不了，靠另一个模型复查。设计书如实写了「单次修补的把关比独立审查弱」，但没有给你一个能照着做的检查单。建议：修工具包的窗口也由脚本启动，用一份只有工具包仓库权限的凭据；修完由脚本跑完全部自测、给你一句「过了／没过」。

## 九、还缺什么

该有而完全没提，或者只提了一句的：

1. **用官方账号登录时，受限环境里怎么放登录信息**（一般 4）；用订阅时花费怎么记（W10 仍未定）。
2. **`sop backup` 的备份怎么还原。** 只有备份，没有还原的命令和步骤。GitHub 账号出问题时，这是你唯一的退路。
3. **私有仓库的 GitHub 免费时长当月用完了怎么办。** 设计书算了「每月只够 3 到 7 个功能」，但用完后检查不跑、F19 一直等，这时流程怎么提示你、能不能等下个月或临时付费，没写。
4. **几个项目同时跑时，机器级登记（端口）的互斥。** 8.4 只管同一个项目开两个 `sop`。两个项目的 `sop` 同时给工作目录分配端口，会争同一个登记文件。
5. **系统升级的影响。** Ubuntu 的小版本升级可能改掉受限环境和免管理员 Docker 依赖的系统安全规则；体检（M1、M6）应在系统升级后自动重跑隔离自检。
6. **造工具包本身的花费粗估**（第七节）。
7. **一个功能从开轮到合并大概要多少天**，包括等你答题、验收的时间。你安排时间要用。
