# 3-40 工具包仓库的检查流程文件

2026-11-21，主控窗口派的子代理做的。没动隔离、放行事件、事件日志；没碰 GitHub（只用 `git ls-remote` 只读查了 `actions/checkout` 的版本标签，经网页摘要读了两页 GitHub 的公开说明）；没碰 Docker；没用 sudo；没调用 AI，0 美元。

## 做了什么

设计书 16.4：工具包仓库自己的检查（内核单元测试、总检查、流程沙箱、文档检查）在 GitHub 上跑；隔离自检、真实 AI 演练、档案合规测试要本机的环境，只在本机跑。

| 文件 | 内容 |
|---|---|
| `.github/workflows/check.yml` | 流程名 `toolkit-check`；四个检查 `unit`、`sandbox`、`checks`、`docs`，各自一台临时电脑，各跑 `uv run python tests/run_all.py [--no-skip] <部分>` |
| `tests/ci/prepare.sh` | 准备临时电脑。只在 GitHub Actions 里跑（没有 `GITHUB_ACTIONS=true`、`RUNNER_TEMP`、`GITHUB_PATH` 就直接停下，本机跑不起来） |
| `tests/run_all.py` | 加 `docs` 部分（跑 `docs/试验/脚本/文档核对/check_refs.py docs/设计书.md`）和 `--no-skip`（有测试被跳过就算没通过）；不给部分就四样都跑；给了不认识的部分报错（原来会当成 `tests/` 下的目录名去找） |
| `tests/unit/test_ci_workflow.py` | 7 项：按行核对流程文件的规矩（内核只用标准库，不读 YAML）、`prepare.sh` 不在 GitHub Actions 里什么都不写就停、版本钉死、`run_all.py` 不认的部分报错 |
| `README.md` | 「跑自测」一节写上四个部分、`--no-skip`、GitHub 上的检查 |

### 流程文件的几处决定

- **四个检查分开、名字固定**：分支保护（3-41）按名字列「必须通过」的检查，名字就是 `unit`、`sandbox`、`checks`、`docs`（显示名和编号一样，单元测试核对）。分开跑哪一样坏了一眼看得出，破坏演练（3-47）看的也是这四个名字。
- **本机跑同样的命令**：`uv run python tests/run_all.py`（四样都跑）。修完之后的把关脚本（3-44）直接调它就是「工具包仓库的检查全过」那一半；GitHub 上那四条命令就是它的四个部分。
- **单元测试、流程沙箱带 `--no-skip`**：GitHub 上的电脑是现准备的，缺了 wt、内核没禁用往终端塞按键之类，有几项测试会自己跳过、整体照样显示通过。本机自测 514 项、43 个剧本都是 0 项跳过，所以 GitHub 上要求 0 项跳过不比本机松。（本机的 `run_all.py` 默认不带，跟原来一样。）
- **临时电脑钉 `ubuntu-26.04`**：工具包只支持 Ubuntu 26.04（4.1）。GitHub 2026-09-17 起正式提供，`ubuntu-latest` 10 月到 11 月 19 日才慢慢换到 26.04（经网页摘要：GitHub 更新日志），不用会自己换系统的 `ubuntu-latest`。镜像带 Python 3.14.4，不带 uv、不带 bubblewrap（经网页摘要：runner-images 的 `Ubuntu2604-Readme.md`，镜像版本 20261116）。
- **第三方 Action 只用了 GitHub 官方的 `actions/checkout`，钉在提交编号上**：标签可以被挪去指向别的代码，钉提交编号才保证跑的是看过的那一份。v7.0.1 → `3d3c42e5aac5ba805825da76410c181273ba90b1`，用 `git ls-remote --tags https://github.com/actions/checkout` 只读查的（轻量标签，就是这个提交）；发布日期经网页摘要是 7 月 20 日（页面没写年份，页脚 2026）。**在真 GitHub 上能不能跑没验，留给 3-41。** 取代码时 `persist-credentials: false`，不把 GitHub 给的临时凭据留在 `.git/config` 里（单元测试会对这个仓库跑 git）。
- **uv、wt 不用别人的 Action**，用工具包自己的 `machine/install/uv.sh`、`machine/install/wt.sh` 装到临时电脑的 `~/tools`（和小白电脑上 M2、M5 一样的装法，顺带让这两个脚本每次都在真 GitHub 上跑一遍），版本钉在 `prepare.sh` 开头：uv 0.13.7、wt 1.3.1，都是本机现在跑自测的那一份。
- **只读权限**（`permissions: contents: read`）；触发只有推送到 `main`、对 `main` 的 PR（`pull_request`，不是 `pull_request_target`）、手动；同一分支新的一次推送取消还在跑的旧的。
- **流程文件里没有任何真的密钥。** 唯一用到的机密是 `WT_DEPLOY_KEY`，只给「准备电脑」那一步（`checks`、`docs` 不要它）。

### 准备电脑 `prepare.sh` 做什么

1. 核对 `python3` 是 3.14 以上（`pyproject.toml` 要求、禁止 uv 另外下载）。
2. 用工具包的 `uv.sh` 装 uv 0.13.7，核对版本，加进 PATH。`--light`（`checks`、`docs` 用）到这里就完了：总检查不起受限环境、不调 wt（在只读 bubblewrap 里把 `bwrap`、`openssl` 挡掉跑过，95 个样例照样全部符合）。
3. `sudo apt-get install bubblewrap`，然后真起一次受限环境核对能用。Ubuntu 26.04 默认限制普通用户建隔离空间，靠 AppArmor 里放行 bwrap 的那条规则；**起不来就停下说明，不去关系统的限制**（关了就和小白的电脑不一样，等于为了过而放宽）。
4. 内核的「往终端塞按键」开关不是禁用就设成禁用（和 Ubuntu 26.04 默认一样，是收紧）；不然对话那几项单元测试会跳过。
5. wt：仓库 `C1fLly/wt` 是私有的（3-22），流程沙箱真调 wt，所以要一把只能读 wt 仓库的部署钥匙。私钥从机密 `WT_DEPLOY_KEY` 临时写进 `~/.ssh/id_ed25519`（0600；那里已经有文件就不盖），GitHub 的主机钥匙从 `https://api.github.com/meta` 取（HTTPS，不盲信第一次连上的），`wt.sh` 经 SSH 克隆、切到 v1.3.1、核对版本，**装完马上删掉私钥**（出错也删）。没给钥匙就停下说清楚。`~/tools/wt` 是一份 Git 克隆，`test_machine_wt.py` 要的正是它。

## 验证

本机没有真的 GitHub 临时电脑，照流程文件的步骤造了一台「像的」，在 `/tmp/sop-3-40/` 里做：

- 「取代码」：把工作区的文件（`git ls-files -co --exclude-standard`）拷成一份新仓库、提交一次，放在临时主目录下的 `work/sop/sop`（GitHub 上也在主目录下）。没有 `.venv`，`uv run` 现建。
- 假的 `sudo`：只打印要做什么（apt、sysctl 在 GitHub 上才真做）。`GITHUB_ACTIONS=true`、`RUNNER_TEMP`、`GITHUB_PATH` 指到临时目录，`WT_DEPLOY_KEY` 是一串假的字（wt 从本机 `~/tools/wt` 只读克隆，用 `SOP_CI_WT_REPO` 换来源，不走 SSH），之后把 `GITHUB_PATH` 里的目录照 GitHub 的顺序加到 PATH 前面，再跑那一条检查命令。
- `docs`、`checks`：套在整个系统只读、真的主目录换成空目录的 bubblewrap 里跑（`checks` 另一遍把 `bwrap`、`openssl` 挡掉）：uv 0.13.7 真从网上装到临时主目录，文档检查 0 处悬空，总检查 95 个样例 0 个不合格。
- `unit`、`sandbox`：**套不了 bubblewrap**：外面一层是 bwrap 时，里面再起 bwrap 被 Ubuntu 26.04 的 AppArmor 规则挡住（正好验了 `prepare.sh` 第 3 步：它停下了、说明了，没去关限制）。所以这两样不套，用 `env -i` 清空环境、主目录换成 `/tmp` 下的临时目录直接跑（和平常跑自测一样，测试本身还有 3-59 的保险）：
  - `unit`：准备全过（uv、受限环境能起、往终端塞按键已禁用、wt 1.3.1 装好，`~/.ssh` 里只剩 `known_hosts`，私钥删了），`--no-skip` 单元测试 521 项全部通过、0 项跳过。
  - `sandbox`：准备全过（同上），`--no-skip` 流程沙箱 43 个剧本全部通过、0 项跳过，约 5 分钟；`~/.ssh` 里只剩 `known_hosts`。
- 反着试：
  - 流程文件的单元测试，在 `/tmp` 的副本上改 8 种（Action 不钉提交、流程沙箱少 `--no-skip`、多一个机密、写权限、少了 `docs`、`ubuntu-latest`、`pull_request_target`、留凭据），8 种都报。头两次有两种「没报」是我改到了注释里的同样文字，改成改代码行后都报。
  - `--no-skip`：造一项跳过的测试，不带时「全部通过」，带了「有 1 项被跳过」、退出码 1。
  - `prepare.sh` 不在 GitHub Actions 里（三种缺法）：退出码 1、什么都没写（单元测试）。
  - `prepare.sh` 没给 `WT_DEPLOY_KEY`：装完 uv、核对完受限环境后停在 wt 那一步，说清要什么，退出码 1，`~/tools` 下没有 wt。
  - `prepare.sh` 受限环境起不来：上面套 bwrap 那一遍碰上了，停下、打出 `kernel.apparmor_restrict_unprivileged_userns = 1`，没去关限制。
- YAML：本机系统自带的 `python3` 有 PyYAML 6.0.3，读得出，四个检查、触发、权限都对（只是核对，不在自测里）。

## 没做的、留给后面的

- **真 GitHub 上没跑**（3-41）：`ubuntu-26.04` 上 AppArmor 放不放行 bwrap、`legacy_tiocsti` 是多少、`apt-get install bubblewrap` 要多久、`actions/checkout` v7.0.1 那个提交能不能用、流程沙箱在 GitHub 的电脑上要多久（本机约 5 分钟）、wt 部署钥匙经 SSH 能不能取，都要在真 GitHub 上看。哪一样不对，3-41 照实改，**不要用关掉系统限制、去掉 `--no-skip` 的办法让它过**。
- **要用户定的**：wt 仓库是私有的，GitHub 上跑流程沙箱要一把只读部署钥匙。推荐：用户在 `C1fLly/wt` 的 Settings → Deploy keys 加一把只读的公钥（不勾 Allow write access），私钥放进 `C1fLly/sop` 的 Settings → Secrets and variables → Actions，名字 `WT_DEPLOY_KEY`；钥匙对可以由 3-41 在 `/tmp` 里现生成、用完删本地副本。别的路：把 wt 改成公开仓库（就不用钥匙）；或者 GitHub 上不跑流程沙箱（违反 16.4，不推荐）。没有钥匙时 `unit`、`sandbox` 两个检查会停在「准备电脑」那一步，红。
- 别人从分叉仓库发来的 PR 拿不到机密，`unit`、`sandbox` 会红。工具包仓库只收自己的改动，不处理。
- **文档检查只查设计书里的章节号、步骤编号**；16.2 说的「文档引用的命令、文件路径都存在」没有，拆成 **3-62**。`check_refs.py` 还放在 `docs/试验/脚本/` 下（交接、提示词里都写着这个路径，没挪），3-62 可以把它挪进 `checks/` 或别处。
- 版本升级：uv、wt、`actions/checkout` 都钉死了，以后换版本要手动改 `prepare.sh` 开头和流程文件、在 GitHub 上跑一遍；没有自动提醒。
- 检查结果在 GitHub 上只保留默认的日志，没有另存报告；`checks` 失败时看日志里「不符合」那几行。
