## 原因（3-54 看清的，这次补了一条）

分组超了上限，内核杀了吃内存的容器进程；被杀的内存要过一会儿才还回来，这期间**同一个分组里谁再要一点内存，就又触发一次**，内核按大小再挑一个杀。3-54 把专用 Docker 自己的分数调低（100）、容器调高（1000）以后，第二次挑中的就是容器，常常是同项目别的容器。第二次是谁触发的：

- `containerd-shim`、dockerd 收尾时要的内存（3-54 看到的）。它们和容器在同一个上限下，所以会触发。
- **吃内存的容器里剩下的进程**（这次加演才看到）：`sh -c 'head … | tail'` 这种吃法，tail 被杀后 13 微秒，同一个容器里的 head 往管道里写又要内存，内核在容器的小组里按大小再挑，挑中了旁边容器的 `sh`（内核日志 `head invoked oom-killer` 紧跟着 `Killed process … (sh)`，那个 sh 是旁边容器的）。

## 做了什么（从根上：容器单独一个内存小组，专用 Docker 自己不在里面）

1. **服务分组下分两个小组**（`runner/docker/service.py`）：服务登记加 `DelegateSubgroup=daemon`，专用 Docker 自己的进程（rootlesskit、dockerd、containerd、各容器的 containerd-shim）都在 `daemon/` 里；服务分组本身没有进程。要 systemd 254 以上（Ubuntu 26.04 是 259）。
2. **容器的小组 `ctr/`**（`runner/docker/dockerd_wrap.py`，起 dockerd 之前、换根之前）：认准自己在 `daemon/` 里（不在就不起，报「服务登记少了 DelegateSubgroup=daemon」），打开服务分组下一层的开关，建 `ctr/`，把项目的内存上限（服务登记里的 `SOPD_MEM`，字节数）写在 `ctr/memory.max`，`memory.swap.max` 写 0。
3. **runc 外壳把容器放进 `ctr/<容器编号>`**：3-54 的外壳本来就在建容器时改 `config.json`，这次改成交给一个小的 `spec.py`（新根里，只读）用 JSON 改：分数 1000（原来的）、`cgroupsPath` 指到 `ctr/<编号>`（不管 dockerd 给的是什么）、`memory.oom.group=1`。改不成（编号认不出、`config.json` 坏了或没有）就不交给 runc，不让容器落到 `ctr/` 外面。
4. **整个容器一起杀**（`memory.oom.group=1`）：一个容器超了，内核把这个容器里的进程一起杀掉，它剩下的进程就不会再触发一次。这和 Kubernetes 1.28 起在 cgroup v2 上的默认做法一样（凭记忆，没核实）。吃内存的容器本来就会因为主进程被杀而停，这一条只是让它剩下的进程别再去要内存。
5. **项目分组上只留一道兜底**：分组的 `MemoryMax` = 容器的上限 + 512M（`DAEMON_ROOM`），不用交换区不变。百分数按这台电脑的物理内存换成字节数（和服务管理器一样，K/M/G/T 按 1024 算），`infinity` 照旧不限。处理器上限还在分组上、照旧当场生效。

这样容器超了上限只在 `ctr/` 里挑着杀；shim、dockerd 要内存记在 `daemon/` 上，不会再触发容器那一组超限。

也看了：`docker build`（这台没有 buildx，用的老构建）RUN 那一步的容器也落在 `ctr/` 里、分数 1000；`docker exec` 起的进程跟着容器在 `ctr/<编号>` 里、分数 1000。

## 上限的含义变了（留给 3-48 并入 6.3 二、6.5，用户可否决）

- **原来**：技术栈档案 `[docker]` 段的 `memory`（默认内存的一半）是「这个项目的专用 Docker 连同它起的所有容器」合起来的上限。
- **现在**：它是「这个项目所有容器合起来」的上限，**不含专用 Docker 自己**（平常约 180 MB，加上每个在跑的容器一个约 5 到 15 MB 的 shim）。
- **代价**：
  1. 一个项目实际最多能占到「上限 + 512M」（默认是内存的一半再加 512M）。两个项目各用默认值时，合起来的兜底比整台电脑的内存多 1G；原来也是两个一半加起来就是全部，差别不大。
  2. 专用 Docker 自己不受项目上限管，只受兜底管：它自己失控（比如 Docker 的毛病）超了兜底，就回到原来的样子：内核在整个项目里挑，先杀容器（1000），可能连着杀几个，专用 Docker 自己（100）还是最后才被杀。演的这么多次里兜底一次都没超过。
  3. 容器指定 `--runtime runc` 就绕开外壳（3-54 写过分数会回到 100）；现在还会落在服务分组下、`ctr/` 外面（虚拟机里看过），不受容器的上限管，只受兜底管。不影响隔离（视野、只读照旧）；受限侧的 AI 一般不会这么写。
  4. 改了容器的内存上限，专用 Docker 正在跑时**不当场生效**，下次起来才生效（闲了停以后、或重启以后）；兜底和处理器上限照旧当场生效。
  5. 同项目几个容器仍然**共用一个上限**：谁超了，内核在 `ctr/` 里按大小挑，最大的那个先被杀。如果吃内存的不是最大的（例如旁边有一个更大的数据库），被杀的可能是那个更大的。这是「上限按项目、不按单个容器设」本来的样子（6.3 二），不是这次的毛病；演的时候吃内存的那个总是最大的。
  6. 「整个容器一起杀」：一个容器里只是某一个子进程超了，也是整个容器一起停（不会只杀那个子进程、让容器自己恢复）。

## 结果

### 单元测试（`tests/unit/test_docker_service.py`，多了 3 项、改了几项）

- 分组上是兜底（300M 加 512M 的字节数）、服务登记有 `SOPD_MEM`（300M 的字节数）、`infinity` 写成 `infinity`/`max`；`DelegateSubgroup=daemon`。
- `memory_bytes`：300M、2G、4096、100%、infinity 换得对；0、0M、0% 不生成。
- runc 外壳：建容器时分数 1000、`cgroupsPath` 是 `ctr/c1`、`memory.oom.group` 是 1，别的字段不动；原来有别的资源设置和别的分组位置时，留着资源设置、分组位置改回 `ctr/`；编号是 `../x`、`-x`、空的，`config.json` 坏了或没有，都不交给 runc、文件不动。
- 换根脚本里有「认准 daemon/、打开开关、建 ctr/、写上限和交换区」这几处。

全部自测：做之前（主控窗口跑的）单元测试 211 项、流程沙箱 24 个剧本、总检查 62 个样例全过；做之后**单元测试 214 项、流程沙箱 24 个剧本、总检查 62 个样例，全部通过**。

## 和设计书的出入（留给 3-48 并入）

1. 6.3 二、6.5、第 5 期那一行：项目的内存上限只管容器合起来的量（容器在服务分组下的 `ctr/` 里、专用 Docker 自己在 `daemon/` 里），项目分组上是兜底：容器的上限加 512M；上面「代价」六条。
2. 6.3 二：容器超内存时整个容器一起杀（`memory.oom.group`）；超内存时同项目别的容器不跟着停、专用 Docker 本身没事（演的次数见上）。
3. 3-54 出入第 2 条「同项目里在跑的别的容器可能被内核顺带杀掉」作废，改成上面两条。
4. 专用 Docker 的服务要 systemd 254 以上（`DelegateSubgroup`）。
