# 3-52 流程沙箱偶尔报 hardlink：假 gh 克隆

2026-11-20。由主控窗口派出的子代理做。没调用 AI，没花钱，没开虚拟机。只改了测试用的假 `gh`，流程引擎一个字没改。

## 原因

假 `gh` 每次跑守门检查（PR 打开、有新推送、重新跑），都要 `git clone` 一份假远程（`/tmp` 下的一个裸仓库）。两边都在本机，Git 默认走「本地克隆」：不走正常的传输，而是把假远程 `objects/` 目录里的文件**逐个硬链接或拷过来**，链完再核对一下是不是同一个文件。

与此同时，`sop` 进程里写事件日志的那个线程正往同一个假远程推送（`sop/journal`），几张工单的线程也在推分支。Git 收推送时先把对象写进 `objects/tmp_objdir-incoming-…/` 下的临时文件，收完再改名挪走、删掉临时目录。克隆正好在逐个拷的时候碰上这些临时文件：

- 链接之后文件已经被换掉 → `fatal: hardlink different from source`（3-50 碰到的那一次）；
- 文件已经被挪走 → `fatal: 无法拷贝文件至 …: 没有那个文件或目录`（同一个原因的另一种样子）。

`/tmp` 是内存盘只是让这件事更快、更容易撞上，不是原因；换成普通磁盘一样会撞，只是概率低一点。

## 重现

- **单独的小脚本能稳定重现**（`/tmp` 下临时目录，一个进程不停往裸仓库推，另一个同时不停本地克隆，跑完删掉）：
  - 默认克隆：2831 次里失败 13 次、2255 次里 15 次、2000 次里 8 次，都是上面两种报错。
  - 加 `--no-hardlinks`（任务名里写的办法）：870 次里失败 10 次、612 次里 5 次，**只是把报错换成了「无法拷贝文件」**，没有解决。
  - 加 `--no-local`（像真的 GitHub 一样打包传过来）：38、39、150、150、161 次，**一次都没失败**。
- **流程沙箱里没重现出 hardlink**：改之前把 `test_failures` 的 `test_fix_diagnose_decide_and_backtracks` 跑了 64 遍（4 个同时跑，24 遍加 40 遍），没出现 hardlink。概率很低（3-50 那次是全部自测跑了三遍碰到一次）。判断依据是上面的小脚本和报错里的路径 `tmp_objdir-incoming-…`：这个目录只在「有人正往这个仓库推送」时才有。

## 做了什么

- `tests/fakes/gh/gh` 第 121 行：守门检查的克隆加 `--no-local`（不是任务名写的 `--no-hardlinks`，原因见上），旁边写了一段注释说明为什么。这样更像真的 GitHub 上的检查流程（真的检出也是从网络打包传来的）。

## 结果

- 改之后：这个剧本 4 个同时跑 40 遍、一个一个跑 20 遍，一共 60 遍，**没有一次报 hardlink 或「无法拷贝文件」**；其中 4 遍因为下面那个另外的问题没过。
- 全部自测：做之前单元测试 182 项、流程沙箱 24 个剧本、总检查 62 个样例全过；做之后跑了一遍，还是 182、24、62，全部通过。

## 另外发现的一个问题（在正式代码里，没改，留给主控窗口）

连跑时还碰到另一种偶尔没过，**和 hardlink 无关**：改之前 4 个同时跑的 24 遍里 2 遍、另外 40 遍里 0 遍；改之后 4 个同时跑的 40 遍里 4 遍、一个一个跑的 20 遍里 0 遍（同时跑的越多越容易碰上），停在工单的 T1（开工单目录）：

```
wt new ticket/jz-1/01 origin/feat/jz-1 失败：wt: 拉取最新（git fetch --all）
error: fetching ref refs/remotes/origin/sop/journal failed: incorrect old value provided
```

我的判断（只读代码，没改）：`kernel/project.py` 调 `wt` 时拿着 `gitlock`，`wt new` 里会 `git fetch --all`，把所有远程分支（包括 `refs/remotes/origin/sop/journal`）都更新一遍；而写事件日志的线程（`kernel/journal.py` 的 `_Writer`，推送成功后 `update-ref refs/remotes/origin/sop/journal`，以及 `Journal.fetch`）不拿 `gitlock`，两边同时改这一个指针，`wt` 那边就报「incorrect old value」。`Journal.fetch` 自己碰到这种报错会重试，`wt` 不会重试，一次失败流程就停下。

这是流程引擎的事（真用的时候也会碰到：几张工单同时开、事件日志同时在写），不是假东西的问题。按交代没改，**拆成新任务 3-53** 写进清单，怎么改（例如写事件日志更新那个指针时也拿 `gitlock`、或者 T1 碰到这种报错重试一次）由主控窗口定。这个失败和这次改动无关：改之前就有。
