# 《AI 开发 SOP 工具包 设计书》草案 v0.4 第三轮独立审查报告

审查日期：2026-11-17。审查对象：`docs/设计书.md`（v0.4，1499 行，从头读到附录 D）。

我没有修改任何已有文件，只新建了本文件。没有调用任何要花钱的 AI 工具，没有在 GitHub 上建、改、删任何东西，没有用 sudo，没有碰你的 Docker、`~/Project`、`~/999_`，没有读 `docs/交接.md` 和 `docs/历史/`，没有打开密钥文件和 AI 工具的会话记录。

每条判断后面的括号是依据，共三种：

- **读了原文**：设计书、试验记录、技能原文、wt 说明书和脚本、各工具的帮助说明。
- **自己验证过**：我在 `/tmp` 下亲手重做了一遍。
- **推断**：按道理推出来的，没有实测。

先解释几个绕不开的词：

- **PR**：合并申请。把一条分支的改动并入另一条分支之前，在 GitHub 上开的单子。
- **主线**：`main` 分支，正式代码所在的那条线。
- **受限环境**：把 AI 和项目代码关在一个读不到登录凭据、写不了别处的小范围里。
- **特权侧**：拿着 GitHub 登录凭据的流程命令 `sop` 本身。
- **守门检查**：GitHub 上的一道检查，规则永远取自主线，专门查「这个 PR 有没有动不该动的文件」。
- **受保护路径**：决定把关松紧的那些文件（检查规则、技能文件、项目声明、视觉基准截图等），普通步骤不许改。
- **视觉基准**：你验收通过时保存下来的页面截图，以后用来比对页面有没有被改坏。
- **门禁**：一组必须全部通过的自动检查。

## 一、总评

**这份设计到了什么程度。** v0.4 比 v0.2 扎实得多。上一轮 38 条问题里，我核对下来 19 条真解决了，13 条部分解决，5 条只在纸面上解决（多数因为部署暂缓，或者还没试），1 条只是换了说法（说「只剩一处」其实不止）。九项试验的记录总体诚实：每份都有「没做的」一节，设计书多数地方也照实写了。我亲手重跑了事件日志的 29 项测试和隔离探测，结果和记录一致。

但它仍然是一份**大部分只在纸面上成立**的设计。14 条要求里，能说「做到了」的只有 2 条（第 3 条 wt、第 13 条不改技能），其余 9 条是「纸面成立、还没验证」，3 条没做到（第 6 条多端和第 11 条上线运维是你自己决定推后的；第 14 条环境迁移是设计书完全没有，而且写的做法正好相反）。

**最要紧的五件事：**

1. **守门检查会把正常的流程卡死，而且不止设计书承认的那两处。** 设计书的 W21 只说「工具包升级、规范变更」过不了守门检查。实际上还有两处更常见的：你每次验收通过后保存页面截图（截图目录也在受保护清单里），以及产品流程一开始写项目声明。前者意味着在公开仓库上，**第一个带页面的功能就合不进主线**。另外，项目初始化的步骤顺序也走不通。（严重 1、一般 2）
2. **有几样地基没验证，就排在了要用它的那一期后面。** 受限环境和专用 Docker 在第 1 期造，但「在里面装依赖、跑 Java 和 Node、跑 Compose 和 Testcontainers、走代理拉镜像」要到第 2a 期才验证。另外，**需要你坐在窗口前和 AI 对话的那种方式，在受限环境里一次都没试过**，而追问、规格、工单这三步全是这种方式。（严重 2）
3. **第 14 条要求（环境迁移）设计书里完全没有，写的还是相反的做法。** 设计书 4.3 说位置不对的工具「不算不合格，登记实际位置后照用」。这和你的第 14 条、第 4 条都对不上。机器层正是第 1 期要做的，所以开工前必须先定。（严重 3）
4. **做一个功能到底花多少钱，设计书没有给出完整的数。** 现有的「约 26 美元」只算了规划和实现，没算四种复查和验收包；数字来自一个只用 Python 标准库的小工具，不是 Java 加 Vue 的真实项目；而且是工具按官方价估出来的，不是你的账户实际被扣的钱。（一般 1）
5. **有几处 AI 可以走捷径而没有东西拦。** 最明显的是：把关的松紧其实有一部分藏在构建配置文件里（比如「跳过测试」的开关），这些文件普通工单本来就要改，不在受保护清单里；而专门查「门禁有没有失效」的门禁自检，最长要隔 5 个功能或 30 天才跑一次。（一般 3）

另有一处我**亲手验证**出来的隔离漏洞：受限环境能改掉一个告诉 Git「仓库在哪」的小文件，之后流程命令在外面执行 Git 时会读到 AI 放的配置。设计书说「四条要求同时满足」，这一处没查到。好在修起来很简单。（一般 4）

**结论先说：第 1 期现在不建议直接开工。先把第八节列的 6 件事定下来（都不需要再做大试验），之后可以开工。**

## 三、确定的问题

### 严重

**严重 1. 守门检查和「正常要改受保护路径」的流程互相卡死，范围比 W21 承认的大**

- 位置：6.4 第三层、5.6、7.4 的 F17 和 F19、7.5 的 T11、7.3 的 P1 和 P2、第 20 节 W21。
- 原文：
  - 6.4：「守门检查……只查这个 PR 有没有改动受保护路径（5.6）」「两个都通过才算通过」。
  - 5.6：受保护路径包括「`sop.json`」「`docs/baseline/`」；「只有三种专门的步骤可以改它们：工具包升级、规范变更（7.11）、验收（只更新视觉基准）」。
  - F17：「通过时更新视觉基准并提交」；F19：「全档检查通过」。
  - W21：「守门检查会拦住一切改动受保护路径的 PR，包括工具包升级和规范变更这两个专门流程。」
  - P2 的产出：「`sop.json` 的档案段」。
- 问题：
  - **验收更新截图会被拦。** 5.6 自己说有三种步骤可以改受保护路径，W21 只提了两种，漏了第三种「验收」。而验收是每个带页面的功能都要走的：你验收通过，截图存进 `docs/baseline/`，提交到功能分支；功能 PR 里就有了对受保护路径的改动，守门检查必然是红的。在公开仓库上，开了分支保护，这个功能就合不进主线。（读了原文；S4 的守门检查脚本就是按「PR 改了哪些文件」来判的，我读了那份脚本）
  - **W21 想的办法解决不了它。** W21 的方向是「专门流程用特定的分支名」。截图是提交在普通的功能分支和工单分支上的，换不了分支名。（推断）
  - **产品流程的产出怎么进主线，全文没有写。** P1 写 `docs/product/risk.json`，P2 写 `sop.json`（受保护路径），P5 到 P9 写地图、产品规格、功能清单。这时还没有任何功能分支（F1 才建）。7.3 的表里没有「开分支、开 PR、合并」这样的步骤。上一轮第 4 条指出过「根本没有功能分支的 P1 到 P7，记录只能直接推到主线」；记录后来挪到了日志分支，但**这些步骤的产出文件**仍然没有着落。（读了原文，检索了全文所有提到产品流程的地方）
- 后果：按现在的写法，公开仓库上主链走到第一个带页面的功能的 F19 就停了；产品流程走完 P2 就没法往下。
- 建议：开工前把这三件事一起定下来，不要留到第 1 期中途。
  - 截图目录怎么处理：例如守门检查对 `docs/baseline/` 只允许图片文件的增改，另外由流程命令在本机核对「这次截图提交确实对应一条验收通过的事件」。
  - 产品流程加上明确的「开规划分支、开 PR、合并」步骤，并说明 `sop.json` 那一次怎么过守门检查。
  - W21 的办法要把上面两种情况也盖住。

**严重 2. 有几样地基性的东西，验证排在了要用它的那一期之后；对话方式在受限环境里从没试过**

- 位置：第 19 节第 0 期开头、第 1 期、第 2a 期；6.3 末尾；7.4。
- 原文：
  - 第 0 期：「只验证地基性的假设……任何一项不成立，先改设计再动工。」
  - 第 1 期内容：「引导脚本、机器层、受限运行器、内核……」
  - 第 2a 期：「从第 0 期留下来、明确放到本期补验证的事……专供受限侧的 Docker 上跑 Compose、构建镜像、Testcontainers，以及走代理联网拉镜像……受限环境里安装依赖、运行 Java 和 Node」。
  - 7.4：F2、F5、F6 的执行者都是「AI 交互」。
- 问题：
  - **受限运行器和专用 Docker 是第 1 期造的，它们撑不撑得住真实的技术栈却要到第 2a 期才知道。** 这几样里任何一样不成（例如 Testcontainers 要把 Docker 的通道再挂进一个容器，而专用 Docker 的视野是白名单），就要启用保底方案「单独的系统用户」。保底方案要管理员权限、Docker 要另配、目录要两个用户共用，等于第 1 期的机器层和受限运行器要重做。这和第 0 期自己定的规矩相反。（读了原文；后果是推断）
  - **对话方式一次都没试过。** 我检索了全部九份试验记录，没有一处提到「交互」。所有试验都是自动调用：S0 的「对话」是驱动脚本一句一句转发的。试验脚本里受限环境都带着「脱离终端」的设置（`--new-session`、`TERM=dumb`），这种设置下，要你坐在窗口前打字的界面能不能正常用是未知数。而追问、规格、工单，加上产品流程的 P5、P7、P8、P9，全是「AI 交互」。（读了原文和脚本；「可能不正常」是推断）
  - **S0 的主链不是在真正的项目结构里跑的。** S0 用的是一个普通目录，整个目录可写；不是裸仓库加工作目录、`.git` 只放开四处的那种结构。也没有连 GitHub，没有 Docker，没有第三方依赖。「主链走得通」这句话成立的环境，比第一版的目标简单得多。（读了 `docs/试验/脚本/S0/sbx.sh` 并看了 `/tmp/sop-spike-s0/proj` 的目录）
  - 各段是分开验证的：S0 没有 GitHub，S3、S4 没有 AI，S7 用的是假远程。**连在一起走一遍**要到第 2a 期。
- 后果：第 1 期做完才发现地基要换，损失的是整个第 1 期。
- 建议：把下面三件事提到第 1 期的最前面，当作第 0 期的补做，结果出来再造受限运行器。
  - 在受限环境里用专用 Docker 跑一个最小的 Java 加 PostgreSQL 加 Testcontainers 的例子，和一个最小的 Vue 加 Playwright 的例子，含装依赖、走代理。
  - 在受限环境里用对话方式启动 Claude Code，让你本人打几句字，关掉，再续接一次。
  - 在裸仓库加工作目录的结构里跑一张 `implement` 工单。

**严重 3. 第 14 条要求（环境迁移）没有设计，4.3 写的做法相反**

- 位置：4.3 末尾、4.5 的 M1 和 M2、6.3。
- 原文：「电脑上已经装好、位置不符合上述规则的工具不算不合格，体检把它的实际位置登记下来，之后按登记的位置使用。」
- 问题：
  - 你的第 14 条要的是「迁移为符合 SOP 开发环境的位置」，并且举的例子就是 Docker。设计书的做法是「不迁移，记下来照用」。全文没有任何迁移的步骤、命令或风险说明。（读了原文，检索了「迁移」，只出现在数据库迁移的意思上）
  - 这也让第 4 条「位置固定」打了折扣：按 4.3，同一样工具在不同电脑上可以在不同位置。
  - Docker 的迁移尤其不简单：要搬镜像和数据卷，要改后台服务的设置。本机 `/etc/apparmor.d/` 下有一条按路径写的规则（文件名是 `home.sanchuanzl.tools.docker.bin.rootlesskit`），说明免管理员的 Docker 换位置后还要用管理员权限重装这条规则。（文件名是我看到的；「要重装」是推断）
  - 说明一下：`docs/原始要求.md` 里只有 12 条，第 13、14 条是你这次才给我的。设计书是按 12 条写的，所以这不是它「漏做」，而是需求变了。但机器层是第 1 期的内容，必须先定。
- 建议：开工前由你定两件事，再让设计书补一节。
  - 迁移是「必须迁」还是「问你一句再迁」。
  - 哪些东西在迁移范围内（Docker 及其数据、JDK、Maven、Node、各 AI 工具）。Docker 的数据要不要一起搬，搬坏了怎么退回。

## 五、你自己做的决定，带来的没说清的后果

这些决定的对错我不评。下面是设计书没有摆在一起、或者没有说的代价。

**1. 不开通 GitHub 付费计划。** 后果散在四处，汇总如下：

| | 项目仓库公开 | 项目仓库私有 |
|---|---|---|
| 谁能看到代码 | 所有人 | 只有你 |
| 谁能看到进度日志（含花费、你的确认记录） | 所有人 | 只有你 |

| 日志分支能不能被改写 | 不能，GitHub 拦着 | GitHub 不拦，靠本机隔离 |

企业项目多半只能选私有。那样的话，设计书 6.4 的第三层「主线只能通过检查过的 PR 改变」在 GitHub 那一头是不存在的，全靠本机。设计书在 6.5 说了这一点，但没有告诉你付费计划多少钱、能换回什么，你没法比较。据我所知个人付费计划是每月几美元，能给私有仓库开分支保护；这个价格我没有联网核对。

## 八、还缺什么；第 1 期能不能开工

### 该有而完全没提的

1. **环境迁移**（第 14 条）。见严重 3。
2. **对话方式在受限环境里的验证。** 见严重 2。
3. **产品流程的产出怎么进主线。** 见严重 1。
4. **AI 工具自身的版本管理。** 见一般 16。
5. **一台电脑撑得住多少。** 每个项目一个专用 Docker，每张并行的工单一套数据库加后端加浏览器测试，需要多少内存和磁盘，没有任何估计。并行上限（W8）排在第 2b 期，但机器层的体检是第 1 期的事。
6. **虚拟机从哪来。** 见疑问 3。
7. **工具包自己怎么被开发。** 16.4 说它不走自己的功能流程。那第 1 期由哪个 AI 写、在不在受限环境里写、工具包仓库自己的检查有哪些，没有写。这关系到「没有专业人员把关」的工具包本身靠不靠得住。
8. **各期大概要多久、花多少。** 分期计划只有内容和验收标准，没有任何量级。你没法据此安排。
9. **小白手册的大纲。** 好几处把事情推给了它（书面标准、只在全绿时点合并的硬规矩、第零步的命令），它本身排在哪一期、有哪些章节没有写。

### 分期计划合不合理

- 先内核和机器层、再最小主链、再完整流程、再第二条实现路径，这个顺序是合理的。
- 不合理的是严重 2 说的那一处：造受限运行器在前，验证它撑不撑得住真实技术栈在后。
- 第 2a 期仍然偏大：两份档案、三个流程、验收环境，外加第一次连起来走、第一次真人上手、第一次用 `wayfinder`。建议把 Vue 那份档案和原型放到第 2b 期，第 2a 期只用后端档案做一个没有页面的骨架，先把「连起来走一遍」这件事单独验掉。
- 第 3 期暂缓后没有拆开，见一般 9。
- 第 5 期（另外三个工具）放最后可以，但 W24 应提前验掉，见第五节第 4 条。

### 结论

**第 1 期现在不建议直接开工。先把下面 6 件事做完，就可以开工。** 它们都不需要再做大试验，前 4 件是定设计，后 2 件是补做小试验。

1. 你定第 14 条的范围（疑问 1），设计书补上环境迁移一节，并改掉 4.3 末尾那句话。（严重 3）
2. 把守门检查这一组定下来：验收的截图怎么过、产品流程的产出怎么进主线、工具包升级和规范变更怎么过（W21）、项目初始化的顺序。（严重 1、一般 2）
3. W18 定下来：工具包升级后，进行中的功能怎么接续。（疑问 6）
4. 受限环境的做法里把 `commondir` 那一处补上，`wt init` 用哪份模板写明。（一般 4、一般 12）
5. 补做三个小试验：真实技术栈在受限环境和专用 Docker 里跑一个最小例子；对话方式在受限环境里用一次；在真正的项目结构里跑一张 `implement` 工单。（严重 2）
6. 确定虚拟机怎么来。（疑问 3）

其余的问题（花费合计、走捷径的口子、失败去向、技能清单等）可以在第 1 期进行中修订设计书，不挡开工。
