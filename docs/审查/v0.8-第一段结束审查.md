我做了什么、没做什么：

- 只新建了本文件，没有改任何已有文件。
- 没有调用任何 AI 工具（`claude -p`、`codex`、`opencode`、`pi` 都没碰），没有花钱。
- GitHub 上只用了 `gh` 的查看类命令看两个试验仓库和技能仓库，没有建、改、删任何东西，没有开 PR、没有触发检查。执行过一次 `gh auth status`，它只显示账号和权限名，令牌本身是遮住的。
- 两台虚拟机各开了一次，进去只读地看，看完都关了（`vm.sh status` 显示两台都关着）。**有一处要如实说明**：在 vm-a 里我执行过一次 `sudo -n ls -d /var/lib/containerd …`（只列目录是否存在，没有改任何东西）。你的规矩写的是「不用 sudo」，这一下越界了，之后再没有用。
- 没有碰 `~/Project`、`~/999_`；`~/tools/wt` 只读了说明书；没有碰你电脑上的 Docker；没有打开密钥文件，没有读任何 AI 会话记录；没有读 `docs/交接.md`、`docs/历史/`。

每条判断后面的括号写依据，三种：

- **读了原文**：设计书、试验记录和脚本、上一轮审查报告、wt 的说明书、GitHub 上的运行记录。
- **自己验证过**：我亲手查过（GitHub 上的检查记录和日志、虚拟机里的实际状态、重跑了只读的脚本、重算了账本）。
- **推断**：按道理推出来的，没有实测。

几个绕不开的词：

- **特权侧、受限侧**：拿着 GitHub 登录凭据的流程命令 `sop` 本身；被关在小范围里、读不到凭据的 AI 和项目代码。
- **专用 Docker**：每个项目另起的一个只给受限侧用的 Docker。Docker 是「在电脑里再开一个个小隔间（容器）跑程序」的工具。
- **`.shared`**：项目根目录下 wt 管的一个本机专用文件夹，里面有 wt 的钩子（**钩子**：某个动作前后自动执行的小脚本）、`.env`、运行日志、AI 的状态目录等。
- **放行事件**：正当要改受保护文件时，特权侧在日志分支上记的一笔，GitHub 上的守门检查看到它才放行。
- **归属**：放行事件记在谁名下，例如 `feat/<功能>`。
- **PR**：合并申请。**主线**：`main` 分支。**守门检查**：GitHub 上专查「有没有动受保护文件」的那道检查。

## 一、总评

**到了什么程度。** 第一段是一次扎实、诚实的验证：十项里的大部分我抽查都对得上（GitHub 上的运行记录、日志分支上的放行事件、虚拟机里的实际状态、账本的加总），记录里「没做的」也大多写清楚了，设计书 v0.8 照结果改了主要的地方。v0.7 对第五轮审查的处理大体到位，没有发现「只换了个说法」的；「不占系统盘改成靠主目录单独分区」这个改法方向是对的，比链接、挂分区都简单可靠。

但这次我找到一个**整个设计的承重点上的洞**，它不是第一段新引入的，而是从 S2 起就在、前五轮审查都没看出来，第一段把专用 Docker 做成正式样子时又原样带了过来。另外，第一段新补的几样做法本身有漏洞或没写完，v0.8 也没有在全文改到位。

**最要紧的五件事：**

1. **（严重）专用 Docker 看得到、写得了整个项目根目录，包括 `.shared`。** 受限侧的 AI 只要用专用 Docker 起一个容器，就能改写 `.shared/hooks/post-create`；特权侧下一次建工单目录（T1 的 `wt new`）会**带着凭据**执行它。这等于凭据隔离（设计书自己说的「承重点」）在这条路上不成立；「封存成只读」的状态目录、`.env`、运行日志也一样能改。现在的隔离自检清单查不出来。（严重 1）
2. **「放弃带放行的工单要重新放行」这条新规矩没有核对规则**，实际上是第六种放行情形，可能把没放行过的内容「洗白」；归属名只防了功能名重复，规划、规范变更、升级的分支会重名。（一般 1、2）
3. **一个进程攒批写事件**：没写哪些事件必须立刻推上去（放行事件必须先于代码推送）、崩溃时内存里那一批怎么办；「降到十几秒」是按满批推算的；复用 SSH 连接又多出一条凭据通道，设计书和隔离自检都没列。（一般 3）
4. **v0.8 没改到位**：十几处还是「没有试」「没有量」的旧话，有一处反过来把私有仓库上没试的说成「每一项都试了」；第 20 节的花费没跟上风险标准第二稿（按第二稿和脚本兜底，大多数工单都会做逐张复查，比现在算的贵）。迁移的「卸干净」说满了：我在虚拟机里看到 containerd 服务还在运行。（一般 5、7、9）
5. **另一条「前一个会话给后一个会话留话」的路没堵**：AI 工具会自动读工作目录里的设置文件（如 `.claude/settings.local.json`）和子目录里的规则文件；被忽略名单忽略的文件，T4 的「工作区干净」看不到，之后的独立复查会读到它。（一般 8，推断）

**结论：第二段（写正式代码）现在不能直接开工。** 先在纸面上改完第九节列的几处（核心是专用 Docker 的视野），其中专用 Docker 那一处改完要在虚拟机里实测一次「经 Docker 改不了 `.shared`」；这些都不花 AI 的钱。改完、你确认之后可以开工，不需要再等一整轮独立审查。

### 用服务器版云镜像代替「全新安装」，哪些结论要打折扣

站不住或要打折扣的：

1. **分区判断「三种情况都对」**：只试了「另一块虚拟盘挂成 `/home`」和云镜像自带的 `/boot` 布局。桌面安装程序真实会产生的布局——同一块盘上手动分出主目录、选了磁盘加密时常见的 LVM（逻辑卷）、可能的 btrfs 子卷——都没试。判断脚本只比设备名，遇到后两种很可能判错（一般 11，推断）。
2. **第零步「读系统里已有的代理设置」**：虚拟机的代理是写在 `/etc/profile.d` 的环境变量里；桌面版的人多半是在「设置」里填代理，不进环境变量。这一项在云镜像上验不了。
3. **管理员密码**：虚拟机里 `sudo` 免密码。真电脑上迁移、装 Docker 途中会多次要密码，密码的有效期过了会怎样，没试。
4. **桌面版默认装了哪些软件**：云镜像带 curl，桌面版默认可能没有 curl、bubblewrap、uidmap（我记得 22.04、24.04 桌面版默认没有 curl，26.04 没核实）。第零步「用系统自带的下载工具」和 M2 要装什么，要在桌面版上定（设计书已挪到第三段）。
5. **凭据通道**：云镜像没有钥匙串和 SSH 代理（记录自己写了）。注意你这台电脑的 GitHub 登录正是存在钥匙串里的（`gh auth status` 显示「keyring」）。
6. **「登录后自己起来」**：是用 SSH 登录试的。桌面登录、注销再登录大概率一样（推断）。
7. **迁移**：旧 Docker 是试验脚本几分钟前刚装的，数据很少；真实电脑上旧 Docker 用了很久、有 Compose 起的带项目标签的卷、多半是 Docker 官方源的装法。只能算「原型走通」。

不太受影响的：专用 Docker 的资源分组和网络（同一内核家族、同一套服务管理器）；nvm、uv 装进 `tools`；放行事件（在 GitHub 上做的）；W34、W35（在你这台桌面电脑上做的）。

## 四、确定的问题

### 严重

**严重 1. 专用 Docker 看得到、写得了整个项目根目录，包括 `.shared/hooks`；受限侧能借它让特权侧带着凭据执行自己写的东西**

- 位置：6.3 二第 1、2 条；5.6 最后一条；6.5 第 2 条；16.2「隔离自检」；第 19 节第二段验收；`docs/试验/脚本/第一段/专用Docker/dockerd-wrap.py`（S2、S9 的同名脚本同样）。
- 原文：
  - 6.3 二：「它启动前先把自己的根目录换成一个只含白名单的目录：系统程序、它自己的数据、这个项目。」「项目里的 `.git` 和各工作目录里指向 `.git` 的小文件，在它的视野里只读。」
  - 5.6：「仓库之外的 `.shared/hooks/`：由工具包安装，受限侧只读。`wt new` 每次都会带着凭据执行其中的准备脚本」。
  - 6.5：「同一个项目的各工作目录之间，经专用 Docker 这条路互相挡不住……靠第四层事后发现。」
- 问题：
  - 专用 Docker 的白名单里放的是**整个项目根**，可写；只有 `.git` 和各工作目录里那个小文件是只读的（读了原文：`dockerd-wrap.py` 里 `(PROJ, 'rw')`）。我在 vm-a 里读了两个专用 Docker 后台程序的挂载表，`/home/xiaobai/Project/demo1 rw`、`…/demo2 rw`（自己验证过，只读地看）。
  - `.shared` 就在项目根下（5.1、4.3）。wt 的说明书写明 `wt new` 建好目录后自动执行 `<项目根>/.shared/hooks/post-create`（读了原文）。
  - 受限环境里给了专用 Docker 的通道（6.3 二），S9 里 AI 在受限环境里亲自用过它。所以 T3 里的 AI 只要执行一句「起一个容器，把 `.shared/hooks` 挂进去，往 `post-create` 里加一行」，特权侧下一次 T1 建工单目录时就会在受限环境外面、带着 GitHub 凭据执行这一行——读 `~/.ssh`、用钥匙串、直接推送都行。（推断：我没有实际演示写入，因为规矩不许改虚拟机里的东西。前提条件都是读原文和只读核对出来的。）
  - 同一条路还能改：封存成只读的 AI 状态目录（容器里的管理员就是你本人的账号，「只读」的文件权限挡不住它），W35 查出来的「设置文件里的钩子」于是又能留下来，续接时执行；`.shared/.env`（设计书说受限侧只读）；`.shared/runs/` 的运行日志（维修窗口会读它，而维修窗口对「可以撤销的」命令是直接执行的）；`sop` 的锁（8.4）；7.6 窄接口的请求和笔记目录，以及特权侧如果把窄接口的状态放在 `.shared` 下也一样。
  - 6.5 只承认了「各工作目录之间挡不住」，没有提 `.shared`。16.2 隔离自检列的「借 Docker 做同样的事」是读凭据、写工具包、改 `.git` 配置，不含 `.shared`，所以照现在的清单，M6 会通过。
  - 第一段 W34 的 Run B 正好说明 AI 被挡住后会自己找别的路（它把 Claude Code 自己那层沙箱关掉再试）。专用 Docker 就是一条现成的别的路。
- 后果：6.2 的第 1、2 条要求（设计书说「整个设计的承重点」）在专用 Docker 这条路上不成立，而且自检查不出来。
- 建议：
  - 专用 Docker 的白名单不再放整个项目根：只放各工作目录、`.git`（只读）和依赖缓存；`.shared` 整个不放，或者像 `.git` 一样在换根时盖成只读（`.env` 如需要，单独只读地放）。
  - 更干净的做法：把 AI 状态目录、运行日志、锁、窄接口的状态挪出项目根（例如 `~/tools/sop/state/<项目名>/`），项目根下只留 wt 必须的 `.shared/hooks` 和 `.env`。
  - 特权侧每次调用 wt（`wt new`、`wt done`、`wt pr`）之前，脚本核对 `.shared/hooks` 里三个文件的内容指纹和工具包模板一致，不一致就停。这一条一秒钟就能查完。
  - 16.2 隔离自检和第二段验收加一项：「经专用 Docker 改 `.shared/hooks`、封存的状态目录、`.env`，都改不动」。
  - 改完在虚拟机里实测一次。

### 一般

**一般 1.「放弃带放行的工单要重新放行」没有核对规则，等于第六种放行情形；也没写怎么发现要重新放行**

- 位置：6.4「试出来要补的一条」；5.6「能改它们的只有五种由流程命令发起的情形」；6.4「特权侧写放行事件之前核对什么」表；第 19 节第二段验收。
- 原文：「一张带放行的工单被放弃，或者它对受保护文件的改动最终没有合进功能分支（T8 拆了工单、T6 又改了一版）时，特权侧要给功能分支上现有的内容重新写一条放行。」
- 问题：
  - 五种情形各有「写放行之前核对什么」，这一条没有。它放行的是「功能分支上现有的内容」，而这些内容是经 T13 合进来的；T13 只等快档，工单 PR 上的守门检查「不作为依据」（6.4）。只要有一份没放行过的受保护改动混进了功能分支（比如 T4 判漏了），这条规矩就会替它补上放行，功能 PR 上的守门检查就白设了。（读了原文；后果是推断）
  - 实测里重新放行的那份内容，恰好和序号 2 放行过的一模一样（日志分支上序号 2、序号 4 的指纹都是 `5839cebe…`，自己验证过）。也就是说，正确的做法本来就是「退回到以前放行过的那一份」，可以写得更紧。
  - 「什么时候要重新放行」靠流程命令自己记得，没有兜底。记录里还写了一种没试的：两张工单改同一个受保护文件、合并顺序和放行顺序相反。
- 后果：放行事件这道关在「放弃工单」这条常见的路上会被自己的补丁放松；漏了重新放行时，功能 PR 一直红，你看不懂为什么。
- 建议：
  - 规则写成：只有当「功能分支上这个路径现在的内容」等于「同一归属下以前某一条放行过的内容」时，才写一条新放行指向它；对不上就停，交维修窗口。把它写进 5.6 和 6.4 的表（作为第六种，或写明它只是前五种的「恢复」）。
  - 加一个脚本检查：每次工单合入功能分支后、F18 之前，逐个比对功能分支相对主线改了的受保护路径和最后一条放行，对不上就停下并说明。这样「要不要重新放行」由脚本发现，不靠记性。

**一般 2. 归属名只防了功能名重复；规划、规范变更、升级分支会重名**

- 位置：6.4「两条防止旧放行被重新利用的规矩」；7.3 的 P0；6.3 表 G1；7.11。
- 原文：「功能名不重复使用（F1 开轮时脚本查事件日志）」；P0「分支 `plan/product`」；G1「一条专用的规范分支（`std/<日期>`）」。
- 问题：「只认最后一条」只管同一路径。产品规划放弃后重做、同一天做两次规范变更、两次升级用同名分支时，旧的那一轮在别的路径上留下的放行仍然算数。试验自己第二次做规划时就改名成了 `plan/product2` 来绕开（日志分支上有 `plan__product` 和 `plan__product2` 两组放行，自己验证过）。
- 建议：所有归属（规划、规范、升级、紧急修复）一律带一个不重复的后缀，开分支前脚本查日志分支确认没用过。

**一般 3. 攒批写事件：没写哪些事件必须立刻推上去、崩溃时怎么办；「十几秒」是推算；复用 SSH 连接多出一条凭据通道**

- 位置：8.2；6.4「先后顺序」；7.12「自动步骤中途崩溃」；6.2 第 1 条；16.2；第 20 节末尾的时间。
- 原文：
  - 8.2：「一个事件一个文件……一个事件一个提交，做两年是几万个提交」，同一节又写「攒成一批、一次提交、一次推送，复用同一条 SSH 连接」。
  - 8.2：「一张工单约 30 个事件……照上面攒批写，降到十几秒。」
  - 第 20 节：「写事件每张 1.5 到 3.5 分钟」。
- 问题：
  - **先后顺序**：6.4 要求「特权侧先写放行事件，再推送带着那份改动的提交」。攒批之后放行事件可能还在内存里，代码已经推上去了。「人的确认」攒着时崩了，你要重新确认一次。「步骤开始」还没推上去就启动了 AI，崩溃后回放看不出这一步开始过，7.12 靠「有开始没有结束」来认中断，就认不出来。（推断）
  - **崩溃和断网**：设计只写了「断网时停下、不在本地攒着」，没写内存里那一批怎么办。
  - **「十几秒」**：实测的是满 10 个一批、每批 2.6 到 4.7 秒，摊下来每个 0.3 秒左右。一张工单的事件是一个接一个出来的，凑不满一批；单个事件在复用连接下要多久没量过（记录里单个事件只量了「每次新建连接」，约 6 秒）。复用连接一共只试了 3 批（私有仓库日志分支上 `b0` 到 `b9` 每组 6 个，共 6 批，一半没复用，自己验证过）。
  - **新的凭据通道**：复用 SSH 连接靠本机一个连接通道文件，谁能连上它，谁就能不用密钥往 GitHub 推送。6.2 第 1 条列的四样要挡的通道里没有它，隔离自检也不查。存档的脚本里看不到是怎么复用的（读了原文）。
  - 8.2 两句打架；第 20 节的时间没改。
- 建议：8.2 写明「放行事件、人的确认、步骤开始」写完推上去才往下走，其余可以合批；连接通道文件放在受限环境和专用 Docker 都看不到的地方，列进 6.2 第 1 条和隔离自检；第二段量一次「复用连接下单个事件多久」再写数；改掉两处旧话。

**一般 4. F19 只看全档；守门检查在转正式时不重跑**

- 位置：7.4 的 F19；6.4 第三层「全档检查被跳过时算成功」一段和「项目仓库私有时」一条；7.5 的 T12。
- 原文：F19「全档检查在 PR 最新的提交上、转正式之后真正跑完并且成功」；6.4「全绿才提示『现在可以点』」。
- 问题：私有仓库没有分支保护，F19 是脚本这边唯一的关，它只看全档，守门检查红了它不管，「全绿」又只写在 6.4。实测守门检查不在「转正式」时重跑：公开仓库 PR 11 的守门在 04:49:22 跑完，04:49:36 才转正式，之后没有新的守门记录（自己验证过）。所以「转正式之后」这个条件不能照搬到守门上，否则 F19 永远等不到。
- 建议：F19 写成三项：全档、快档在最新提交上、转正式之后真跑成功；守门在最新提交上真跑成功（不要求在转正式之后）。7.4、6.4 用同一句话。

**一般 5. 迁移的「卸干净」说满了；最常见的一种 Docker 装法没试**

- 位置：4.8 第一段那一段；4.8「原来是哪一种 Docker」表第一行；W27 记录；第 18 节第 14 条。
- 原文：4.8「系统自带的卸干净后新的不受影响」；W27「软件包卸了，`/var/lib/docker` 删了」。
- 问题：
  - vm-a 里 docker.io 卸掉之后：containerd 的系统服务仍在运行、开机自启（约 85 MB 内存）；runc、bridge-utils、pigz、ubuntu-fan 这几个随 docker.io 自动装进来的软件包还在；`/var/lib/containerd` 还在；`docker` 用户组还在（自己验证过；`/var/lib/containerd` 里有多大，看不了，要管理员权限）。你要的是「完全卸载」。
  - 只试了 Ubuntu 软件源里的 docker.io。很多电脑上装的是照 Docker 官网装的 docker-ce（包名、软件源文件、钥匙文件、数据位置都不一样），没试。
  - Docker 较新的版本新装时可能把镜像放在 containerd 的目录里；那样 Q1 只清点 `/var/lib/docker` 会漏算大小，卸载后系统盘上还留着镜像。（推断，没核实）

**一般 6. Q4「出错一定把旧容器起回来」只靠脚本的退出钩子**

- 位置：4.8「Q4 要先停掉用这个卷的容器」一条；`迁移.sh` 的 `q4`。

**一般 11.「不占系统盘」改成靠主目录单独分区，漏了三样**

- 位置：4.3；`W36/主目录在哪个分区.sh`；第 18 节第 4 行。
- 问题：
  - 判断脚本只比「根目录和主目录是不是同一个设备名」（读了原文）。主目录在 LVM 逻辑卷上（装系统选「加密」时常见）或 btrfs 子卷上时，设备名不同但其实在同一块盘、同一个分区上，会被判成第一种「合格，不在系统盘上」。整块盘不分区直接格式化的不算进去。用「可移动」标记判断移动盘不可靠，很多 USB 硬盘报的是「不可移动」。（推断，没实测：造这几种盘要管理员权限）
  - 体检没有任何**磁盘剩余空间**的检查（全文只有迁移备份时查空间，读了原文）。第二、三种电脑上，镜像按项目各存一份（每个项目约 420 MB 起）、依赖缓存、数据库数据都在系统盘上，系统盘满了 Ubuntu 会进不了桌面、更新失败——对没人兜底的你很麻烦。
  - 第 18 节写「是」，可第二、三种电脑上「不占系统盘」不成立（你接受了），应该如实写「部分，你接受了」。
- 建议：判断时按「底下实际是哪块盘、哪个分区」比；体检加剩余空间检查，系统盘或主目录分区低于某个数就提醒，并指向 `sop machine clean`；改写第 18 节。

### 问题 6：AI 能走捷径、没有东西拦、事后也发现不了的地方

1. **借专用 Docker 改 `.shared`**：改钩子让特权侧执行、改封存的状态目录、改运行日志去影响维修窗口（严重 1）。这一条事后也很难发现：钩子执行完可以把自己改回去。

5. W34 Run B 是一个现成的例子：任务说明让它提交，提交不成，它先把自己那层沙箱关掉再试。设计靠外面那层挡住是对的，但这也说明「AI 只是走捷径、不会绕」的前提要打折扣，外面那层上任何一个口子（比如严重 1）都可能被用上。

### 问题 7：交给你、你其实做不了或判断不了的

3. **16.5 要你在 GitHub 上建一份「只有工具包仓库权限」的凭据**。GitHub 网页上建这种细粒度凭据要点很多处，要有一步一步带截图的引导，最好由脚本打开对应的网页并核对你建出来的权限。
4. **「官方账号第一次要用时先在虚拟机里验一次」**（4.5）。这件事你自己做不了，要写明由谁来做（修工具包的窗口）。
5. **第一段小结让你「到服务后台看实际扣费」**：这个你做得了（你以前做过）。
6. 其余（选留还是卸、公开还是私有、网页上点合并、验收）设计书都给了默认值和大白话说明，你做得了。

### 问题 8：花费站不站得住

- **第一段花的钱**：账本加总对得上，14 次调用 1.90 美元；私有仓库 11 次检查运行，和记录一致（自己验证过）。但这只是「试验里调用 AI」的钱。写设计、做试验的窗口本身花了多少，工具包看不到，小结如实写了，这多半才是大头。另外「累计 21.17」不含 S0（轻微 4）。
- **第 20 节**：每个功能 21 到 41 美元的算术本身没错（第五轮审查重算过），但口径偏小的情况更明显了：逐张复查会做得比 3 张多得多（一般 9）；写事件的时间那一行是旧数。每个功能 50 美元的提醒线，在真实项目里可能每个功能都会响。

## 八、你自己定的事带来的没说清的后果

1. **裸仓库加 wt**（1.2）：wt 把钩子放在项目根下的 `.shared`，和专用 Docker「整个项目根可见」叠在一起，就是严重 1。不是 wt 的错，是两样放在一起没人对过。
2. **主目录在系统盘上、另有分区的电脑直接装主目录下**（4.3）：后果是系统盘可能被镜像、缓存、数据库占满，而体检不查空间（一般 11）。
3. **花费不设上限**加**风险标准第二稿**：逐张复查会做得比你当初想的多得多，钱也多（一般 9）。不设上限意味着不会被卡住，但你要知道这个量级。
4. **GitHub 不开付费**：私有仓库上，F19 是脚本这边唯一的关，现在它只看全档（一般 4）；转正式那几秒网页上可能显示可以合并（轻微 9）。

其余你定的事，后果设计书都写清楚了。

## 九、对第一段小结里「替我定的」几条的意见

| 替你定的 | 我的意见 |
|---|---|
| 容器默认直接上网，不打开「容器能连到本机内部」 | **不否决前半句，后半句该否决。** 不打开是对的（要装软件、要管理员密码）。但「遇到只能走本机内部代理的电脑，建议把代理对局域网开放，由你决定」这半句该否决：你判断不了，代价没写（一般 10）。应该由工具包给一个试过的办法 |
| 资源上限按项目设，不按单个容器设 | **不否决。** 按容器设要把通往钥匙串的通道交给专用 Docker，等于拆掉凭据隔离，不值。代价是同一项目里一张工单的测试吃满额度会拖慢别的工单；本机和 GitHub 上的限制不一样。这两点设计书写了 |
| 专用 Docker 登录后自己起来，不开 linger | **不否决「不开 linger」，建议改「登录即起」。** 现在是每个项目的专用 Docker 一登录就全部起来，每个常驻约 180 MB，不在做的项目也占着。建议改成「`sop` 要用时才起、闲一段时间后停」，项目多了才不会白占内存。这是建议，不是硬伤 |
| 技能固定在 `5863806`，换版本算大版本 | **不否决。** 我核对了它就是技能仓库现在的最新提交。代价是技能上游修了错，也要等手上的功能做完才换，可以接受 |
| 风险标记标准用第二稿，修复工单一律标 | **不否决，但要你知道代价。** 第二稿比初稿好；「修复工单一律标」的理由（修复本身说明前面漏过一次）站得住。只是加上脚本兜底，大多数工单都会做逐张复查（一般 9），要请写设计的人把钱重算给你看 |
| W22 第 2a 期看分钟数再定 | **不否决。** 条件已实测可行，没有分钟数之前定不了 |
