# 第一段 W21：放行事件（含 W22、W17、合并要不要 `workflow` 权限）

状态：已完成（2026-11-18）。设计书 6.4 列的要试的几项都试了，放行事件这个做法在公开和私有两个仓库上都成立。另外发现两处要补进设计书：放弃一张带放行的工单之后要重新放行；GitHub 的「可以合并」状态在转正式的那一瞬间不可信。

没有调用 AI，没有花钱。用了私有仓库的免费检查时长：真正跑了的任务 11 个，合计 93 秒（按「不足一分钟算一分钟」最多 11 分钟）。公开仓库跑了 44 次工作流，公开仓库不计时长。

**在 GitHub 上建了两个试验仓库**（用户 2026-11-17 同意建、试完删）：公开的 `C1fLly/sop-p1-guard-public`、私有的 `C1fLly/sop-p1-guard-private`。里面全是假内容，没有任何真的密钥。审查看完运行记录后，2026-11-18 按用户的答复删了。

脚本和试验仓库的初始内容在 `docs/试验/脚本/第一段/W21放行事件/`。

## 要验证什么

设计书 6.4 的「放行事件」：特权侧在日志分支 `sop/journal` 上按「归属、路径、内容指纹、序号」写放行事件，GitHub 上的守门检查（定义永远取自主线、不运行 PR 的代码）凭它放行对受保护文件的正当改动。6.4 列的要试的几项，加上 v0.7 加的几项：

1. 守门检查读不读得到日志分支；日志里有几千个事件时读一次要多久。
2. 工单 PR 压合进功能分支之后，功能 PR 上的守门检查仍然通过。
3. 解决冲突产生的合并提交不影响结果。
4. 把受保护的文件改回旧内容、借用别的功能的放行，都通不过；删除受保护的文件，有放行才通过。
5. 检查抢在放行事件前面跑了之后，重跑能通过。
6. 同一路径两条放行，只认序号大的；守门检查只取日志最新的一份。
7. 改了 `sop.json` 的 PR 上，新档案的受保护清单被并进来。
8. 全档检查在草稿期间被跳过、转正式后真的跑；F19 能分清「跳过」和「真跑完」。
9. 用 `gh` 合并一个改了检查流程文件的 PR，现有的凭据权限够不够。
10. W22：草稿期间的功能 PR 连快档也跳过，条件写得出、管用。
11. W17：几个进程同时往真的 GitHub 写事件要多久、被抢先重来几次。

## 怎么做的

- 两个仓库的主线上放了：一份假的项目声明 `sop.json`、两份假的规范文件、一张假的页面截图、一个普通文件、一个假的项目检查脚本，以及三样「工具包」的东西：项目检查的流程（快档、全档，触发写明含「草稿转正式」）、守门检查的流程（`pull_request_target`）、守门检查的脚本和受保护清单（工具包的基础清单，加一份假档案 `demo` 的清单）。
- 守门检查（`guard.py`，约 100 行）：只把 PR 的提交当数据读，算出它相对目标分支改了哪些文件、受保护文件现在的内容指纹；只取日志分支最新的一份，读 `releases/<归属>/` 下的放行事件；受保护清单只从主线取，PR 改了 `sop.json` 且放行对得上时并入新档案的清单。从不检出、不运行 PR 里的东西。
- 特权侧写放行（`release.py`）：照 S6 的写法，不检出日志分支，直接造一个只多一个文件的提交、不强制推送；序号是读出现有最大的再加一，被抢先就重读重来。
- 公开仓库开了分支保护：主线要求快档、全档、守门三项通过，对管理员同样生效；日志分支禁止改写和删除。私有仓库的免费计划开不了保护。
- 合并都用脚本（`gh pr merge --squash`），代替设计里公开仓库的特权侧和私有仓库的小白点按钮。

## 结果

### 放行事件本身（公开仓库为主，私有仓库重复了关键几项）

| 情形 | 结果 |
|---|---|
| 工单 PR 改了页面截图，还没写放行 | 守门不通过：「没有放行」 |
| 写了放行、让守门检查重跑 | 通过（第 5 项） |
| 工单 PR 压合进功能分支后，功能 PR 的守门检查 | 通过（第 2 项）。截图的内容指纹不受压合影响 |
| 工单和功能分支冲突，在工单分支上用合并解决冲突后 | 通过，功能 PR 也通过（第 3 项）。有冲突的时候项目检查不跑、守门检查照跑，和 S4 一样 |
| 功能分支上的规范已是第 3 版（序号 2 放行），工单把它改回第 2 版（序号 1 放行过、较松） | 不通过：「指纹对不上最后一条放行」（第 4、6 项） |
| 工单把规范改成功能 b 名下放行过的内容 | 不通过（借用别的功能的放行，第 4 项） |
| 工单删掉一个受保护的文件，没有放行 | 不通过；写了「删除」的放行再重跑，删除那一处通过（第 4 项） |
| 规划 PR 改 `sop.json` 选档案 `demo`，`sop.json` 没有放行 | 只报 `sop.json` 没放行，新档案的清单不并入（第 7 项） |
| `sop.json` 有放行 | 并入档案 `demo` 的清单；新加的规范文件、新加的覆盖配置 `eslint.config.mjs` 都被拦住，各自写了放行才通过（第 7 项） |
| 日志分支有 5016 个文件、5017 个提交时 | 守门检查只取最新一份，读日志 1.47 秒，整个守门任务 7 秒（第 1、6 项）。日志里只有几个文件时读日志 0.2 到 0.8 秒 |
| 私有仓库：没放行不通过、写放行通过、压合后功能 PR 通过 | 和公开仓库一样 |

### 新发现一：放弃一张带放行的工单，功能 PR 会一直是红的

- 工单 8 把规范改成第 4 版，特权侧为它写了序号 3 的放行；然后工单 8 被放弃（关闭、没合并）。
- 功能分支上仍是第 3 版，可最后一条放行是第 4 版，功能 PR 的守门检查从此一直不通过：「指纹对不上最后一条放行」。
- 特权侧给功能分支上现有的第 3 版重新写一条放行（序号 4），重跑就通过了。

所以要加一条规矩：**一张带放行的工单被放弃、或者它对受保护文件的改动最终没有合进功能分支（T8 拆工单、T6 修复时又改了一版都算）时，特权侧要给功能分支上现有的内容重新写一条放行。** 同一个功能里两张工单都改了同一个受保护文件、先写放行的后合并时，中间也会短暂变红，最后合进去的那一份有最新的放行就恢复；第五轮审查推过这种情况，这次没有专门试。

另外，试的时候第一次把「改回旧内容」这一项做成了：功能分支本来就还是旧内容，工单「改回」它，相对目标分支其实没有改动，守门检查当然通过。这是试验步骤做错了，不是漏洞；照正确的步骤（先把新内容合进功能分支，再改回旧的）重做，通不过。真正的把关在功能 PR 上：功能 PR 相对主线比，任何「改回较松内容」都逃不过。

### 新发现二：转正式的那一瞬间，GitHub 说「可以合并」

在公开仓库上，一个草稿 PR 转正式，之后每秒查一次它的合并状态：

```
0 秒：可以合并　2 到 18 秒：被挡住（检查在跑）　20 秒以后：可以合并（检查都过了）
```

- 草稿期间全档被跳过，GitHub 把「跳过」算成功，合并状态一直是「可以合并」；只是草稿本身合并不了（脚本去合，GitHub 回答「还是草稿」）。
- 转正式之后的第 0 秒，新的检查还没登记上，合并状态仍是「可以合并」。脚本要是在这一瞬间看状态去合并，就会在全档一次都没跑的情况下合进主线。
- 检查记录的接口里分得清：全档有两条记录，较早的一条结论是「跳过」，较新的一条是「成功」。

所以 F19 不能看 GitHub 的合并状态，只能照 6.4 写的：**在 PR 最新的提交上，找转正式之后的那一条全档记录，结论是「成功」才算**；「跳过」一律不算。v0.7 在 6.4 写的就是这个，这次实测确认了它是必要的。私有仓库上一样：全档在转正式后真跑，接口里同样有「跳过」和「成功」两条。

### 第 9 项：合并改了检查流程的 PR，要不要 `workflow` 权限

用现有的 GitHub 凭据（权限是 `repo`、`delete_repo` 等，**没有** `workflow`）合并了一个改了检查流程文件、守门脚本和项目声明的 PR（模拟工具包修补版升级），**合并成功**。推送走的是 SSH，S4 已查明那时也不需要这项权限。所以 M3 申请的权限里不需要 `workflow`。

### 第 10 项（W22）：草稿期间的功能 PR 连快档也跳过

条件写在项目检查的流程里（目标是主线并且是草稿时跳过快档），实测有效：草稿期间快档、全档都显示「跳过」，转正式后两个都真的跑了。跳过的任务不占时长。要不要这样做，取决于每个任务跑几分钟（第 2a 期量），写进 W22。

### 第 11 项（W17）：并行写事件

在私有仓库的日志分支上：

| 做法 | 结果 |
|---|---|
| 一个进程连写 5 个（每次新建连接） | 31 秒，每个约 6.3 秒，重来 0 次 |
| 4 个进程同时各写 10 个 | 一共 263 秒；4 个进程分别被抢先重来 0、10、24、30 次；40 个一个不少，历史是一条直线 |
| 一个进程把 10 个事件攒成一批，一次提交、一次推送（每次新建连接） | 每批 6.3 到 8.4 秒 |
| 同上，复用同一条 SSH 连接 | 每批 2.6 到 4.7 秒 |

结论：**几个进程同时写，总的速度并不比一个进程快**（40 个用了 263 秒，平均每个 6.6 秒），只是互相抢、重来几十次，某张工单的一个事件可能要等半分钟。一个进程替大家写、攒成一批推送、复用连接，平均每个事件 0.3 秒左右。设计书 8.2 改成这样。断网时仍然停下，不在本地攒着（攒一批只是几秒钟之内的事）。

## 结论

1. **放行事件的做法成立。** 按「归属、路径、内容指纹、序号」放行，压合、合并提交、改回旧内容、借用、删除、`sop.json` 并入新档案清单、检查跑早了重跑，都和设计一致。公开、私有两种仓库都试了。
2. **要加一条规矩**：放弃带放行的工单（或它的受保护改动没合进去）时，给功能分支上现有的内容重新写放行。
3. **F19 不能看 GitHub 的合并状态**，只能找转正式之后那一条真跑完的全档记录。实测有一个「转正式后第 0 秒显示可以合并」的空当。
4. M3 不需要 `workflow` 权限。
5. W22 的条件可行，定不定看第 2a 期的分钟数。
6. W17：改成一个进程替大家写、攒批、复用连接。
7. 守门检查读几千个事件不慢（1.5 秒）。

## 试验中自己出的错（如实列出）

- 守门脚本第一版按字符而不是按字节读放行事件，放行里有中文、又不止一条时读错，守门检查报错。它是「出错就算不通过」的，所以没有放过不该放的。修好的版本是通过一个「工具包修补版」的 PR 合进主线的，顺带试了第 9 项。正式的守门脚本要有一个「放行里有中文、有多条」的样例。
- 一次撤销命令的参数写错，导致「改回旧内容」那一项第一次做的步骤不对（见上）。
- 等检查结果的小函数第一版会把上一次的结果当成这一次的，改成只认推送之后开始的检查。
- 有一次重跑之后取不到运行日志（GitHub 对重跑的日志有时不给），改用空提交触发一次新的检查。

## 没做的

- 第三方从自己的副本开 PR（一个账号试不了，S4 也没试）。
- 两张工单同时改同一个受保护文件、合并顺序和验收顺序相反的情形：没有专门造，只推了一遍。
- 私有仓库上没有重复「改回旧内容」「借用」「删除」「`sop.json`」这几项：守门脚本两边是同一份，只验证了私有仓库上读得到日志、放行和不放行都对。
- 私有仓库上小白在网页上点合并：S4 已试过，这次用脚本合并代替。
- GitHub 账号上实际扣了多少时长：查用量的接口要一项现有凭据没有的权限，没有去申请。
