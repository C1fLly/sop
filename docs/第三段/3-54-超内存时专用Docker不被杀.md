# 3-54 超内存时专用 Docker 自己也被杀

2026-11-20。主控窗口派的子代理做的。没调用 AI，没花钱。真起专用 Docker、用 sudo 只在虚拟机里做（`tests/vm/vm.sh new d54`，全新的 `one` 底盘；用户 2026-11-19 已答应第三段在虚拟机里用 sudo、装 Docker、起停专用 Docker）。本机只跑了单元测试和全部自测：没用 sudo，没建任何 systemd 用户服务或分组，没碰 `~/tools/docker` 和它的数据。

**动了隔离。** 专用 Docker 的换根脚本 `runner/docker/dockerd_wrap.py` 多放了一个 runc 外壳、设成默认的运行时，服务登记文件多了一行 `OOMScoreAdjust=100`。视野（哪些目录挂进去、哪些只读）没变，只多了新根里一个只读的 `/sop/runc`。按「动了隔离、放行事件、事件日志三处之一再开一次独立审查」，要告诉用户。

**只做完了一部分。** 「专用 Docker 自己被杀」修好了：改之后在虚拟机里一共演了 84 次超内存，专用 Docker 一次都没被杀（改之前同一台虚拟机 28 次里被杀 9 次）。但「同一项目里在跑的别的容器不跟着停」没做到：吃内存的容器只有一个进程时，内核杀了它之后紧接着常常又多杀一个，现在挑中的是同项目里别的容器（原来挑中的是 dockerd）。这件事拆成新任务 **3-55**。

## 原因（虚拟机里看清的）

1. 分组超了上限，内核先杀吃内存的容器进程，这一下没问题。
2. 紧接着（1 到 2 毫秒后）被杀容器的 `containerd-shim` 收尾时要一点内存，分组还是满的（被杀进程的内存还没还回来），内核**再挑一个杀**。内核日志里 `containerd-shim invoked oom-killer` 每次都在第一个之后 1 到 3 毫秒。
3. 第二次挑谁看「分数」（`oom_score_adj`）加占的内存。**免管理员模式下 dockerd 给容器的分数默认等于它自己的**（Docker 源码 `daemon/internal/rootless/specconv` 的 `ToRootless`：容器要的比 dockerd 自己的低就抬到 dockerd 的；虚拟机里把 dockerd 调成 600、100，新起的容器跟着是 600、100）。所以大家都是 200，占内存最多的 dockerd（约 100 MB）就被挑中；它一死，rootlesskit 跟着退出，服务管理器把整个服务连同所有容器一起收掉再拉起来，同项目在跑的别的容器也就停了。
4. 3-17 记录里的「6 次 1 到 2 次」是吃内存的容器经 `sh -c` 起的情况：容器里剩下的 `sh` 有时先被第二次挑中，挡了一下。

## 做了什么（从根上：让专用 Docker 的分数比容器低）

只改了两处，十几行：

1. **服务里的进程设成 100**（`runner/docker/service.py` 登记文件加 `OOMScoreAdjust=100`）：rootlesskit、dockerd、containerd 都是 100。这是普通用户能设的最低（Ubuntu 的 `user@.service` 是 100，用户服务默认 200，再往下调被拒）。
2. **容器设成 1000**（`runner/docker/dockerd_wrap.py`）：换根时在新根（内存盘）里写一个几行的 runc 外壳 `/sop/runc`（只读），用 `--add-runtime sop-runc=/sop/runc --default-runtime sop-runc` 设成默认的运行时。它在建容器（`--bundle` 下的 `config.json`）、`docker exec` 另起进程（`--process` 文件）时把 `oomScoreAdj` 改成 1000，然后原样交给真的 `runc`。不能只靠第 1 条：容器的分数跟着 dockerd 的走，dockerd 调成 100 容器也是 100，一样的。

这样内核不管第几次挑，都先挑容器（1000），挑不到专用 Docker（100）。容器设 1000 也意味着整台电脑内存不够时，项目的容器先于用户自己的程序被杀，这正是想要的。

试过、没用的（虚拟机里手工试，没进代码）：

- **只把 containerd 调高**（900，让 shim 跟着 901 先被杀）：containerd 自己被杀，`docker run` 卡住半小时不返回。放弃。
- **把服务里的进程挪到下一层分组**：容器的分组位置是「runc 所在分组的上一层」，专用 Docker 的进程和容器永远是同一层的兄弟，挪不开（要单独给容器一个分组得改 runc 的位置，见 3-55）。
- 每个容器带 `--oom-score-adj 1000`：12 次 0 次 dockerd 被杀，但要求每个调用方都带，做不到；所以改成运行时外壳统一改。

## 结果

### 单元测试（多了 4 项，`tests/unit/test_docker_service.py` 的 `TestOomScore`）

- 服务登记文件有 `OOMScoreAdjust=100`。
- 用假 runc 跑外壳：建容器时 `config.json` 里的分数改成 1000、别的字段不动、参数原样交给 runc。
- `docker exec` 的 `--process` 文件也改；带空格的写法也认；`kill` 之类别的命令什么都不改。
- 换根脚本把外壳放进新根、只读，并设成默认的运行时。

全部自测：做之前单元测试 198 项、流程沙箱 24 个剧本、总检查 62 个样例全过；做之后**单元测试 202 项、流程沙箱 24 个剧本、总检查 62 个样例，全部通过**。

|---|---|---|---|

内核日志：改之后被杀的只有容器里的进程（`tail`、`sh`、`sleep`），分数都是 1000；第二次挑的那一下照旧（由 `containerd-shim` 或 dockerd 要内存触发），挑中的变成了容器里的进程。服务的主进程一直没换、重启次数一直是 0。

## 没做的

- **同项目在跑的别的容器还会被内核顺带杀掉**（拆成 **3-55**）：吃内存的容器里只有一个进程时，第二次挑的那一下没有它自己剩下的进程可挑，就挑中了别的容器里的进程（全套里 8 次中 4 次、单独演 15 次中 12 次）。经 `sh` 起的吃法，吃内存的容器里剩下的 `sh` 常常先被挑中：旁边是只睡觉的容器时 16 次 0 次停；旁边也是 `sh` 起的容器时 45 次里停了 8 次（两边的 `sh` 差不多大，挑中谁看运气）。比改之前好（原来是 dockerd 被杀、同项目所有容器一起停），但没达到「别的容器不跟着停」。从根上的办法是给容器单独一个内存分组、专用 Docker 自己不在里面（runc 外壳在建容器时把 `config.json` 的 `cgroupsPath` 指到服务分组下的 `ctr/` 里，限额设在 `ctr/` 上），这样 shim、dockerd 要内存不会触发容器那一组的超限；但这会改「上限管的是什么」（只管容器、不含专用 Docker 自己约 180 MB），还要换根脚本建分组、写限额，改动不小，没在这一项里做。也可能最后只能接受，写明代价交 3-48。
- 外壳只在默认运行时上：容器指定 `--runtime runc` 就绕开了（分数回到 100，和专用 Docker 一样）。这只影响「超内存时先杀谁」，不影响隔离；受限侧的 AI 一般不会这么写。
- 本机没真跑（会建 systemd 用户服务、起专用 Docker）。

## 自己出的错

1. 第一次连着演时每一轮单独开一个 SSH 会话，上一个会话一断用户级服务跟着停了（3-17 记录里写过这一条），8 次都没测到东西。改成一个会话里跑完。
2. `pkill -f "exp.sh ctd900"` 把自己那条 SSH 命令也匹配上杀了；之后用 `[e]xp` 的写法。
3. 第三个小试验忘了先起专用 Docker（上一个会话断开后它停了），每轮等 40 秒超时，白跑了几分钟才发现，停掉重跑。
4. 一开始在小试验里用「占着 40M 的旁边容器」（`head -c 40m | tail &`），以为它一直占着内存；其实 `tail` 读到头就退了，它只剩 `sh` 和 `sleep`。结论不受影响（被挑中的就是它的 `sh`），但记录里的说法按实际改了。
5. 动手前想过把新根整个改成只读，再一想 dockerd 可能要往新根里的 `/var/lib` 之类写东西，改成只把 `/sop` 这一个目录绑成只读。
