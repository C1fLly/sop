# 第二段 W40：公开仓库的 `pull_request_target` 能不能只放开守门检查那一个文件

状态：**第一部分已完成（2026-11-18）；第二部分要等 12 月 2 日 GitHub 真正开始禁用之后（计划 12 月 3 日到 5 日）再做。**

没有调用 AI，没有花钱（公开仓库不计检查时长）。用户 2026-11-18 同意在 GitHub 上建一个公开的试验仓库（全是假内容，试完删）。

## 背景

设计书 6.4、W40：GitHub 从 2026-12-02 起，公开仓库默认挡掉 `pull_request_target` 这种触发方式，守门检查靠的就是它。官方说可以用仓库的「Actions 事件规则」按流程文件的路径放开。没核实的三样：个人账号免费计划的仓库能不能设；用接口设要什么权限；被挡时记成什么。

官方说明（2026-11-18 经网页摘要工具读到，没有逐字读原文）：
- 规则在仓库「设置 → Actions → Policies」里；接口是 `POST /repos/{所有者}/{仓库}/actions/policies`，官方写的权限是「Administration 写」；目前是公开预览，可能会变。
- 「只评估不执行」（evaluate）只有企业版能用，免费的只能选「生效」或「停用」。
- 被默认规则挡掉的运行，会留下一个失败的运行记录，带一条报错说明，流程本身不执行。

## 做了什么

建了公开仓库 `C1fLly/sop-w40-trial`，主线上三个检查流程：

| 文件 | 触发 | 用途 |
|---|---|---|
| `.github/workflows/guard.yml` | `pull_request_target` | 模拟守门检查，要放开的那个 |
| `.github/workflows/other-target.yml` | `pull_request_target` | 对照，不放开 |
| `.github/workflows/check-pr.yml` | `pull_request` | 普通检查，对照 |

用 `gh api` 建了一条规则（规则编号 15840）：

```json
{
  "name": "sop-guard-allow-pull_request_target",
  "enforcement": "active",
  "conditions": { "workflow_path": { "include": [".github/workflows/guard.yml"], "exclude": [] } },
  "rules": [ { "type": "restrict_action_events", "parameters": { "allowed_events": ["pull_request_target"] } } ]
}
```

## 结果（第一部分）

| 问题 | 结果 |
|---|---|
| 个人账号、免费计划的公开仓库能不能设 | **能**，建成了，返回 201 |
| 用接口设要什么权限 | **现有的凭据就够**（权限是 `repo`、`delete_repo`、`gist`、`read:org`、`admin:public_key`，没有另加）。所以 M3 不用为它多申请权限。读规则（`GET`）也够 |
| 请求格式 | `workflow_path` 里 `include`、`exclude` 两个都要写，只写 `include` 会被拒（422，第一次就是这样错的） |
| 12 月 2 日之前开一个 PR | 三个检查都照常跑了、都成功（`guard`、`other-target`、`check-pr`） |

## 还要做的（第二部分，12 月 3 日到 5 日）

## 对设计的影响（第一部分）

- I6 开保护时「设一条事件规则只放开守门那个文件」做得到，接口和请求格式就是上面那样，现有凭据够。
- 规则是「这个文件只允许被 `pull_request_target` 触发」的白名单：守门检查只用这一种触发，正好。
- 免费仓库没有「只评估」，只能直接生效。
